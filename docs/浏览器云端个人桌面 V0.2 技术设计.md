# 浏览器云端个人桌面 V0.2 技术设计

状态：草案

对应需求：第三方静态应用生态

## 1. 设计原则

1. 先实现 GitHub 静态应用安装闭环，不扩展成通用插件平台；
2. 协议负责应用侧契约，宿主实现不能偷偷增加第三方必需步骤；
3. 内建特权层保持编译期可审查；
4. 安装失败不影响现有桌面；
5. 第三方内容与管理界面分 origin；
6. 单用户、单进程、单实例优先，避免过早引入分布式组件；
7. 关键规则必须由服务端实施，不能只依赖前端表单。

## 2. 现状

V0.1 是 Vite 构建、Nginx 提供的纯静态站点：

- 启动时读取 `/config/apps.json`；
- 内建应用和运行时配置在浏览器合并；
- iframe 直接打开配置 URL；
- 桌面状态保存在 localStorage；
- 没有管理 API、服务端状态或应用文件数据卷。

V0.2 需要写入安装文件和共享 APP 状态，因此必须增加服务端。

## 3. 总体架构

V0.2 采用一个 Node.js 管理服务进程，同时提供两个 HTTP origin：

```text
浏览器
├── Desktop Origin
│   ├── React 桌面静态文件
│   ├── GET /api/v1/apps
│   └── /api/v1/admin/*
│
└── 每应用独立 App Origin
    └── /apps/<commitSha>/*

Node.js 管理服务
├── GitHub 获取与检查
├── Manifest/协议校验
├── 安装生命周期
├── APP 表投影
├── 桌面静态文件服务
└── 第三方应用静态文件服务

持久化数据卷
├── state/installed-apps.json
├── apps/<appId>/<commitSha>/
├── staging/
└── trash/
```

单进程维护应用操作锁，V0.2 不支持多副本管理服务。

## 4. 为什么替换纯 Nginx 运行容器

保留 Nginx 再增加管理容器会引入：

- 两个服务间共享数据卷；
- API 反向代理；
- 动态 APP 表同步；
- 本地开发与生产两套不同路由；
- 更复杂的健康检查和部署说明。

V0.2 使用 Node.js 同时提供已构建桌面、管理 API 和应用静态文件，可把首版部署保持为一个容器和一个数据卷。

Nginx 仍可作为用户部署在 Biunivers 前面的 TLS 反向代理，但不再是项目镜像内的必需运行时。

## 5. Origin 模型

### 5.1 必须分离

Desktop Origin 包含管理 UI 和 API。App Origin 只提供已安装应用文件与公开配置。

开发默认：

```text
Desktop Origin: http://localhost:8080
App Origin 基域: http://localhost:8081
应用 Origin:    http://app-<hash>.localhost:8081
```

生产推荐：

```text
Desktop Origin: https://desktop.example.com
App Origin 基域: https://apps.desktop.example.com
应用 Origin:    https://app-<hash>.apps.desktop.example.com
```

第三方应用 iframe 的 URL 必须使用由 app ID 稳定派生的独立 App Origin。App Origin 不暴露管理 API 和桌面静态文件。

这样可以防止第三方应用直接访问父页面 DOM、桌面 localStorage 和只存在于 Desktop Origin 的管理接口。

### 5.2 应用间隔离

宿主以 app ID 的 SHA-256 前 160 bit 生成单标签 `app-<hash>`，避免 app ID 中的点产生多级
子域和 wildcard TLS 不匹配。请求 Host 必须精确映射到一个 active 应用，URL 路径不接受
app ID，因此一个应用 Origin 不能通过修改路径读取另一应用。生产环境需要 wildcard DNS
和证书；本地使用浏览器定义为 loopback 的 `*.localhost`。

建议目录：

```text

├── index.ts
├── config.ts
├── auth/
│   └── adminAuth.ts

├── manifests/
│   ├── schema.ts

│   ├── appService.ts
│   ├── appStore.ts

│   └── errors.ts
```

模块之间的主要依赖：

```text
HTTP route

```

HTTP 层不直接拼接磁盘路径或修改状态文件。

## 7. 运行配置

服务端使用：

| 环境变量 | 必需 | 用途 |
|---|---|---|
| `BIUNIVERS_ADMIN_TOKEN` | 是 | 管理操作 Bearer token |
| `BIUNIVERS_DATA_DIR` | 否 | 数据目录，默认 `/data` |
| `BIUNIVERS_DESKTOP_PORT` | 否 | 默认 `8080` |
| `BIUNIVERS_APP_PORT` | 否 | 默认 `8081` |
| `BIUNIVERS_DESKTOP_ORIGIN` | 是 | 允许的桌面 origin |
| `BIUNIVERS_APP_ORIGIN` | 是 | 生成已安装应用 URL |
| `BIUNIVERS_GITHUB_TOKEN` | 否 | 提高 GitHub API 限额，只保存在服务端 |
| `BIUNIVERS_MAX_APP_BYTES` | 否 | 应用总大小上限 |
| `BIUNIVERS_MAX_APP_FILES` | 否 | 文件数量上限 |

启动时必须验证：

- 两个 origin 合法且不同；
- admin token 非空且不使用示例默认值；
- 数据目录可写；
- 支持列表包含静态应用协议 V1；
- 协议原文和 Manifest Schema 能读取。

## 8. 管理认证

V0.2 使用单一管理员 Bearer token：

```http
Authorization: Bearer <BIUNIVERS_ADMIN_TOKEN>
```

规则：

- 只保护 `/api/v1/admin/*`；
- `/api/v1/apps` 是桌面启动所需的只读公开端点；
- token 只在 Desktop Origin 的设置界面内存中保存；
- 页面刷新后需要重新解锁应用管理；
- token 不写入 localStorage、APP 表或第三方配置；
- 服务端使用恒定时间比较；
- 生产部署必须使用 HTTPS；
- App Origin 不提供管理路由。

这是单用户 V0.2 的最小认证，不扩展账号、Cookie 会话或角色模型。

## 9. GitHub 获取

### 9.1 输入限制

只接受：

```text
https://github.com/<owner>/<repository>
```

拒绝：

- 非 HTTPS；
- 非 `github.com` host；
- URL 用户名或密码；
- query 和 fragment；
- 额外路径；
- 重定向到非 GitHub/codeload GitHub host；
- 任意下载 URL。

### 9.2 解析和下载

`GitHubSource`：

1. 通过 GitHub API 把 ref 解析为完整 commit SHA；
2. 下载该 commit 的 archive；
3. 流式写入 staging；
4. 解包时校验路径和数量；
5. 不解析 submodule；
6. 不下载 Git LFS 对象；
7. 不执行 Git hook 或仓库命令。

可选 `BIUNIVERS_GITHUB_TOKEN` 只用于服务端访问公开 GitHub API，不进入安装配置。

### 9.3 可测试性

`GitHubSource` 使用接口抽象。单元和集成测试通过本地 fixture source 提供 archive，不依赖真实 GitHub 网络。

## 10. 仓库检查

检查顺序：

1. 根目录 `biunivers.app.json` 存在且是普通文件；
2. JSON 可解析且通过内置 Schema；
3. 协议版本在显式支持列表；
4. 对应协议文件存在且 bytes 与内置原文一致；
5. 根目录 `index.html` 和 `LICENSE` 存在；
6. icon 路径合法且文件存在；
7. `appId` owner 与 GitHub owner 一致；
8. ID 不与编译期 internal 或既有其他来源冲突；
9. 不包含符号链接和越界路径；
10. 文件数量和总大小在限制内。

检查结果生成短期 `inspectionId`，保存：

- 来源仓库和请求 ref；
- commit SHA；
- manifest；
- staging 目录；
- 过期时间。

检查记录默认 30 分钟过期。服务重启后可以丢弃，不属于持久安装记录。

## 11. API

所有响应使用 JSON。错误格式：

```json
{
  "error": {
    "code": "MANIFEST_INVALID",
    "message": "biunivers.app.json 校验失败",
    "details": [
      {
        "path": "window.defaultWidth",
        "message": "必须是正整数"
      }
    ]
  }
}
```

### 11.1 桌面读取

```http
GET /api/v1/apps
```

返回 active 已安装应用的 APP 投影。失败时桌面降级到编译期应用和传统配置。

### 11.2 检查仓库

```http
POST /api/v1/admin/inspections
Authorization: Bearer ...
```

请求：

```json
{
  "repository": "https://github.com/example/hello",
  "ref": "v1.0.0"
}
```

返回 `inspectionId`、manifest、commit SHA、安装/更新类型和配置 schema。

### 11.3 完成首次安装

```http
POST /api/v1/admin/apps
Authorization: Bearer ...
```

请求：

```json
{
  "inspectionId": "inspection-id",
  "configuration": {
    "greeting": "你好"
  }
}
```

### 11.4 查询管理列表

```http
GET /api/v1/admin/apps
Authorization: Bearer ...
```

返回 active 和 disabled 安装记录。

### 11.5 完成更新

```http
PUT /api/v1/admin/apps/<appId>/version
Authorization: Bearer ...
```

请求包含 inspection ID 和最终配置。

### 11.6 修改配置或状态

```http
PATCH /api/v1/admin/apps/<appId>
Authorization: Bearer ...
```

只允许修改：

- `configuration`；
- `status`：`active` 或 `disabled`。

### 11.7 卸载

```http
DELETE /api/v1/admin/apps/<appId>
Authorization: Bearer ...
```

删除操作需要 UI 二次确认。API 本身以有效 Bearer token 作为授权依据。

## 12. 数据模型

`installed-apps.json`：

```json
{
  "schemaVersion": 1,
  "apps": [
    {
      "appId": "io.github.example.hello",
      "repository": "https://github.com/example/hello",
      "requestedRef": "v1.0.0",
      "commitSha": "0123456789abcdef",
      "version": "1.0.0",
      "protocol": "biunivers.static-app/1",
      "manifest": {},
      "configuration": {
        "greeting": "你好"
      },
      "status": "active",
      "installedAt": "2026-07-28T20:00:00.000Z",
      "updatedAt": "2026-07-28T20:00:00.000Z"
    }
  ]
}
```

V0.2 使用 JSON 状态文件而不是数据库：

- 状态规模小；
- 单进程串行修改；
- 部署和备份简单；
- 不需要查询或关系能力。

写入采用“同目录临时文件 → flush → rename”。服务启动时校验整个状态文件；损坏时不覆盖原文件，并只提供内建/传统应用。

## 13. 文件布局和静态提供

```text
/data/
├── state/installed-apps.json
├── apps/<appId>/<commitSha>/...
├── staging/<inspectionId>/...
└── trash/<operationId>/...
```

App Origin 路由：

```text
https://app-<hash>.<app-base>/apps/<commitSha>/index.html
https://app-<hash>.<app-base>/apps/<commitSha>/assets/...
https://app-<hash>.<app-base>/apps/<commitSha>/.biunivers/config.json
```

配置保存在原子的 `installed-apps.json` 记录中，配置路由根据当前安装记录动态生成 JSON，不允许仓库文件覆盖。这样更新版本、配置和 APP 投影只需要提交一个状态文件，不会产生跨文件切换不一致。

拒绝提供：

- dotfile；
- `.git`；
- `biunivers.app.json`；
- `BIUNIVERS_APP_PROTOCOL_*.md`；
- 数据目录中未登记版本；
- 目录列表；
- 越界路径。

HTML 和配置不使用 immutable cache；commit SHA 路径下的普通资源可以使用长期缓存。

## 14. 原子性和失败恢复

### 首次安装

```text
inspection staging
→ 校验配置
→ 移动到正式 commit 目录
→ 原子写安装记录
→ APP 对外可见
```

APP 记录是可见性的最终开关。记录写入前的失败不会产生桌面入口。

### 更新

```text
安装新 commit 目录
→ 原子切换安装记录及其配置
→ 新窗口使用新 URL
→ 旧版本进入可清理状态
```

失败不修改 current commit。

### 卸载

```text
从安装记录移除
→ APP 立即不可见
→ 文件移入 trash
→ 异步或启动时清理
```

服务启动时：

- 清理过期 staging；
- 重试 trash 清理；
- 检查 active 记录的入口存在；
- 忽略并报告没有状态引用的孤立目录，不立即永久删除。

## 15. 应用注册合并

桌面 APP 来源：

```text
编译期 internal
  + 传统 apps.json 中的 iframe/external
  + 管理服务返回的 installed iframe
```

规则：

1. internal 只来自编译期静态映射；
2. 传统 `apps.json` 不再接受 `kind: internal`；
3. installed 投影固定为 `kind: iframe`；
4. 所有来源之间 app ID 必须唯一；
5. 冲突条目被拒绝并显示警告，不覆盖已有来源；
6. 管理服务不可用时不影响前两类来源。

需要把当前按 `internalComponent` 字符串分发的方式收敛为编译期 app ID → React 组件映射。

## 16. 前端设计

### 16.1 数据层

新增：

```text
src/api/appManagementClient.ts
src/apps/managedApps.ts
src/apps/refreshAppRegistry.ts
```

桌面 bootstrap 并行读取：

- 传统 `/config/apps.json`；
- `/api/v1/apps`。

然后通过统一 registry 合并。API 失败只产生可见警告。

安装、更新、停用或卸载成功后重新读取动态 APP 表，并协调：

- 新应用进入桌面；
- disabled/uninstalled 应用关闭窗口并移除本地运行状态；
- 更新应用的现有窗口保留到关闭，新窗口使用新 URL；
- 已卸载 ID 从 pinned 和 persisted windows 中清理。

### 16.2 设置应用

设置增加“应用管理”区域：

```text
未解锁
└── 输入管理员 token

已解锁
├── 安装应用
│   ├── GitHub URL
│   ├── ref
│   ├── 检查结果
│   ├── 动态配置表单
│   └── 确认安装
└── 已安装应用
    ├── 配置
    ├── 检查更新
    ├── 停用/启用
    └── 卸载
```

管理员 token 只保存在组件所属的内存状态。关闭设置或刷新页面后重新输入。

V0.2 不建设复杂路由或独立管理后台。

## 17. 依赖选择

建议新增运行依赖：

- `express`：两个小型 HTTP server 和 JSON API；
- `ajv`：Manifest Schema 校验；
- `tar`：安全解包 GitHub archive；
- `mime-types`：静态文件 MIME。

服务端代码继续使用 TypeScript，与前端共用工具链。生产构建输出：

```text
dist/client/
dist/server/
```

测试继续使用 Vitest，服务端 HTTP 集成测试可以直接监听随机本地端口。

具体依赖版本在实施时以当前兼容稳定版锁定，不在设计文档中写死。

## 18. Docker

V0.2 镜像：

1. Node build stage 安装依赖；
2. 构建前端和服务端；
3. Node runtime stage 只复制生产依赖和 dist；
4. 以非 root 用户运行；
5. 暴露 desktop 和 app 两个端口；
6. `/data` 声明为持久化卷；
7. 健康检查访问 Desktop Origin `/health`。

Compose 示例至少包含：

```yaml
ports:
  - "8080:8080"
  - "8081:8081"
volumes:
  - biunivers-data:/data
environment:
  BIUNIVERS_ADMIN_TOKEN: "replace-me"
  BIUNIVERS_DESKTOP_ORIGIN: "http://localhost:8080"
  BIUNIVERS_APP_ORIGIN: "http://localhost:8081"
```

示例值只能用于本地；服务端必须拒绝生产式启动仍使用 `replace-me`。

## 20. 协议反馈

V0.2 是 Static App Protocol v1 和 Manifest v1 的参考实现。

实施期间：

- 发现协议无法实现或开发体验明显不合理时，先修改草案和开发包；
- 不允许只在代码中增加隐藏规则；
- 每次协议字段调整同步 Schema、模板和测试；
- 端到端验收通过后再决定把协议状态改为正式并固定最终摘要。
