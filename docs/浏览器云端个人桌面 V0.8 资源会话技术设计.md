# 浏览器云端个人桌面 V0.8 资源会话技术设计

状态：技术设计草案，待施工前评审

日期：2026-07-29

对应协议：

- [Resource Session Protocol v1 设计](<Biunivers Resource Session Protocol v1 设计.md>)
- [Resource Session Protocol v1 规范评审](<Biunivers Resource Session Protocol v1 规范评审.md>)

前置版本：`v0.7.0`

## 1. 目标与约束

V0.8 实现第三方应用的可续租资源会话和通用单区间 Range，同时保证现有 Host API v1
Notepad 无修改继续工作。

不修改：

- Static App Protocol v1 原文和 Manifest schema；
- Open Resource Protocol v1 原文；
- Host API v1 原文；
- PVLogS3Lite CBOR、FID、Chunk 或 RefStore 格式；
- S3 权限和 GET/条件 PUT 模型。

不实现目录会话、多文件、原生 video URL、区间写入或持久租约。

## 2. 总体结构

```text
iframe App
  │ postMessage 控制面
  ▼
IframeApp Resource Session Dispatcher
  │ Desktop Origin + app runtime token
  ▼
ResourceSessionService ───── AppStore/Handler/OpenResource
  │
  ├─ ResourceSessionRegistry（内存租约）
  ├─ ResourceContentService（完整/Range GET、完整 PUT）
  ├─ FileContentStore（Chunk/Manifest）
  └─ FileSystemTransactions（CAS 发布）
                         │
                         ▼
                 RefStore + Repository
```

Host API v1 继续走现有：

```text
FileCapabilityRegistry → FileTransferService
```

两条路径只共享 File Service Core，不在 V0.8 强制统一注册表。

## 3. 应用运行身份

继续使用 `/api/v1/host/instances` 签发的 instance token 作为 app runtime 凭据。虽然现有记录
包含 `windowInstanceId`，Resource Session 只使用它解析出的 `appId`，不把资源租约绑定到
窗口显示状态。

资源会话记录归属于 `appId`，不是 instance token。任一合法 runtime token 只有同时满足以下
条件才能使用会话：

- token 当前有效；
- token 解析出的 app ID 与会话相同；
- 请求 Origin 是该 app ID 的专属 App Origin；
- AppStore 中应用仍为 `active`。

iframe 卸载会关闭 runtime token，因此不能继续访问；资源会话本身等待租约过期，不需要处理
窗口关闭事件。页面刷新会丢失内存中的 session ID，应用应重新领取对象。

## 4. ResourceSessionRegistry

新增 `server/resources/resourceSessionRegistry.ts`。

### 4.1 内部记录

```ts
interface ResourceSessionRecord {
  sessionId: string;
  appId: string;
  access: "read" | "edit";
  entryIdHex?: string;
  pendingParentEntryIdHex?: string;
  pendingName?: string;
  content?: FileContentRef;
  expectedContentFidHex?: string;
  publicContentVersion: string;
  issuedAtRevision: number;
  createdAtMs: number;
  lastRenewedAtMs: number;
  expiresAtMs: number;
  revoked: boolean;
  activeUses: number;
}
```

`FileContentRef` 和内部 FID 不进入公开响应。公开 `contentVersion` 使用独立不透明随机值；
每次成功保存后更新。

### 4.2 核心方法

```text
issueFile(appId, entry, revision, access)
issuePendingFile(appId, parent, name, revision)
authorize(appId, sessionId, requiredAccess)
renew(appId, sessionIds)
beginUse(appId, sessionId, operation)
finishUse(use, success)
advanceAfterSave(sessionId, entry, revision)
release(appId, sessionIds)
revokeApp(appId)
prune()
```

默认参数：

- lease TTL：300 秒；
- 客户端建议续租间隔：60 秒；
- token：32 随机字节 base64url；
- 内存会话上限：作为部署保护，默认值在实现阶段根据现有 4096 handle 上限确定。

使用惰性过期：每次签发、续租、访问和管理操作调用 `prune()`，不为每个会话建立计时器。

`beginUse` 在请求开始时检查租约并增加 `activeUses`。合法流式请求即使跨过 `expiresAt` 也能
完成；`finishUse` 成功时在应用仍启用的前提下刷新租约。服务端 HTTP 超时限制停滞连接。

应用撤销时记录立即不可用于新请求。活动读取在 Chunk 边界检查撤销信号并中止；活动写入
即使已经产生不可达 Chunk，也不能发布新 Ref。

## 5. 控制面协议

新增 `src/resourceSession/protocol.ts` 和 dispatcher。继续使用 iframe 与父页面之间经过
Origin/source/requestId 校验的 `postMessage`。

最小方法：

| 方法 | 用途 |
|---|---|
| `resource.getCapabilities` | 返回协议版本、续租建议和 Range 支持 |
| `resource.open` | 显示宿主选择器并创建已有文件会话 |
| `resource.saveAs` | 显示宿主保存对话框并创建待保存会话 |
| `resource.claimLaunch` | 领取 Open Resource 待打开对象 |
| `resource.getMetadata` | 读取公开元数据与租约 |
| `resource.renew` | 批量续租 |
| `resource.release` | 批量、幂等释放 |

`resource.open` 的候选类型和最大 access 来自当前应用已注册 Handler，不接受应用临时声明任意
扩展名。`edit` 只有在 Handler 和用户打开动作均允许时签发。

公开会话描述：

```json
{
  "sessionId": "opaque",
  "access": "read",
  "expiresAt": "2026-07-29T18:05:00.000Z",
  "metadata": {
    "name": "movie.mkv",
    "size": 4294967296,
    "mtimeMs": 1785348000000,
    "mediaType": "video/x-matroska",
    "contentVersion": "opaque"
  },
  "content": {
    "url": "https://desktop.example/api/v1/resource-content",
    "sessionHeader": "Biunivers-Resource-Session",
    "authorization": "Biunivers-Instance",
    "instanceToken": "opaque"
  }
}
```

`mediaType` 第一版由扩展名映射产生，是响应提示，不写入文件身份或 PVLog。

## 6. Desktop Origin 控制 API

父页面 dispatcher 调用以下 same-origin API：

```text
POST /api/v1/host/resource-sessions
POST /api/v1/host/resource-sessions/save-targets
POST /api/v1/host/resource-sessions/launches/:launchId/claim
POST /api/v1/host/resource-sessions/renew
POST /api/v1/host/resource-sessions/release
POST /api/v1/host/resource-sessions/metadata
```

所有接口要求：

- `requireDesktopOrigin`；
- `Biunivers-Instance`；
- 严格 JSON 字段白名单和 64 KiB 总请求上限；
- app runtime 身份与会话 app ID 一致；
- 当前应用状态检查。

Entry ID 和 parent Entry ID 只在可信父页面与宿主服务之间传递，不返回 iframe。

## 7. 数据 API 与 CORS

新增固定数据端点：

```text
GET /api/v1/resource-content
PUT /api/v1/resource-content
```

请求头：

```http
Authorization: Biunivers-Instance <token>
Biunivers-Resource-Session: <session-id>
Range: bytes=<start>-<end>
```

session ID 不进入 URL。router 先用 instance token 取得 app ID，再计算精确 app-specific Origin，
最后授权资源会话。

预检允许：

```text
GET, PUT
Authorization, Biunivers-Resource-Session, Range, Content-Type
```

响应暴露：

```text
Accept-Ranges, Content-Range, Content-Length
```

继续设置精确 `Access-Control-Allow-Origin`、`Vary: Origin`、
`Cross-Origin-Resource-Policy: cross-origin` 和 `Cache-Control: no-store`。

## 8. Range 解析

新增纯函数模块 `server/resources/byteRange.ts`：

```ts
parseSingleByteRange(header: string | undefined, size: number)
```

支持：

- `bytes=0-99`
- `bytes=100-`
- `bytes=-100`
- 无 Range

拒绝：

- 多区间；
- 非 `bytes` 单位；
- 非整数、负值、溢出和反向范围；
- 空文件上的任意 Range；
- 起点不小于文件大小。

合法范围统一归一化为闭区间 `{ start, end, length }`。无 Range 返回完整范围和 `200`；合法
Range 返回 `206`；不满足范围返回 `416` 和 `Content-Range: bytes */<size>`。

## 9. Chunk 区间读取

在 `FileContentStore` 增加：

```ts
readRange(
  content: FileContentRef,
  start: number,
  endInclusive: number,
): AsyncGenerator<Uint8Array>
```

直接 Chunk：

1. GET 并校验完整 Chunk FID；
2. 校验长度；
3. 返回 `subarray(start, end + 1)`。

Manifest：

1. GET 并校验 Manifest；
2. 校验总大小、FID 数组和长度数组；
3. 计算每个 Chunk 在文件中的累计起止位置；
4. 只 GET 与目标区间相交的 Chunk；
5. 每个 Chunk 仍完整校验 FID 和长度；
6. 裁剪首尾，按原顺序流式返回；
7. 返回字节总数必须等于 Range length。

S3 接口不需要 Range GET。Biunivers 最多额外读取首尾两个完整 64 MiB Chunk，保持现有
Repository 完整对象校验和 GET/条件 PUT 权限模型。若以后实测需要 S3 Range，再独立评审，
不能牺牲完整 Chunk 校验。

## 10. 完整读取与保存

### 10.1 读取

`ResourceContentService.read()` 使用会话内部固定 `FileContentRef`，不重新从当前 Entry 获取
内容，因此外部保存、移动、改名或删除不改变响应字节。

### 10.2 保存

PUT 只允许 `edit` 会话：

1. `beginUse(..., "write")`；
2. 以现有大小上限流式调用 `FileContentStore.putStream`；
3. 对 `entryIdHex + expectedContentFidHex` 调用 `setFileContent`；
4. 成功后从当前索引取得新 Entry；
5. 原子更新会话的 content、expected FID、revision 和公开 version；
6. 返回新元数据并隐式续租。

外部保存、删除或 Ref CAS 竞争统一返回 `FILE_VERSION_CONFLICT`。已上传但未发布的不可变对象
成为可达性扫描候选，不改变当前文件。

待保存会话首次 PUT 调用现有 `createFile`。失败、过期或撤销时不发布 Entry；成功后将会话
转换为普通 edit 会话。

## 11. Open Resource 集成

现有 `OpenResourceLaunchRegistry` 继续保存尚未领取的路由事实，不在创建时签发 handle 或
session。

领取路径并行：

- 旧应用发送 `biunivers.open-resource/1 launch.getContext`，现有
  `OpenResourceLaunchService.claim()` 返回 Host API v1 handle；
- 新应用发送 `biunivers.resource-session/1 resource.claimLaunch`，新增
  `ResourceSessionLaunchService.claim()` 消费同类 Launch 并返回资源会话。

同一个 Launch 只能被一个路径成功消费。两条路径都重新校验应用 active、Handler、action、
扩展名和 expected revision。

不要求在 Manifest 增加协议支持字段。应用实际发送的协议请求就是能力选择；父页面可以同时
发送通用“资源待领取”通知，应用按自身实现领取。

## 12. 应用生命周期撤销

`AppService` 增加成功提交后的生命周期回调：

```ts
onAppInvalidated(appId, reason)
```

在以下操作成功写入 AppStore 后调用：

- active → disabled；
- update commit；
- uninstall。

回调执行：

- `ResourceSessionRegistry.revokeApp(appId)`；
- `OpenResourceLaunchRegistry.cancelTarget(appId)`；
- 现有 V1 instance/handle 兼容行为保持不变。

每次 renew 和数据访问再读取/核对 active 状态，防止回调与并发请求之间出现授权窗口。重新
启用不会恢复旧会话。

## 13. 前端与开发者 API

新增小型客户端模块，负责：

- requestId 和 postMessage 校验；
- session 描述类型；
- 60 秒批量续租调度；
- 页面卸载前 best-effort `resource.release`；
- 带 instance token、session header 和 Range 的 fetch；
- `RESOURCE_SESSION_EXPIRED`、`FILE_VERSION_CONFLICT` 和 V1 fallback。

续租器只为调用方显式登记的 session 工作。应用释放最后一个 session 后停止定时器。
开发者模板提供完整读取、Range 读取和释放示例，不内置播放器或容器解析。

## 14. 错误映射

控制面使用 JSON 错误；数据面使用 HTTP 状态并保留不泄露细节的错误体：

| 条件 | 状态/代码 |
|---|---|
| 无效或不属于应用的 session | `404 RESOURCE_SESSION_NOT_FOUND` |
| 已过期 | `410 RESOURCE_SESSION_EXPIRED` |
| 应用已撤销 | `403 RESOURCE_SESSION_REVOKED` |
| read 会话 PUT | `403 RESOURCE_ACCESS_DENIED` |
| Range 不满足 | `416` |
| 文件版本冲突 | `409 FILE_VERSION_CONFLICT` |
| File Service 不可用 | `503 HOST_API_UNSUPPORTED` |

随机 ID、其他应用 ID 和已释放 ID 对调用方统一表现为 not found。

## 15. 测试策略

### 15.1 单元

- 60/300 边界、批量续租、隐式续租、过期不复活；
- app ID 隔离、read/edit、撤销、幂等释放；
- Range 四种合法形式和所有拒绝形式；
- Chunk/Manifest 首、中、尾、跨 Chunk 和 64 MiB 边界；
- 空文件、64 MiB、64 MiB + 1 和大于两个 Chunk；
- 保存推进版本、外部保存/删除冲突和待保存失败。

### 15.2 HTTP/安全

- 精确 Origin、错误 Origin、其他 app 子域；
- 缺失/错误 runtime token 和 session header；
- CORS preflight 与 expose headers；
- `200/206/416` 的精确响应头和字节数；
- session ID 不出现在 URL 和日志；
- 停用/更新/卸载后新请求失败且 PUT 不发布 Ref。

### 15.3 兼容

- 现有 Host API v1 全套测试零修改通过；
- 现有 Notepad 打开、保存、另存为和冲突人工回归；
- Open Resource v1 仍返回旧 handle；
- 同一 Launch 不能被 V1 与 Resource Session 重复领取。

### 15.4 真实验收

- 真实 R2 上 Range 读取 64 MiB + 1 文件并逐字节比对；
- WASM/JavaScript 测试应用读取 MKV 头部、尾部和随机区间；
- 连续拖动模拟产生多次 Range，内存不累计完整文件；
- 暂停超过 60 秒仍续租，超过 300 秒不续租后明确过期；
- 应用停用后会话撤销；
- 容器重启后旧会话失效，文件内容仍可重新打开；
- Host API v1 Notepad 同环境继续工作。

## 16. 发布与回滚

Resource Session 是纯新增的内存状态和 HTTP/消息接口，不迁移 `/data`、RefStore 或 S3。
回滚到 V0.7 时新会话全部自然失效，旧应用和文件内容不受影响。

只有完成自动化、真实 Range、应用撤销和 Notepad 兼容验收后，才在开发者包中把
`biunivers.resource-session/1` 标为推荐协议。
