# 浏览器云端个人桌面 V0.1 技术设计

## 1. 设计结论

V0.1 按需求文档可以实现，不需要增加服务端、微前端框架或操作系统式抽象。

采用以下最小方案：

- Vite + React + TypeScript；
- Zustand 保存产品状态；
- 直接使用 WinBox.js，不使用 React-WinBox；
- 一个模块级 `Map` 保存 WinBox 和 React Root 等运行时对象；
- 手写 `apps.json` 校验，不引入 schema 库；
- localStorage 保存版本化的可序列化状态；
- 普通 CSS 完成基础可用界面；
- Nginx 提供静态文件、SPA fallback 和健康检查。

WinBox 继续作为窗口机械状态源，Zustand 作为桌面产品状态源。WinBox 自己管理窗口层级，应用只同步“当前活动窗口”，不保存或恢复 z-index。

## 2. 可行性与范围审查

### 2.1 可行性

需求中的桌面、任务栏、应用菜单、单实例窗口、三种应用类型、状态持久化和 Docker 静态部署均可在纯前端内完成。

iframe 能否显示最终由目标服务的 `Content-Security-Policy: frame-ancestors`、`X-Frame-Options`、Cookie 和认证策略决定。桌面不能可靠判断所有 iframe 拒绝加载情形，因此“在新标签页打开”是必要的降级入口，而不是错误检测机制。

### 2.2 文档内需要澄清并在实现中统一的点

1. **壁纸运行时配置缺少字段定义**

   需求提到“配置文件指定壁纸 URL”，但 `/config/apps.json` 是数组，`AppDefinition` 中也没有壁纸字段。V0.1 不扩展配置协议：默认壁纸作为前端常量，设置应用可覆盖。若以后确需部署时配置默认壁纸，再单独增加 `/config/desktop.json`，本版不做。

2. **配置错误状态不足以表达部分成功**

   `configStatus` 只有 `loading | ready | error`，但要求“有效应用继续加载、无效应用跳过”。设计为：请求失败或顶层 JSON 不是数组时为 `error`；成功取得数组但包含无效条目时仍为 `ready`，同时保存 `configWarnings: string[]`。这是状态字段的小幅补全，不增加错误框架。

3. **固定应用默认值需要区分首次启动与用户空列表**

   空的 `pinnedAppIds` 既可能是首次启动，也可能表示用户已取消全部固定。持久化状态增加 `preferencesInitialized: true`，或以完整持久化对象是否存在判断。首次加载才采用配置的 `pinned`；之后用户的空列表也必须被尊重。

4. **“恢复默认桌面状态”语义重叠**

   设置页中的“恢复默认桌面状态”定义为：恢复默认壁纸和配置中的默认固定应用，关闭所有窗口并清除窗口记录。“清除所有本地桌面数据”执行相同本地清理后刷新页面。V0.1 不再拆分更多重置层级。

5. **关闭窗口后的保存描述容易误读**

   关闭时可保留最后边界用于同一次或以后重新打开，但必须从 `runningAppIds` 删除。会话恢复只看 `runningAppIds`，因此明确关闭的应用不会在刷新后恢复。

6. **状态模型中的 `displayState` 不能同时表达“最大化后隐藏”**

   用户可能先最大化再从任务栏隐藏，恢复显示时应仍为最大化。单一的 `normal | maximized | hidden` 会丢失隐藏前状态。实现采用：

   ```ts
   interface WindowState {
     appId: string;
     hidden: boolean;
     maximized: boolean;
     active: boolean;
     x: number;
     y: number;
     width: number;
     height: number;
     openedAt: number;
   }
   ```

   持久化窗口记录同样分别保存 `hidden` 和 `maximized`。这是本设计中唯一必要的状态模型修正。

### 2.3 建议从 V0.1 删除或降级

- 不引入 Lucide React；开始按钮、通用图标和状态标记用 CSS 或仓库内 SVG。
- Playwright 保留为阶段六的建议项；若 WinBox 在无头浏览器中稳定，则纳入冒烟测试，否则以构建检查和人工验收清单为 V0.1 阻断条件。
- 任务栏右键菜单保留，因为需求已明确；只做固定/取消固定和关闭两个命令，不做通用菜单系统。
- 不实现 iframe 加载失败自动提示，只常驻“在新标签页打开”操作。
- 不做窗口层级持久化，也不恢复刷新前所有窗口的精确堆叠顺序；只最后聚焦保存的活动窗口。

## 3. 核心运行结构

```text
bootstrap
  ├─ load persisted state
  ├─ fetch and validate apps.json
  ├─ reconcile removed/invalid app IDs
  ├─ render Desktop
  └─ restore running windows once

React UI ──commands──> desktopStore
   │                       │
   │                       └─serializable product state
   │
   └─window commands──> windowController
                          ├─WinBox instance
                          ├─React Root
                          └─runtime Map (memory only)
```

### 3.1 状态边界

Zustand 保存：

- 应用注册表及配置加载状态；
- 运行应用 ID；
- 活动应用 ID；
- 每个窗口的边界、隐藏和最大化状态；
- 固定应用、壁纸、菜单和桌面选择状态。

`windowRuntimeMap` 保存：

```ts
interface WindowRuntime {
  winbox: WinBox;
  reactRoot: Root;
  container: HTMLDivElement;
  closing: boolean;
}
```

Map 的 key 为 `appId`。WinBox、DOM、React Root、定时器和函数不得进入 Zustand 持久化数据。

### 3.2 命令所有权

- React 组件只调用 store action 或窗口控制器，不直接创建 WinBox。
- `openApp` 先检查应用类型及 runtime Map，再决定创建、显示或聚焦。
- WinBox 回调将机械状态回写 store。
- `closeApp` 调用统一的 `requestClose(appId)`；最终清理由 WinBox `onclose` 进入唯一的 `finalizeClose(appId)`。
- localStorage 写入集中在持久化模块，窗口移动和缩放采用 300ms 防抖。

## 4. WinBox 与 React 生命周期设计

### 4.1 为什么不用 React-WinBox

直接使用 WinBox 更简单：

- 需求已经需要显式的 runtime Map 和单实例控制；
- React 内容需要独立 Root，原生 `mount` 正好满足；
- 包装组件会增加 React 声明式状态与 WinBox 命令式状态之间的双向同步；
- V0.1 不需要包装库提供的受控 props 抽象。

固定 WinBox 版本，升级时重新执行 API 冒烟验证。

### 4.2 创建顺序

```ts
function createWindow(app: AppDefinition, saved?: PersistedWindow) {
  if (windowRuntimeMap.has(app.id)) {
    return focusOrShowExisting(app.id);
  }

  const container = document.createElement("div");
  container.className = "app-window-root";
  const reactRoot = createRoot(container);

  const winbox = new WinBox({
    id: `app-${app.id}`,
    title: app.name,
    icon: app.icon,
    root: windowLayer,
    mount: container,
    class: ["no-min", "no-full"],
    bottom: TASKBAR_HEIGHT,
    // bounds, minimums and callbacks
  });

  windowRuntimeMap.set(app.id, {
    winbox,
    reactRoot,
    container,
    closing: false,
  });

  reactRoot.render(<WindowContent app={app} />);
}
```

实际实现必须在 WinBox 创建前预留“正在创建”的集合，或先建立占位 runtime，避免同步重入：

```ts
const creatingAppIds = new Set<string>();
```

`openApp` 在 `Map` 或 `creatingAppIds` 已包含 appId 时绝不新建窗口，并用 `try/finally` 清除创建标记。

### 4.3 关闭与只卸载一次

WinBox 的 `onclose` 返回真值会阻止关闭。因此回调中执行清理后必须返回 `false` 或不返回。

关闭流程：

1. 检查 runtime 是否存在且 `closing === false`；
2. 设置 `closing = true`；
3. 立即从 runtime Map 删除，阻止重入创建/关闭命中旧实例；
4. 取消该窗口相关的防抖任务；
5. 同步调用 `reactRoot.unmount()` 一次；
6. 从 store 的运行列表删除，保留最后边界但不再标记运行；
7. 让 `onclose` 返回 `undefined`，由 WinBox 继续卸载容器和删除 DOM。

不要在 `requestClose` 和 `onclose` 两处分别调用 `reactRoot.unmount()`。程序关闭也调用 `winbox.close()`，统一进入 `onclose`。若将来需要关闭确认，可在进入 `finalizeClose` 前返回 `true`，本版不实现。

### 4.4 React Strict Mode

窗口创建不是 React render 的副作用，也不放在普通组件挂载 effect 中。用户命令进入模块级控制器；会话恢复只由 bootstrap 协调器执行一次。即使开发模式下 Strict Mode 重跑组件 effect，runtime Map 和 `creatingAppIds` 仍提供幂等保护。

根应用可以保留 Strict Mode。若 WinBox 本身在开发环境出现不可消除的第三方副作用，再仅对窗口创建路径修正，不先删除 Strict Mode。

### 4.5 hide/show 代替原生最小化

方案可行。WinBox 提供 `hide()`、`show()`、`hidden`、`onhide` 和 `onshow`，控制类 `no-min` 可隐藏原生最小化按钮。

任务栏逻辑：

```ts
if (runtime.winbox.hidden) {
  runtime.winbox.show()?.focus();
} else if (runtime.winbox.focused) {
  runtime.winbox.hide();
} else {
  runtime.winbox.focus();
}
```

由于 WinBox 某些状态无变化时方法可能不返回实例，实际代码不要依赖可选链式返回：

```ts
runtime.winbox.show();
runtime.winbox.focus();
```

隐藏活动窗口后应显式清空活动应用，或让窗口失焦并聚焦下一个可见窗口。阶段二用浏览器验证 WinBox `hide()` 是否自动触发 blur；若没有，控制器执行 `blur()` 后按 runtime Map 中最近聚焦记录选择下一个窗口。本版不引入窗口栈抽象。

### 4.6 最大化、边界与视口变化

- `bottom` 使用与 CSS `--taskbar-height` 同源的 TypeScript 常量；CSS 变量由该常量在根节点设置，避免两处手写数值。
- 保存的普通边界先 clamp 到可用区域，再创建窗口。
- 最大化状态先用普通边界创建，再调用 `maximize(true)`，确保恢复时有合理尺寸。
- WinBox 当前源码在浏览器 resize 时不会主动修正已有窗口，因此桌面注册一个防抖的 `window.resize` 监听器，逐个：
  - 更新可用最大宽高；
  - 缩小超过可用区的普通窗口；
  - clamp 坐标，至少完整保留标题栏且不覆盖任务栏；
  - 对最大化窗口执行一次 restore/maximize 或经验证可用的 resize/move 更新。
- WinBox `root` 决定 DOM 挂载位置，但当前实现的边界尺寸取自文档视口。V0.1 的窗口层本来就是全屏，所以没有影响；不要把窗口层改为非全屏局部容器。

### 4.7 层级与 iframe 聚焦

WinBox 在 `focus()` 时维护自己的内部栈并提高 z-index，应用不重复同步 index。`onfocus/onblur` 只同步 `activeAppId`。

WinBox 在窗口 body 上使用捕获阶段的 `mousedown` 监听器，因此用户点击 iframe 元素前，父文档通常能先聚焦窗口；进入 iframe 文档后的事件不会冒泡回父文档，但点击入口已发生在 iframe 元素上。阶段二必须验证：

- 点击 iframe 内容是否触发窗口 focus；
- 在两个 iframe 窗口间切换时任务栏活动标记是否正确；
- iframe 自身获得键盘焦点后，点击桌面是否正确 blur。

若浏览器验证失败，只在 iframe 外层加透明的首次点击聚焦层，并在聚焦后立即移除；不引入跨窗口消息总线。

## 5. 应用注册表设计

### 5.1 加载流程

1. 启动时加载内建应用定义；
2. `fetch("/config/apps.json", { cache: "no-store" })`；
3. 验证顶层数组；
4. 逐项校验并收集错误；
5. 按 ID 去重，重复项全部跳过或保留首项并记录明确警告；设计采用“保留首项、跳过后项”；
6. 外部配置按 ID 覆盖内建应用只允许预先声明的内建 ID，且 `kind/internalComponent` 不允许被改为未知组件；
7. 合并有效应用并更新 store；
8. 根据最终 ID 集合清理持久化状态。

### 5.2 手写校验

配置只有约 13 个字段和三个简单分支，手写类型守卫比引入 Zod 等库更合适。校验器返回：

```ts
type ValidationResult =
  | { ok: true; app: AppDefinition }
  | { ok: false; index: number; issues: string[] };
```

共同规则：

- 对象且非数组；
- `id` 匹配 `/^[a-z0-9.-]+$/`；
- `name`、`icon` 为非空字符串；
- `kind` 是允许值；
- 默认和最小尺寸为有限正数，最小尺寸不得大于默认尺寸；
- `desktop`、`pinned` 为 boolean；
- internal 必须是允许列表中的 `internalComponent`；
- iframe/external 必须有可解析 URL；允许 `/` 开头的同源相对 URL以及 `http:`/`https:`；
- iframe 必须显式 `trusted: true`，否则跳过；
- 未知字段忽略，未知类型跳过。

请求失败时保留内建设置和关于应用，并在桌面显示非阻断错误横幅；设置页展示详细错误。

### 5.3 external 应用

external 不创建 runtime 或 running 状态。通过用户点击直接调用：

```ts
window.open(url, "_blank", "noopener,noreferrer");
```

浏览器可能阻止非用户手势触发的新标签，因此 external 不参与会话恢复。

## 6. 持久化与恢复设计

### 6.1 存储

- key：`biunivers.desktop.v1`；
- schemaVersion：`1`；
- 使用自有 parse/validate 函数，不直接信任 JSON；
- 写入采用 300ms 防抖，关闭和 `pagehide` 时同步 flush；
- 不保存菜单、选中图标、错误信息或 runtime 对象。

### 6.2 恢复算法

```text
读取并校验持久化数据
        │
        ├─损坏/未知版本──> 删除该 key，使用默认值
        │
加载并校验最终应用注册表
        │
清理不存在、无效及 external 的 running/window/pinned ID
        │
先提交协调后的 Zustand 状态
        │
串行恢复 runningAppIds（每个 ID 只处理一次）
        │
恢复 hidden/maximized 状态
        │
最后显示并聚焦 activeAppId（若其存在且未隐藏）
```

恢复函数带模块级状态：

```ts
let restoreStarted = false;
```

同时对 `runningAppIds` 去重，并复用 `openApp` 的 runtime Map/creating set 幂等保护。恢复期间 WinBox 回调可以更新 store，但持久化写入暂停；全部完成后一次性恢复写入，避免半恢复状态覆盖完整快照。

如果保存的 active 应用已删除、为 external 或处于隐藏状态，则选取最后打开的可见窗口；没有则设为 null。

## 7. 交互设计

### 7.1 桌面

- 全屏、无页面滚动；
- 左上角固定网格，按列向下排列；
- 单击选中、双击打开、Enter 打开；
- 点击空白取消选中并关闭 App 菜单；
- 小于 1024px 显示非阻断桌面浏览器提示。

### 7.2 App 菜单

- 任务栏开始按钮切换；
- 打开后搜索框 focus；
- 名称和 ID 做 `toLocaleLowerCase()` 包含匹配；
- 固定应用在前，其余用当前浏览器 locale 按名称排序；
- 点击外部或 Escape 关闭；
- 点击应用先关闭菜单再启动。

### 7.3 任务栏

- 固定应用与运行但未固定应用合并去重；
- external 固定项永远不显示“运行”；
- 状态用背景和底部圆点/线条区分，不做动画依赖；
- 右键菜单定位到视口内，点击外部/Escape 关闭；
- 每分钟按下一个整分钟边界更新时间，卸载时清除 timer。

### 7.4 设置

只提供需求中的外观、固定应用、桌面信息和系统操作。壁纸 URL 为空或无效时不保存；图片网络加载失败时保留设置值但背景回退默认壁纸，并显示提示。

“清除所有本地桌面数据”属于破坏性操作，需要一次确认。确认后依次关闭窗口、删除指定 localStorage key、重置 store 并刷新；不使用 `localStorage.clear()`，避免删除同源其他应用数据。

## 8. 错误隔离

- 根桌面不依赖远程配置成功才能渲染；
- 每个 internal 应用内容外包独立 Error Boundary；
- iframe 只提供新标签入口，不宣称可靠探测加载失败；
- 图标组件在 `onError` 后切换为本地默认 SVG，并避免重复报错；
- 所有持久化读取做 `try/catch` 和结构校验；
- WinBox 创建失败时卸载已创建的 React Root、清除 creating 标记并回滚运行状态；
- 单个无效应用只生成 warning，不使整个配置失败。

## 11. WinBox API 验证清单

实现阶段二时必须在锁定版本上逐项验证，不能只依赖类型声明：

- `new WinBox({ root, mount, class, bottom, ... })` 的 ESM 导入及 CSS 导入路径；
- `class: ["no-min", "no-full"]` 是否正确隐藏按钮；
- `root` 为全屏 WindowLayer 时 DOM 层级和拖动是否正常；
- `bottom` 是否同时约束拖动、缩放和最大化；
- `hide/show` 是否触发 `onhide/onshow`，隐藏活动窗口是否触发 blur；
- `focus/blur` 和 `focused` 在多窗口及 iframe 点击时是否一致；
- `maximize/restore` 的回调顺序，以及 restore 后边界；
- `onmove/onresize` 在拖动时的调用频率和参数；
- `onclose` 返回真值阻止关闭、非真值继续关闭的行为；
- `close()` 是否先调用 `onclose`、再执行 WinBox 自身 unmount；
- React Root 卸载后 WinBox 的 `unmount()` 是否安全移动空容器；
- 浏览器 resize 后最大化窗口与普通窗口的行为；
- `width/height/x/y/minwidth/minheight/maxwidth/maxheight` 的读写是否与源码版本一致；
- 多窗口 focus 时 WinBox 是否独立维护正确 z-index；
- 连续调用 `hide/show/focus/close` 时无异常。

已从 WinBox 0.2.82 官方源码确认：存在以上构造选项、状态属性和回调；`hide/show` 可用；`onclose` 真值会取消关闭；`onmove/onresize` 会在 `move/resize` 每次执行时调用；全局 resize 处理未自动修正普通窗口。因此这些结论进入设计，但仍需在真实浏览器集成验证。

## 12. 高返工风险

按风险从高到低排列：

1. **WinBox 维护状态与类型质量**

   当前 npm 版本较旧，应锁定精确版本。若关键 API 与打包器不兼容，优先写很薄的本地适配函数，不切换到 React-WinBox。

2. **最大化与隐藏的组合状态**

   已通过拆分 `hidden/maximized` 消除模型缺陷。若沿用三值 `displayState`，阶段五必然返工。

3. **iframe 的可嵌入性和认证**

   这是部署配置问题，前端无法兜底。README 必须说明同源反向代理、CSP、X-Frame-Options 和 Cookie 配置责任。

4. **会话恢复与回调竞争**

   恢复期间暂停持久化、串行创建、最后聚焦，并用 runtime Map + creating set + restore gate 三层幂等，不增加通用任务系统。

5. **配置默认值与用户偏好优先级**

   首次初始化标记必须在阶段三/五统一，否则用户取消全部固定后刷新会重新出现默认固定项。

6. **视口变化**

   WinBox 不负责自动 clamp，必须由项目代码处理，并围绕任务栏高度写边界单测。

7. **关闭生命周期**

   只能有一个 finalize 路径。若 UI、store 和 WinBox 回调各自清理，会产生重复 unmount 和幽灵运行状态。

## 13. 阶段入口与验收原则

在开始阶段一前，只需确认本设计；无需额外 UI 稿。实现过程中遵守：

- 不提前实现后续阶段；
- 不为未来需求创建 manager、event bus 或 DI；
- 新增依赖必须能对应本设计中的明确用途；
- 每阶段保持可运行、可构建；
- WinBox 验证失败时先缩减行为或增加局部适配，不替换整体技术栈；
- 基础可用、状态正确和可部署优先于视觉效果。
