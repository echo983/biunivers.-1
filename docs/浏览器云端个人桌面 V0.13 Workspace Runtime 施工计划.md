# 浏览器云端个人桌面 V0.13 Workspace Runtime 施工计划

状态：施工中

日期：2026-07-30

## 1. 施工原则

- 先使 File Service 内部 Ref-aware，再增加 Workspace；
- public/third-party API 不暴露任意 Ref；
- 先完成不依赖 Runtime 的创建、浏览和删除；
- Runtime、COW 提交、导回分别设验收门；
- 无法证明的 Upper 变化一律拒绝提交并保留现场；
- 每个切片独立提交、全量回归并同步文档。

实现：

- `workspace_records`、`workspace_runs`；

- Run 状态迁移和 `active_write_run_id`；

## 4. 切片 C：选择集派生

状态：已完成（2026-07-30）

实现 `WorkspaceDeriver`：

- 固定 main `sourceHead`；
- 校验同一父目录并递归展开；
- 限制深度、Entry 数和元数据；
- 新虚拟根、lineage 和 Entry ID；
- 复用 Content FID；
- revision 0 Checkpoint/Genesis Head；
- 原子创建 Workspace + `ws-*` Ref。

测试文件、目录、空目录、嵌套、重名、越界、来源竞争和 SQLite 失败。确认未选内容不可见、
Entry ID 全新而 Content FID 复用。

出口：服务层可创建和删除最小 Workspace，不依赖 Docker。

完成说明：

- 新增窄幅 PVLog Core ABI，由 Rust 核心从 packed Entry 投影规范编码带内容的 revision 0
  Checkpoint；TypeScript 不复制 CBOR 格式；
- `WorkspaceDeriver` 固定读取 `main` HEAD，要求非空、唯一且同一直接父目录的选择集，目录递归
  展开；
- 默认限制 100 个直接选择、100,000 个派生 Entry、128 层深度和 32 MiB packed 元数据；
- Workspace 使用新虚拟根、新 lineage 和全新 Entry ID，文件 Content FID 与大小原样复用；
- Checkpoint 与 Genesis Head 先写不可变仓库，再由 RefStore 在单一 SQLite 事务中校验来源 HEAD
  并原子发布 Workspace + `ws-*` Ref；
- 来源竞争会返回 `REF_CONFLICT`，不留下 Workspace/Ref；已写的不可变对象允许成为未来 GC
  候选，不执行危险回滚删除；
- 服务测试覆盖文件与嵌套目录派生、未选择隔离、FID 复用、同父约束、重复选择、Entry/深度/
  元数据边界和发布前来源竞争。

## 7. 切片 F：Compute Runtime Daemon

状态：施工中（Compute Runtime 主链与真实沙箱验收已完成，2026-07-30）

实现本机认证窄 API、固定执行器注册表、Run 目录、PVLogFS/fuse-overlayfs supervisor、
OCI 生命周期、资源限制、orphan 隔离和幂等清理。

安全验收：

- 非 root、无网络/capabilities；
- 无 `/dev/fuse`、S3 secret、RefStore、Docker socket；
- 不能指定镜像、命令、mount、device 或宿主路径；
- 只见 `/workspace`；
- 重启对账不删除未知 Upper；
- Upper 超限稳定返回 ENOSPC。

出口：诊断执行器能修改 Upper，但尚不推进 Ref。

阶段进度：

- `RunDirectoryManager` 已实现固定绝对 Run 根、原子目录布局、`0600 runtime.json`、本地状态
  CAS 和安全检查；
- Runtime 启动对账只接受控制面已知 Run；未知目录和中断 prepare 残留移入
  `.quarantine`，不递归删除；已知 Run manifest 损坏时失败关闭并保留 Upper；
- `ExecutorRegistry` 只接受 digest-pinned、非 root、固定 entrypoint 和固定资源上限定义；
- Docker OCI 计划固定 `network none`、只读 rootfs、`cap-drop ALL`、`no-new-privileges`、
  PID/CPU/内存限制和唯一 `/workspace` 映射；
- 调用方不能提交镜像、命令、环境变量、mount、device、network 或宿主路径。
- `MountSupervisor` 已按固定 Run 布局启动正式 PVLogFS 与 fuse-overlayfs，并在每一步等待
  mount readiness；
- 部分启动失败会逆序回滚；正常清理固定为卸载 merged、停止 overlay、卸载 lower、停止
  PVLogFS，TERM 超时后升级 KILL；
- Supervisor 不删除 Upper；路径、binary 和 capability 均在执行前严格校验。
- Docker OCI Adapter 只执行宿主预构造的固定参数计划，使用无 shell、有限超时与输出上限的
  `execFile`；容器身份与 `docker inspect` 状态均严格解析，调用方没有 Docker 参数透传面；
- `ComputeRuntimeCoordinator` 已闭合 `prepare → start → inspect → stop` 主链，统一编排
  Snapshot provision、PVLogFS/overlay mount 和 OCI 生命周期；启动中途失败会逆序释放资源并
  标记失败，Upper 始终保留；
- Runtime 控制面使用 `0600` Unix Socket、256-bit 随机共享凭据、长度前缀帧和逐操作精确
  schema；当前只开放 prepare/start/inspect/stop，额外的镜像、命令或 mount 字段会被拒绝；
- Socket 启动只清理陈旧 Unix Socket；同名普通文件会失败关闭，不会被覆盖。
- `PvlogSnapshotProvisioner` 已把 Runtime 主链接到正式 PVLog Gateway；发布前必须复核捕获的
  Workspace、HEAD 和 revision 与 Run 锁定值完全一致，发生并发推进时失败关闭，不会静默
  换用新快照；每个 Run 的 capability 固定绑定自己的 Gateway。
- daemon 正式入口已完成 File Service、验证缓存、Snapshot Gateway、Mount Supervisor、
  OCI Adapter、Coordinator 与私有 Socket 的固定依赖装配；
- Runtime 配置只允许 digest-pinned 的内置诊断执行器，并固定非 root UID/GID、入口、
  CPU/内存/PID/输出限制；镜像 tag 和非规范宿主路径会在启动前拒绝；
- 优雅停机会先停止接收控制请求，再清理活跃容器、overlay、PVLogFS 和 Gateway，将本地
  Run 标为 `FAILED/DAEMON_SHUTDOWN`，同时保留 Upper；
- 启动时会根据 RefStore Run 集合隔离未知目录；对上次异常中断的已知活跃 Run，按确定性
  容器名确认并删除容器，再依次卸载 merged/lower，全部成功后标记
  `FAILED/INTERRUPTED_DAEMON_RECOVERY`，Upper 保留；
- 容器查询、删除、卸载或卸载复验任一步不确定，恢复立即失败关闭，daemon 不会提前开放
  控制接口。
- 固定诊断执行器镜像已落盘：以 UID/GID 65532 运行，启动时断言无 capabilities、无网络
  接口（loopback 除外）、无 Docker socket、无 `/dev/fuse`，并仅向 `/workspace` 写入
  机器可读验收结果；Runtime 同时支持 registry digest 与本地 `sha256:<image-id>` 两种
  内容寻址镜像身份，不接受 tag。
- Supervisor 会在 Run 私有 `0700` 父目录内将 Upper 调整为 `0707`，使固定非 root
  容器身份可通过 fuse-overlayfs 写 `/workspace`；挂载后的 merged 不再由宿主 chmod，
  Work 不开放，父路径无法被其他宿主用户穿越，lower 仍保持只读，写入只进入 Upper。
- overlay 视图使用 `squash_to_uid=65532,squash_to_gid=65532`，统一映射为固定执行器身份；
  Workspace 不暴露宿主 UID/GID 语义，避免跨 FUSE 边界的异 UID 写入，同时不需要赋予
  容器 root 身份。
- 2026-07-30 用户在真实 S3/RefStore 数据、正式 PVLogFS、fuse-overlayfs 和 Docker 上
  执行 `scripts/run-compute-runtime-test.sh`：诊断 Run 完成
  `PREPARED → RUNNING → STOPPED`；
- 实测容器 UID/GID 为 65532、network 为 none、有效 capabilities 为零，且不可见 Docker
  socket 与 `/dev/fuse`；容器成功写入 `/workspace`，结果落入 Upper；
- 停止后容器删除、merged/lower 卸载、Gateway/PVLogFS/overlay 清理全部通过，固定输入
  快照与 Upper 均按设计保留。
- Runtime 窄 API 已补齐 `freeze/thaw/destroy`：freeze/thaw 映射为 Docker
  pause/unpause，并以本地 `FROZEN` 状态 CAS；冻结期间容器不能继续写 Upper，但挂载保持；
- `destroy` 要求调用方显式提交 `preserveUpper`，不提供隐式默认值；它先停止容器并清理
  完整挂载栈，保留模式只留下 `upper/runtime.json` 并标记 `DESTROYED`，丢弃模式删除整个
  固定 Run 根；
- 终态 inspect 不再访问已删除的容器；异常重启恢复也将 `FROZEN` 视为活跃中断态处理。
- 2026-07-30 用户再次执行真实验收：Run 完成
  `RUNNING → FROZEN(paused) → RUNNING → STOPPED → DESTROYED`，容器身份、无网络、零
  capabilities 与 Workspace 写入断言继续通过；
- `destroy(preserveUpper=true)` 实测后机器状态为 `DESTROYED`，诊断结果仍存在于 Upper，
  容器与挂载栈均已清理；Compute Runtime 切片验收门关闭。

## 8. 切片 G：COW 提交

状态：施工中（不可变提交对象构建已完成，2026-07-30）

实现 freeze/stop、安全扫描、whiteout/opaque、支持类型矩阵、目标树、新内容分片、PVLog
对象、Ref CAS、Run 终态、写租约和 discard。

测试新建、覆盖、截断、删除、重命名、目录替换、未知 xattr、symlink、hardlink、特殊文件、
扫描竞争、CAS/S3/SQLite 故障。

阶段进度：

- 新增原生 `biunivers-workspace-cow-scan`，从固定 Upper 目录 fd 出发，使用
  `openat/fstatat(AT_SYMLINK_NOFOLLOW)` 遍历，不通过字符串路径追踪子节点；
- 接受普通文件、目录、`0:0` 字符设备 whiteout 与
  `user.fuseoverlayfs.opaque=y`；拒绝 symlink、hardlink、其他特殊文件和未知 xattr，
  错误包含首个不支持的相对路径；
- 扫描执行 entry/depth/单文件/总 bytes 上限，并比较 dev/inode/mode/size/mtime/ctime；
  整棵 Upper 使用独立目录游标扫描两遍，不一致时失败关闭；
- Node `UpperScanner` 只执行固定绝对二进制和固定 `<runId>/upper`，限制执行时间与输出，
  并对原生 JSON 的排序、相对路径、类型、mtime、bytes 汇总和所有上限再次校验；
- 原生测试已覆盖普通树、opaque、symlink、hardlink 和未知 xattr；Node 测试已覆盖命令
  参数冻结与恶意/不一致输出拒绝。
- 本机真实 fuse-overlayfs 复验发现 opaque 目录同时含 xattr 与内部
  `.wh..opq`/`.wh..wh..opq` 标记；扫描器只在父目录已验证 `opaque=y` 时接受并隐藏这两种
  精确表示，其他位置或错误类型的保留名失败关闭；
- 真实 Upper 规范化结果仅保留 opaque 目录、新文件和普通 whiteout，overlay 内部标记未
  泄漏到逻辑变更集，whiteout/opaque 扫描验收门已关闭。
- `TargetTreeProjector` 已以内存方式从固定 Lower EntryIndex 构造 path 索引，并依次应用
  opaque、whiteout、目录合并/替换、文件修改和新增，不读取或写入 S3/RefStore；
- 未修改内容继续复用 Lower Content FID；同路径普通文件修改保留 Entry ID，kind 替换、
  opaque 删除重建和新增路径分配新 128-bit Entry ID，rename 仍表现为删除加新增；
- 投影完成后重新验证唯一 Entry ID/path、唯一根、父目录关系、名称、kind/content、
  depth 和 Entry 总量；孤儿变更、不存在的 whiteout 与随机 ID 分配失败均整次拒绝。
- 原生扫描结果现携带 dev/inode/size/mtime/ctime；`UpperContentMaterializer` 使用
  `O_NOFOLLOW` 打开每个普通文件 fd，并在不可变写入前后复核全部指纹，扫描后替换、截断
  或改写都会整次失败；
- 内容读取按固定小缓冲流式交给现有 `FileContentStore.putStream`，复用其 64 MiB Chunk
  边界、XXH3-128 FID、Manifest 编码和 Manifest 回读校验，不在内存缓冲整个文件；
- 所有 Upper 文件成功后才返回 path→ContentRef 映射；目标树回填要求每个 placeholder
  恰好一个同尺寸 ContentRef，并拒绝缺失或额外物化结果。存储中途失败只留下不可变孤儿
  候选，不产生 Head 或 Ref 可见状态。
- `CommitOperationPlanner` 比较固定 Lower 与已解析目标树，生成最小顶层递归删除、
  parent-first 创建和已有文件内容替换；复用既有 Entry ID 却改变 path/kind 会失败关闭；
- PVLog 批处理现在原生支持 `set-file-content`，同一个 revision 可以组合删除、创建和
  内容替换；普通既有目录只因子项变化时保持原 mtime，因为 PVLog V1 没有独立目录元数据
  操作，避免为时间戳制造替换 Entry；
- `WorkspaceCommitObjectBuilder` 从固定输入 Head 与 revision 加载并校验 Checkpoint，
  编码合并 Segment、应用目标 Checkpoint、构造后继 Head，并对三个持久化对象逐一回读
  校验；
- 对象构建器不持有 RefStore，也不执行 CAS；失败或 CAS 前中止最多留下不可变孤儿对象，
  Workspace Ref 仍保持输入 Head。
- `WorkspaceCommitCoordinator` 只接受控制面 `STOPPED` Run，先原子进入 `COMMITTING`，
  再串联固定 Head 加载、Upper 扫描、投影、内容物化、操作规划、对象构建和最终发布；
