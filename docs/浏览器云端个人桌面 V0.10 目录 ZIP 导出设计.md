# 浏览器云端个人桌面 V0.10 目录 ZIP 导出设计

状态：已实现并归档

日期：2026-07-30

## 1. 目标

让用户从文件管理器把目录或一组项目完整带出 Biunivers，同时保持现有单文件下载体验。
第一版只生成不压缩的 ZIP（Store），不增加新工具栏按钮，不开放第三方目录遍历能力。

## 2. 用户行为

文件管理器现有“下载”按钮根据选择自动决定行为：

| 当前选择 | 行为 | 建议文件名 |
|---|---|---|
| 未选择 | 禁用 | — |
| 一个文件 | 沿用现有原文件下载 | 原文件名 |
| 一个目录 | 导出完整目录树 | `<目录名>.zip` |
| 多个文件或目录 | 导出一个组合归档 | `biunivers-download.zip` |

目录、文件和批量选择均使用同一个下载图标。`aria-label` 和 `title` 应随选择变为“下载文件”、
“将目录导出为 ZIP”或“将 N 个项目导出为 ZIP”，使实际行为可被发现。

导出期间复用现有传输进度条和取消按钮：

- 服务端尚在建立快照计划时显示“正在准备 ZIP…”；
- 响应开始后按收到的 ZIP 字节显示下载进度；
- 完整接收后才触发浏览器保存；
- 用户取消、网络中断或任一对象读取失败时不触发保存。

## 3. 架构选择

ZIP 在 Biunivers 服务端内部生成，浏览器不负责递归遍历。

原因：

- 服务端可以只加载一次 EntryIndex，在一个 revision 上固定目录结构和每个文件的不可变
  Content Ref；
- 文件内容可直接通过 `FileContentStore.readChunks()` 从 Chunk/Manifest 流入 ZIP，不需要
  在服务端拼成完整文件或完整归档；
- 浏览器只处理一个下载响应，取消、进度和错误语义与现有下载接近；
- 不需要向 Host API、Resource Session 或第三方开发包增加目录枚举接口。

这是 `system.files` 的 internal 特权能力。第三方应用仍只能读取宿主明确交付或用户明确选择的
单个资源。

## 4. Internal API

新增：

```http
POST /api/v1/internal/files/exports/zip
Authorization: Biunivers-Instance <instanceToken>
Content-Type: application/json

{
  "entryIds": ["<32 hex Entry ID>", "..."],
  "expectedRevision": 12
}
```

约束：

- 实例必须属于 `system.files`；
- `entryIds` 非空、去重并只保留顶层选择；
- 当前 revision 必须等于 `expectedRevision`，否则返回 `FILE_VERSION_CONFLICT`；
- 根目录不能作为普通列表项提交，但内部实现可以为未来“导出全部”保留扩展空间；
- 所有路径和尺寸检查必须在写出响应头之前完成。

成功响应：

```http
HTTP/1.1 200 OK
Content-Type: application/zip
Content-Disposition: attachment; filename="..."; filename*=UTF-8''...
Content-Length: <准确的 ZIP 字节数>
Cache-Control: no-store
```

JSON 错误沿用现有 internal 文件接口的错误结构。响应流已经开始后若对象读取或客户端连接
失败，服务端立即终止响应；前端 Fetch 因响应不完整而失败，不保存残缺 ZIP。

## 5. 快照与不可变性

收到请求后：

1. 读取一次当前 EntryIndex；
2. 校验 `expectedRevision`；
3. 从该 Index 递归展开所选目录，建立确定顺序的导出计划；
4. 将每个文件的 `FileContentRef` 固定在计划中；
5. 后续直接按这些不可变 Ref 读取内容。

导出过程中即使文件被重命名、移动、删除或更新，当前 ZIP 仍使用开始时的路径和内容。
这利用了 PVLog 元数据快照与 S3 不可变内容的组合，不需要锁住文件树。

当前 GC 不删除对象，因此导出期间的旧 Content Ref 不会失效。未来若启用破坏性 GC，GC 必须
把活动导出计划作为临时可达根或遵守覆盖最长导出时间的删除宽限期；在满足该条件前不得开放
对象删除。

## 6. ZIP 格式

第一版实现 ZIP32 Store：

- 不压缩文件内容；
- 文件名使用 UTF-8，并设置通用用途位 11；
- 目录以末尾 `/` 的独立条目写入，因此保留空目录；
- 本地文件头后的 CRC-32 和尺寸使用 Data Descriptor；
- Central Directory 保存在小型内存索引中，文件内容不进入该索引；
- 修改时间写入 ZIP DOS 时间字段，超出范围时安全截断；
- 条目按顶层选择顺序及目录内名称顺序稳定输出。

Entry 名称本身已经禁止 `/`、控制字符、`.` 和 `..`。ZIP Writer 仍应把最终相对路径作为
不可信输入校验：不得以 `/` 开头，不得包含空段、`.` 或 `..` 段，不得含反斜杠，从而防止
Zip Slip。

第一版明确限制：

- 最多 10,000 个 ZIP 条目；
- 单条 UTF-8 路径不超过 65,535 字节；
- 单文件、Central Directory 偏移和 ZIP 总尺寸均不得达到 `0xffffffff`；
- 超限时在传输开始前明确报错，不静默截断，也不生成 ZIP64。

这些限制足以覆盖当前交互式导出需求。ZIP64、压缩级别和超大备份归档留待出现真实需求后
再设计。

## 7. 流式与背压

ZIP Writer 以异步字节序列输出：

- 小型头、Data Descriptor 和 Central Directory 记录按需生成；
- 文件正文直接 `yield* FileContentStore.readChunks(content)`；
- CRC-32 在正文流过时增量计算；
- HTTP 层尊重 `response.write()` 背压，等待 `drain` 后继续读取 S3；
- 请求被中止时停止后续遍历和对象读取；正在进行的单次对象 GET 至迟在返回后丢弃结果。

归档总字节数可由已知文件尺寸、UTF-8 路径长度和固定 ZIP 结构预先精确计算，因此能够设置
`Content-Length`，前端可以显示准确进度。

浏览器端仍需在完整下载后构造 Blob 才能通过通用 Web 下载能力保存。这与现有单文件下载
一致，会占用约等于 ZIP 大小的浏览器内存；绕过 Blob 需要依赖并非所有浏览器支持的本地文件
系统 API，不纳入第一版。

## 8. 错误和取消

- revision 变化：提示“文件系统已发生变化，目录已刷新，请重新下载”并刷新列表；
- 选择项不存在：提示对应项目已不存在并刷新；
- 超过 ZIP32 或条目限制：说明具体限制，不开始下载；
- S3 内容缺失或完整性失败：终止响应，不保存不完整归档；
- 用户取消：中止 Fetch，清除进度，提示“下载已取消”；
- 取消和失败都不得影响文件树、RefStore 或不可变对象。

下载是只读操作，不创建 PVLog 事件，也不在 S3 留下临时对象或垃圾对象。

## 9. 非目标

第一版不做：

- Deflate 或其他压缩；
- TAR、ZIP64、加密 ZIP 和分卷；
- 在 Biunivers 内浏览或解压 ZIP；
- 后台下载队列和断点续传；
- 导出第三方应用包、系统设置或 RefStore；
- 向第三方协议开放目录树。

## 10. 验收标准

- 单文件下载行为保持不变；
- 单个目录导出后保留顶层目录、嵌套文件和空目录；
- 多选文件与目录进入同一个 ZIP，路径和内容正确；
- 中文、空格和常见 Unicode 文件名可正常解压；
- 大于 64 MiB 的 Manifest 文件以流式方式导出且内容逐字一致；
- 进度持续更新，取消不会触发浏览器保存；
- 导出开始后发生重命名或内容更新，归档仍保持开始时的同一 revision 快照；
- revision 冲突、超限、对象读取失败均不给出看似成功的残缺文件；
- 第三方 Host API 与 Resource Session 能力没有扩大；
- 现有上传、文件下载、批量选择、移动、复制和移除回归通过。
