# 浏览器云端个人桌面 V0.13 Workspace Runtime 技术设计

状态：总设计通过；局部设计冻结候选

日期：2026-07-30

## 1. 目标

V0.13 引入系统级 Workspace：

> 用户从主文件世界选择文件或目录，宿主派生一个只包含所选内容的独立 PVLog 世界，并把
> 固定 HEAD 的只读文件系统与本地临时写层合并后挂载到隔离容器。

Workspace 是通用计算基础，不从属于 AI。Agent、编译测试、转码、OCR、批处理和用户脚本
都是运行在 Workspace 中的不同执行器。

第一版必须闭环：

```text
选择内容
→ 派生最小 Workspace
→ 固定 HEAD 并直接挂载
→ 在沙箱中修改
→ 提交为新 HEAD
→ 查看差异
→ 复制结果回 main 或丢弃
```

## 2. 非目标

V0.13 第一版不做：

- 任意第三方 OCI 镜像安装；
- Workspace App 公共安装协议；
- 多容器编排；
- 同一 Workspace 多写者；
- 实时可写 PVLogFS；
- 自动合并回 `main`；
- 跨 Workspace 挂载；
- Windows 或 macOS 宿主；
- FUSE 挂载直接暴露给远程客户端；
- 多智能体编排或模型供应商绑定。

## 3. 概念模型

### 3.1 Universe

Universe 是技术概念，表示一条独立 PVLog lineage 及其 Ref/HEAD。第一版不建立单独的
`UniverseService` 或 `universes` 表。

### 3.2 Workspace

Workspace 是用户管理的产品对象：

```text
Workspace
├── workspaceId
├── refId
├── name
├── baselineHead
├── source
├── state
├── retention
└── runs[]
```

每个 Workspace 恰好映射一个 SQLite Ref。

### 3.3 Run

Run 是在 Workspace 上执行的一次隔离计算：

```text
Run
├── runId
├── workspaceId
├── executorId
├── inputHead
├── outputHead?
├── state
├── resourcePolicy
└── runtimeIdentity
```

一个 Run 从启动到结束始终固定同一个 `inputHead`。运行期间 Workspace Ref 不得改变本次
Run 的只读 Lower。

### 3.4 Workspace App

Workspace App 是未来应用类型，由 iframe UI 和 OCI Runtime 组成。V0.13 先使用系统维护的
诊断执行器验证运行时闭环，不冻结第三方 Workspace App 协议。

## 4. 总体架构

```text
文件管理器 ─────────┐
                    v
Workspace internal App
                    |
                    v
Workspace Service
├── Workspace Store
├── Selection Deriver
├── Run Coordinator
├── Diff / Import
└── Retention
                    |
          窄、受认证的本地 API
                    |
                    v
Compute Runtime Daemon
├── PVLogFS Supervisor
├── COW Mount Manager
├── OCI Runtime Adapter
├── Runtime Proxy
└── Resource Policy
                    |
                    v
PVLog Object Repository / S3
```

当前 Biunivers 容器不挂载 Docker socket。Compute Runtime 是独立的宿主服务，仅暴露
`prepare/start/inspect/checkpoint/stop/destroy` 等固定操作，不暴露通用 Docker API。

## 5. 控制状态

具体 Schema、状态机、事务和恢复规则由
[Workspace 控制面局部设计](<浏览器云端个人桌面 V0.13 Workspace 控制面局部设计.md>)
冻结。

### 5.1 Ref 继续存放在 SQLite

Ref 不文件化，也不写入 S3。现有 `filesystem_refs` 扩展为：

```text
main
ws-<opaque-id>
ws-<opaque-id>
```

普通桌面路径永远使用 `main`。Workspace API 接受不透明 `workspaceId`，由服务端映射到
内部 `refId`；浏览器和容器都不能提交任意 Ref ID。

### 5.2 Workspace 表

Workspace 与 Ref 都是关键可达性控制数据，第一版放在同一个 RefStore SQLite 文件的独立表，
以便在同一事务内创建或删除 Workspace 与 Ref：

```sql
workspace_records(
  workspace_id BLOB PRIMARY KEY,
  ref_id TEXT UNIQUE NOT NULL,
  name TEXT NOT NULL,
  source_ref_id TEXT NOT NULL,
  source_head_fid BLOB NOT NULL,
  baseline_head_fid BLOB NOT NULL,
  state TEXT NOT NULL,
  retention TEXT NOT NULL,
  created_at_ms INTEGER NOT NULL,
  updated_at_ms INTEGER NOT NULL
)

workspace_runs(
  run_id BLOB PRIMARY KEY,
  workspace_id BLOB NOT NULL,
  executor_id TEXT NOT NULL,
  input_head_fid BLOB NOT NULL,
  output_head_fid BLOB,
  state TEXT NOT NULL,
  runtime_identity TEXT,
  created_at_ms INTEGER NOT NULL,
  started_at_ms INTEGER,
  finished_at_ms INTEGER
)
```

SQLite schema 升级、备份和恢复必须同时覆盖 Ref、Workspace 与 Run。

## 6. 派生最小 Workspace

### 6.1 第一版选择边界

- 入口来自文件管理器；
- 选择项必须属于同一目录；
- 可以选择普通文件和目录；
- 目录递归包含当前来源 HEAD 中的后代；
- 根级名称不得冲突；
- 设置文件数、总元数据和最大深度上限；
- 创建期间来源固定为一个 `sourceHead`。

### 6.2 派生过程

```text
main Ref
  ↓
固定 sourceHead
  ↓
加载并验证 EntryIndex
  ↓
展开选择集
  ↓
创建新虚拟根和新 Entry ID
  ↓
文件内容继续引用原 Content FID
  ↓
编码 revision 0 Checkpoint
  ↓
生成新 lineage 的 Genesis HEAD
  ↓
同一 SQLite 事务创建 Workspace + ws-* Ref
```

这是“选择集派生”，不是普通 Fork。因为它不包含完整来源世界、根和 Entry ID 都不同，所以
使用新的 lineage。来源 Ref、来源 HEAD 和顶层选择记录在 Workspace 元数据中，不写入
PVLog 对象。

第一版结果导回采用显式复制，不尝试根据来源 Entry ID 自动执行三方合并，因此不保存完整
的逐 Entry 来源映射。

## 7. Ref-aware 文件服务

现有上层实现多处硬编码 `getRef("main")`。需要在内部服务边界显式传入 Ref：

```ts
loadEntryIndex(repository, refStore, refId)

new FileSystemTransactions({
  refId,
  repository,
  refStore
})
```

规则：

- 桌面、File Manager、Resource Session 和 Wormhole 默认只能使用 `main`；
- Workspace Service 通过内部可信调用使用 `ws-*`；
- public/third-party API 不增加 `refId` 参数；
- Scoped WebDAV 可以以后通过 `workspaceId` 映射 Ref，但不属于 V0.13 必选路径。

## 8. 只读 PVLogFS

具体 inode、完整 Chunk 校验缓存、进程边界和 Runtime API 由
[PVLogFS 与 Compute Runtime 局部设计](<浏览器云端个人桌面 V0.13 PVLogFS 与 Compute Runtime 局部设计.md>)
冻结。

### 8.1 挂载语义

PVLogFS 挂载固定的 `inputHead`，而不是跟随可变 Ref：

```text
Workspace Ref → HEAD A
Run.inputHead = HEAD A
PVLogFS lower 始终读取 HEAD A
```

第一版实现：

- `lookup`；
- `getattr`；
- `readdir`；
- `open`；
- `read/pread`；
- 固定只读权限；
- 稳定 inode 映射；
- Head、Checkpoint、Manifest 与 Chunk FID 验证；
- Chunk/Manifest 本地缓存；
- 明确拒绝写入和未支持的特殊文件。

第一版不支持符号链接、设备、FIFO、socket、扩展属性和文件锁语义。PVLog 当前只表达普通
文件与目录，因此不伪造这些类型。

### 8.2 缓存

```text
内存
├── Head
├── EntryIndex
└── 热 Manifest

本地共享缓存
├── Checkpoint
├── Manifest
└── Chunk
```

缓存按 FID 校验，可跨 Workspace/Run 共享，非权威且可按 LRU 回收。内容读取只获取实际需要
的 Chunk；不得因小范围读取下载完整大文件。

## 9. COW 挂载

每个 Run 建立：

```text
/run/biunivers/workspaces/<run-id>/
├── lower/   # PVLogFS，只读
├── upper/   # 本地临时写层
├── work/    # Overlay 工作目录
└── merged/  # bind 到容器 /workspace
```

技术探针已验证并固定使用 `fuse-overlayfs`；V0.13 不再同时实现内核 OverlayFS 路线。容器
只看到 `/workspace`，不获得 `/dev/fuse`、挂载权限、Docker socket、S3 凭据或 RefStore。

同一 Workspace 第一版最多一个可写 Run。需要并行计算时先从同一 Workspace HEAD 派生新的
Workspace。

Run 处于 PREPARING、RUNNING 或 CHECKPOINTING 时，Workspace Service 必须持有该
Workspace 的写租约，拒绝文件页和其他内部 API 的修改。此时文件页只展示已发布的 Ref，
Upper 中尚未 Checkpoint 的变化只在 Run 活动中显示；提交成功后才成为 Workspace 文件视图
的一部分。

## 10. Compute Runtime

第一版运行策略：

- Linux 宿主；
- 系统维护、固定 digest 的诊断镜像；
- 非 root；
- `no-new-privileges`；
- 移除全部 capabilities；
- 只读容器 root filesystem；
- 仅 `/workspace` 可写；
- 默认无网络；
- 限制 CPU、内存、PID、运行时间和 Upper 容量；
- 禁止 host network、宿主设备和任意宿主路径；
- 异常退出后保留 Upper，等待恢复或丢弃。

窗口、Run 和 Workspace 生命周期独立：

- 关闭 iframe 不自动停止 Run；
- 停止 Run 不删除 Workspace；
- 删除 Workspace 必须先停止并清理全部 Run。

## 11. 提交

Upper 支持矩阵、whiteout/opaque 解释、CAS、Diff 和导回规则由
[COW 提交、Diff 与导回局部设计](<浏览器云端个人桌面 V0.13 COW 提交、Diff 与导回局部设计.md>)
冻结。

Checkpoint/停止时：

1. 暂停或停止容器写入；
2. 读取 Lower 基线与 Overlay Upper/whiteout；
3. 构造目标目录状态；
4. 未修改内容继续引用原 FID；
5. 仅对新增或修改内容分片、计算 FID并上传；
6. 把变更规范化为 PVLog operations；
7. 生成 Segment、Checkpoint 和新 Head；
8. 验证新对象；
9. CAS 推进 Workspace Ref；
10. 记录 Run `outputHead`。

第一版可把重命名表示为删除加创建，不承诺跨任意工具保持 Entry ID；内容仍可按 FID 去重。
提交必须限制单次操作数和新增字节数，超限时明确失败并保留 Upper。

若 Workspace Ref 不再等于 `inputHead`，提交进入冲突状态，不覆盖、不自动合并。

## 12. Diff 与导回

Workspace Diff 比较 `baselineHead` 与当前 Workspace HEAD，展示：

- 新增；
- 修改；
- 删除；
- 路径变化；
- 文本 Diff；
- 二进制文件的大小、类型和内容版本变化。

V0.13 导回规则：

- 用户选择结果文件或目录；
- 选择 `main` 中的目标目录；
- 按现有复制/冲突确认语义创建新 Entry；
- 不自动应用删除；
- 不自动覆盖同名文件；
- 不执行三方合并。

因此第一版不需要完整来源 Entry 映射。

## 13. Workspace 系统应用

新增 internal 应用“工作空间”：

```text
列表
├── 名称
├── 状态
├── 来源
├── revision
├── 最近 Run
├── 变更统计
└── 保留策略

详情
├── 概览
├── 文件
├── 变更
├── 运行
└── 活动
```

文件页复用 Ref-aware `FileManagerBrowser`，客户端只传 `workspaceId`。文件管理器增加“创建
工作空间”入口；Workspace 创建完成后打开对应详情。

## 14. GC 与删除

现有 GC 只以 `main` 及其快照为根，V0.13 必须改为读取一致性快照中的所有 Ref 和 Snapshot
HEAD。任何 READY、RUNNING、REVIEW 状态的 Workspace Ref 都是可达根。

删除顺序：

1. 将 Workspace 标记为 DELETING；
2. 停止容器并阻止新 Run；
3. 卸载 merged/Overlay/PVLogFS；
4. 删除 Run 临时目录；
5. 在 SQLite 事务中删除 Workspace Ref 和记录；
6. 后续 GC 才能把独占对象列为候选。

共享 FID 不做即时对象删除。

## 15. 崩溃恢复

启动时协调：

- RUNNING 但容器不存在；
- 容器存在但 Run 记录缺失；
- 遗留 FUSE/Overlay mount；
- PROVISIONING/DELETING 中断；
- Upper 存在但未提交；
- Ref 已前进但 Run 未记录 outputHead；
- Workspace 记录与 Ref 不一致。

恢复过程不得自动丢弃 Upper，不得在不确定时推进或覆盖 Ref。

## 16. 技术探针

正式施工前首先完成 Linux 探针：

1. 最小只读 FUSE Lower；
2. 目录与随机读取；
3. OverlayFS 或 `fuse-overlayfs` 合并；
4. 新建、修改、重命名、删除和 whiteout；
5. bind mount 给非特权容器；
6. 大文件随机读取；
7. 容器异常退出；
8. 正常、强制和重启后卸载；
9. Upper 变化可确定性解释；
10. 不向容器授予 mount/FUSE/Docker 权限。

探针决定 Overlay 实现，是 V0.13 的 Go/No-Go 门槛；不通过时先调整挂载实现，不回退为正式
全量物化架构。

## 17. 建议施工阶段

1. 挂载与 Overlay 技术探针；
2. RefStore schema 升级和 Ref-aware 服务；
3. 选择集派生与 Workspace 管理；
4. 固定 HEAD 的只读 PVLogFS；
5. Compute Runtime 与 COW Run；
6. Upper 提交、Diff、导回和 GC；
7. Workspace internal 应用；
8. 系统诊断执行器真实验收；
9. 闭环稳定后另行设计 Workspace App v1。

## 18. 验收主线

- 大 Workspace 不全量下载即可启动；
- 容器只能看到所选内容；
- 未读取内容不会提前下载；
- 原文件保持不可变；
- 容器修改只进入 Upper；
- 丢弃 Run 不推进 Ref；
- 提交生成新 HEAD；
- 结果可查看和选择性导回；
- `main` 不被自动修改；
- Workspace 删除后 GC 可安全识别独占对象；
- 宿主和容器异常后可以恢复或人工处置。
