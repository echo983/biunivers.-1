# 浏览器云端个人桌面 Open Resource v1.1 规范评审

状态：评审通过，具备施工条件

日期：2026-07-30

## 1. 评审结论

Open Resource v1.1 有明确必要性，范围可以保持克制，设计闭环。

采用 v1.1 而不是独立 Multi-Resource Extension，可以避免协议碎片化。v1.1 只负责“如何
取得一组资源”，每个资源仍由 Resource Session v1 访问，因此没有重复定义内容协议。

## 2. 必要性

真实应用需要一次取得多个用户选择文件：

- 图片查看器的一组图片；
- 播放器的播放列表；
- 两个文件的比较工具；
- 批量转换、上传或归档应用。

当前反复调用单文件 picker 在技术上可同时持有多个 Session，但用户需要重复打开对话框，
无法表达“一次授权这一组文件”，也无法从文件管理器多选直接交付。缺口真实且接近当前
产品能力，不是远期假设。

## 3. 保留项

必须保留：

- `resource.openMany`；
- Handler 的 `multiple` 明示资格；
- 文件管理器共同 Handler 解析；
- 批量 Launch Context；
- 每文件独立 Session；
- 全成或全败签发；
- 数量和消息大小上限；
- v1 长期兼容。

缺少 `multiple` 会把批量文件交给只实现单文件状态机的应用；缺少共同 Handler 校验会让
应用收到自己未声明支持的文件；缺少原子签发会产生用户和应用都难以理解的部分授权。

## 4. 删除或延期项

第一版删除或延期：

- 批量编辑和多文件保存；
- 多目录选择篮；
- 目录 capability；
- 组 Session ID；
- 批量默认关联；
- 跨应用 Session 转交；
- 操作系统拖放；
- 后台目录观察；
- 自动补充同类型或相邻文件；
- 多文件原子内容快照。

这些能力不是“选择一组文件供应用读取”的必要条件。

## 5. 协议数量评审

不新增 Multi-Resource Extension。协议集合保持：

```text
Open Resource v1
Open Resource v1.1
Resource Session v1
```

v1.1 是 Open Resource 的版本演进，不是第四种资源概念。Resource Session 标识和内容
接口不变。

新增 v1.1 固定原文和 Schema 是版本兼容的必要成本，不能通过修改 v1 原文规避。

## 6. 授权边界

通过：

- 用户仍在宿主 UI 明确选择；
- 只交付具体 Entry；
- 选择器不返回目录；
- 同一目录限制避免隐式跨目录选择篮；
- Handler 不能枚举其他匹配文件；
- Session 独立撤销；
- 停用、卸载、更新和重启撤销全部能力。

批量并没有扩大单个 Session 的权限，只把多次用户选择合并为一次明确授权。

## 7. 只读边界

批量第一版只读是必要收敛。

多文件编辑会引出：

- 部分保存成功；
- 多文件版本冲突；
- 用户对整批保存的预期；
- 应用崩溃后的恢复；
- 是否需要事务性提交。

这些问题与批量打开无关。应用仍可对某一个文件另行请求单文件 edit Session。

## 8. 数量上限评审

协议上限 500、默认请求 100合理，但必须服从 64 KiB 消息上限。施工阶段必须用最大长度
文件名、媒体类型、URL 和 token 测量公开投影。

如果 500 项无法安全放入一条响应：

- 降低宿主硬上限；
- 通过 `maximumOpenMany` 公开真实值；
- 不在第一版引入分页或组 token。

这是比新增分页协议更简单可靠的选择。

## 9. 顺序语义

选择结果采用宿主当前显示顺序，而不是鼠标点击时间：

- 行为确定；
- Shift 选择天然一致；
- 文件管理器与 picker 能复用排序；
- 不需要额外维护点击序列；
- 图片和播放列表得到可预测顺序。

应用可以在取得资源后自行重排。

## 10. 兼容性

通过：

- v1 文件和 Schema 逐字不变；
- 单文件结果仍为 `resource`；
- v1.1 批量结果使用 `resources`；
- 两者互斥；
- v1 应用不收到批量 Launch；
- v1.1 应用仍能处理单文件 Launch；
- 旧 Host API 保持单资源，不扩张第二条批量数据路径。

## 11. 实现复杂度

复杂度中等，主要集中于：

- 版本化 Validator；
- 多选 picker；
- 集合 Handler 解析；
- Session Registry 批量预检；
- Pending Launch 单值到集合迁移；
- 文件管理器批量打开 UI；
- 开发者包与第三方应用适配。

不涉及 S3、PVLog、WASM 或内容流，风险可控。适合分两阶段施工。

## 12. 风险与控制

| 风险 | 控制 |
|---|---|
| 应用未实现批量状态机 | 必须声明 `multiple: true` |
| 部分 Session 泄漏 | Registry 批量预检、全成或全败 |
| 集合中混入不支持文件 | 同一个 Handler 匹配全部 Entry |
| 消息过大 | 真实投影测量并下调 capability 上限 |
| v1 应用回归 | 双 Validator、v1 原文不变 |
| 文件系统枚举 | 只返回用户选择 Entry |
| 批量写语义膨胀 | 第一版强制 read |
| 未领取 Launch 被覆盖 | 每应用一个 pending，busy 明确失败 |

## 13. 施工门槛

施工前已经满足：

- v1.1 固定原文草案；
- v1.1 Handler Schema；
- 兼容和安全边界；
- 分阶段技术设计；
- 明确非目标。

可以进入施工。施工时如果发现必须修改 Resource Session v1 原文、增加组 Session 或引入
目录遍历，必须暂停并重新评审，不能在实现中悄悄扩大范围。
