# 浏览器云端个人桌面 V0.9 文件管理器批量操作技术设计

状态：已完成并归档（`v0.9.0`）

日期：2026-07-29

## 选择模型

```ts
interface FileSelection {
  entryIds: Set<string>;
  anchorEntryId?: string;
}
```

Shift 区间只基于当前 `listing.entries` 的稳定显示顺序。刷新和导航后不尝试把旧区间映射到
新列表。

## API

```text
POST /api/v1/internal/files/batch/move
POST /api/v1/internal/files/batch/copy
POST /api/v1/internal/files/batch/remove
```

共同约束：

- 只允许 `system.files` 实例能力；
- `entryIds` 为去重后的非空 Entry ID 数组；
- 设置合理的项目数量上限；
- 必须携带 `expectedRevision`；
- 服务端重新完成所有校验，不能信任 UI 已过滤的选择；
- 成功返回新 revision 和受影响的顶层 Entry ID。

## 原子性

PVLog Segment 已包含 `Vec<Operation>`。V0.9 扩展 WASM ABI，使一个编码调用接受多项
MoveEntry、CreateDirectory/CreateFile 或 RemoveEntry 操作，输出一个规范 Segment。

事务流程：

1. 从 `expectedRevision` 加载 Head 与 Checkpoint；
2. 构造完整操作列表；
3. Rust `apply_segment` 在内存按序应用全部操作；
4. 任一操作失败则不写 Head、不 CAS Ref；
5. 成功后写一个 Segment、一个 Checkpoint、一个 Head；
6. 对 Ref 执行一次 CAS。

因此批量操作只增加一次 revision。

## 递归复制

服务端从当前 EntryIndex 深度优先展开选中的顶层 Entry：

- 先为目录生成新 Entry ID 和 CreateDirectory；
- 再为其直接子项生成新 Entry ID；
- 子项的 parent ID 指向刚生成的新目录 ID；
- 文件 CreateFile 复用原 `content.kind`、FID、size 和 mtime；
- 新 Entry 的 createdAt 使用本次事务时间；
- 展开总数超过限制时在编码前拒绝。

复制不会读取或重写 Chunk/Manifest。

## 校验

- 输入 ID 必须存在且不能为根；
- 顶层选择规范化，去掉已被所选祖先包含的项；
- 目标必须是现存目录；
- Move 对每个目录做环检测；
- 目标目录现有名称与本批顶层名称共同做冲突检查；
- Copy 展开后确保 Entry ID 唯一；
- Remove 总是递归，并按最上层选择编码；
- revision 冲突返回既有 `FILE_VERSION_CONFLICT`。

## 兼容

现有单项接口保留。单项重命名和“创建副本并指定新名称”继续使用原有接口；批量按钮使用新
接口。Checkpoint 和 Segment 的磁盘格式不变，只是已有 Segment `operations` 数组开始包含
多个元素，因此旧数据保持可读。
