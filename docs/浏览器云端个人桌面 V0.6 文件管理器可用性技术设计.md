# 浏览器云端个人桌面 V0.6 文件管理器可用性技术设计

状态：设计基线

对应需求：[V0.6 文件管理器可用性需求](<浏览器云端个人桌面 V0.6 文件管理器可用性需求.md>)

## 1. 设计结论

V0.6 复用 `FileContentStore`、`FileSystemTransactions` 和
`InternalFileManagerService`，不新增存储格式。

```text
system.files
  ├─ POST /api/v1/internal/files/files
  │    └─ empty Chunk → CreateFile → Ref CAS
  └─ POST /api/v1/internal/files/entries/:entryId/copies
       └─ current content ref → CreateFile → Ref CAS
```

## 2. 新建空文件

请求：

```json
{
  "parentEntryId": "32 lowercase hex",
  "name": "未命名.txt",
  "expectedRevision": 8
}
```

服务端依次验证实例、revision、父目录、名称和重名，再通过
`FileContentStore.putBytes(new Uint8Array())` 取得空 Chunk 引用。空 Chunk 天然按 FID 去重。
最后调用带 `expectedRevision` 的 `createFile` 发布新 Entry。

## 3. 复制文件

请求：

```json
{
  "newParentEntryId": "32 lowercase hex",
  "newName": "note - 副本.txt",
  "expectedRevision": 9
}
```

服务端从同一 revision 的 EntryIndex 读取源文件。源必须是普通文件且具有有效 content ref；
目标必须是目录且名称唯一。事务创建新 Entry ID，并把源 `kind`、`fidHex` 和 `size` 原样写入
CreateFile Segment。

服务端不调用 `FileContentStore.readChunks` 或 `putStream`。因此复制 1 字节与 1 TiB 文件的
控制面成本相同，且不会生成重复内容对象。

## 4. 事务调整

`CreateFileInput` 增加可选 `expectedRevision`，并传给事务的 current-state 读取。Host API
`saveAs` 不提供此字段，保持现有提交时 CAS 行为；internal 新建和复制必须提供精确 revision。

Internal File Manager 把底层 `REF_CONFLICT` 继续映射为 `FILE_VERSION_CONFLICT`。

## 5. 前端

- 工具栏新增“新建文件”和“复制”；
- “复制”只对普通文件启用；
- 两者复用名称对话框，并分别提供 `未命名.txt` 与基于原名的副本建议；
- mutation 期间沿用全局 `working` 锁，按钮不可重复提交；
- 主目录导航和移动对话框在请求开始时清除陈旧 listing；
- 加载区域显示 `正在读取目录…` 或 `正在读取目标文件夹…`；
- 成功后刷新 listing 并显示明确 notice。

## 6. 安全与失败

- 路由复用 `requireInternalFileManager`；
- 第三方 App Origin 和非 `system.files` token 被拒绝；
- 不返回 FID、对象 Key 或 Ref 内容；
- 重名、非法名称、目录复制、根复制和缺失 Entry 返回明确错误；
- CAS 冲突不自动重试，以免把用户基于旧 listing 的意图应用到新树。
