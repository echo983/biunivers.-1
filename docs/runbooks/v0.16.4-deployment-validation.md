# Plan: Harden & Validate Biunivers v0.16.4 First-Time VPS Deployment

## 1. Goal
Harden the Biunivers v0.16.4 first-time VPS deployment flow, then prove it
end-to-end on clean Debian 12 and Debian 13 QEMU/KVM test VMs.

---

## 2. Current State

| Item | Status |
|------|--------|
| Fresh v0.16.4 Debian runtime release built in `release/` | Done |
| `scripts/build-debian-release.sh` resolves ghcr.io top-level manifest digest automatically via Node `fetch`, falls back gracefully if `BIUNIVERS_RELEASE_*_DIGEST` is unset | Done |
| `scripts/verify-debian-deployment-vm.sh` reads `BIUNIVERS_DESKTOP_BIND/PORT` and `BIUNIVERS_APP_BIND/PORT` from the provided `.env`, and checks the Runtime socket as the `biunivers` user | Done |
| `deploy/install.sh` flips `BIUNIVERS_FILE_INITIALIZE=false` after successful genesis, preventing re-initialization on every restart | Done |
| Reboot detection timeout in `scripts/verify-debian-deployment-vm.sh` raised to 180s/180s | Done |
| Debian 12 / 13 test VMs wiped and re-prepared to a clean state | Done |

The previous verification runs proved the first-time install and container startup
work on both OS versions. They failed only at the reboot-persistence stage because
the verifier gave up before `systemctl reboot` could finish waiting for the long
`TimeoutStopSec` of the Biunivers services.

---

## 3. Scope / Boundary

### In scope
- `deploy/install.sh`
- `scripts/build-debian-release.sh`
- `scripts/verify-debian-deployment-vm.sh`
- Environment-aware verification for `.env` files such as `secret/biunivers-test.env`
- First-time deployment on stock Debian 12 and Debian 13 cloud images under QEMU/KVM
- Genesis one-shot behavior (`BIUNIVERS_FILE_INITIALIZE` flip)
- Container image digest pinning matching Docker `RepoDigests`

### Out of scope
- Any application feature work outside the deployment path
- Upgrade path from pre-v0.16.4 installed systems
- Other Linux distributions or architectures
- Public TLS / wildcard certificate setup
- Production secret rotation beyond providing a single `.env` file to the test runner

---

## 4. Next Steps

1. **Run final end-to-end verification**
   - Execute `scripts/verify-debian-deployment-vm.sh` against:
     - Debian 12, release `v0.16.4`, env `release/biunivers-test-d12.env`
     - Debian 13, release `v0.16.4`, env `release/biunivers-test-d13.env`
   - The script will install from scratch, run health checks, reboot, and verify
     the Runtime socket and File Service status are still stable.

2. **Capture evidence**
   - Keep `/tmp/biunivers-acceptance-d12/verify.log`
   - Keep `/tmp/biunivers-acceptance-d13/verify.log`
   - Record final pass/fail lines and service status after reboot.

3. **Commit the code changes**
   - `deploy/install.sh`
   - `scripts/build-debian-release.sh`
   - `scripts/verify-debian-deployment-vm.sh`
   - Do not commit `release/` or test env files (they are build/test outputs).

4. **Clean up the test environment**
   - Stop both QEMU/KVM VMs.
   - Delete the VM disk images (`secret/debian-deployment-vm-*/disk.qcow2`).
   - Remove temporary `/tmp/biunivers-acceptance-*` and `/tmp/biunivers-vm-*` logs.

---

## 5. Exit Conditions (Definition of Done)

The task is considered complete only when **all** of the following are true:

1. `scripts/verify-debian-deployment-vm.sh` exits `0` for both Debian 12 and
   Debian 13, and each log ends with the success banner.
2. After reboot, on each VM:
   - `biunivers-host.service` is active,
   - `docker compose ps` shows both containers `Up (healthy)`,
   - the Runtime socket `/run/biunivers/runtime.sock` exists and is owned by the
     `biunivers` user,
   - the desktop (`127.0.0.1:8090`) and app (`127.0.0.1:8091`) endpoints respond.
3. `.env` inside the VM has `BIUNIVERS_FILE_INITIALIZE=false`, confirming genesis
   ran exactly once.
4. The three script changes are committed (or ready for review) with a clear
   commit message explaining the genesis-flag, digest-resolution, and verifier
   hardening fixes.
5. VMs are stopped, disks removed, and no stale `verify-debian-deployment-vm.sh`
   or `prepare-debian-deployment-vm.sh` processes remain.

---

## 6. Rollback / If Things Go Wrong

- If either verifier fails again, stop both VMs, wipe their disks and
  `known_hosts`, fix the offending script, and repeat step 1.
- Do **not** manually patch installed VMs; always restart from a clean image to
  keep the "first-time deployment" guarantee.
