# 浏览器云端个人桌面 V0.13 Workspace Runtime 规范评审

状态：评审通过，可进行技术探针；尚未批准完整施工

日期：2026-07-30

评审对象：

- [V0.13 Workspace Runtime 技术设计](<浏览器云端个人桌面 V0.13 Workspace Runtime 技术设计.md>)

## 1. 必要性

### 1.1 Workspace 是否应独立于 Agent

结论：应当。

选择集派生、挂载、COW、提交、Diff、导回和回收同时适用于 Agent、编译、测试、转码、OCR
和批处理。把底座命名为 Agent Service 会导致生命周期和权限模型被单一执行器绑架。

### 1.2 是否需要直接挂载

结论：需要。

全量物化会把启动成本绑定到 Workspace 总体积，并削弱按需读取、共享缓存和大世界快速分叉
的价值。V0.13 必须先验证固定 HEAD 的只读挂载。

### 1.3 是否需要 Workspace 管理界面

结论：需要。

Workspace 是长期可达根和潜在存储占用者。没有管理界面就无法审阅结果、停止 Run、设置保留
策略或安全删除。

## 2. 逻辑自洽性

### 2.1 不可变后端

自洽：

- S3 仍只保存不可变对象；
- 可变 Ref 保留在 SQLite；
- PVLogFS 固定到不可变 HEAD；
- 容器写入本地 Upper；
- 只有 Workspace Service 可以验证并 CAS 发布新 HEAD。

容器不能接触 S3 凭据或 RefStore，因此没有绕过发布点。

### 2.2 最小披露

自洽：

- 选择集派生新根、新 Entry ID 和新 lineage；
- 新 Checkpoint 不包含未选择 Entry；
- 内容层只共享不可逆寻址的 FID对象；
- 容器只挂载派生 Workspace。

从内容去重不能反推出或枚举主世界目录。

### 2.3 Run 一致性

自洽：

- Run 固定 `inputHead`；
- Lower 不跟随 Ref；
- 同一 Workspace 只有一个可写 Run；
- Run 持有 Workspace 写租约，阻止文件页或其他 API 并发修改 Ref；
- 提交以 `inputHead` 做 CAS；
- 冲突保留 Upper，不覆盖。

### 2.4 结果导回

自洽：

- Workspace 修改只推进自己的 Ref；
- 导回通过现有文件复制语义显式创建到 `main`；
- 不自动删除、覆盖或三方合并；
- 因此无需在第一版维护完整来源 Entry 映射。

### 2.5 GC

当前实现不满足，但设计闭环清晰：

- GC 必须从只保护 `main` 改为保护所有 Ref；
- 删除 Workspace 先停止 Run并移除 Ref；
- 共享对象仍由其他 Ref 保持可达；
- 不即时删除 S3 对象。

这是施工阻塞项，不是设计矛盾。

### 2.6 部署权限

自洽：

- 当前主容器不获得 Docker socket；
- 独立 Runtime Daemon 承担 mount 和 OCI 权限；
- 第三方容器无 `/dev/fuse`、mount capability 或 Docker API；
- 控制面只调用窄 API。

需要新增部署组件，但没有扩大普通应用和 File Service 的权限。

## 3. 冗余检查

### 3.1 Universe 与 Workspace

发现潜在重复，已删减：

- Universe 保留为 PVLog 技术概念；
- 不建立独立 Universe 表、Universe Service 或 Universe UI；
- 用户和 API 只管理 Workspace；
- 每个 Workspace 直接映射一个 Ref。

### 3.2 WorkspaceStore 与 RefStore

发现跨数据库事务冗余，已删减：

- 不另建 `workspace.sqlite`；
- Workspace/Run 表与 Ref 表放在同一 SQLite 文件；
- 代码层仍可拆分 Store 类，但共享事务和备份。

### 3.3 Workspace 文件浏览器

不重复实现：

- 复用 Ref-aware `FileManagerBrowser`；
- 普通文件管理器固定 `main`；
- Workspace 页面通过 `workspaceId` 获得受限文件视图。

### 3.4 WebDAV 与 PVLogFS

职责不重复：

- 共用 Ref-aware 文件读取和 Range/Chunk 能力；
- PVLogFS 是本地低延迟挂载主路径；
- WebDAV 保留远程交换、兼容和技术探针价值；
- 不采用 rclone/WebDAV 作为正式默认 Lower。

### 3.5 Snapshot、Fork 与 Workspace

不合并概念：

- Snapshot 是一个命名、只读 Head 指针；
- Fork 是新 Ref 指向完整相同 HEAD；
- Workspace 是有生命周期、Run 和审阅语义的产品对象；
- 选择集派生不是 Fork。

### 3.6 Workspace App 协议

延期以避免提前规范：

- V0.13 只使用系统诊断执行器；
- 闭环稳定前不冻结第三方镜像 Manifest、UI Proxy 和安装协议；
- 未来 Workspace App v1 单独评审。

## 4. 第一版保留项

必须保留：

- 同目录选择集派生；
- 目录递归；
- 新 lineage 和 Genesis HEAD；
- SQLite Workspace + Ref 原子管理；
- Ref-aware 内部文件服务；
- 固定 HEAD 只读 PVLogFS；
- 本地 COW Upper；
- 非特权容器；
- 一个 Workspace 一个写 Run；
- 提交、Diff、选择性导回、丢弃；
- 所有 Ref 的 GC 可达性；
- 崩溃恢复和挂载清理；
- Workspace internal 应用。

## 5. 第一版删除或延期项

删除或延期：

- 公开 Workspace App 安装协议；
- 任意镜像；
- 网络权限 UI；
- 模型 secret 管理；
- 实时写 PVLogFS；
- 多写者和自动合并；
- 完整来源 Entry 映射；
- 自动把删除应用回 `main`；
- 跨目录选择；
- 远程 Workspace WebDAV 管理；
- Windows/macOS Runtime；
- 多 Agent 和调度市场；
- 复杂空间独占量精确核算。

这些能力不影响“派生—挂载—运行—提交—审阅—导回/丢弃”主闭环。

## 6. 主要风险

### 6.1 FUSE Lower 与 Overlay 兼容

最高风险。不同 Linux 内核对 OverlayFS + FUSE Lower 的支持不同。必须先做探针，并准备
`fuse-overlayfs` 路线。

### 6.2 Upper 语义解释

whiteout、opaque directory、copy-up 和重命名必须被确定性转换为目标状态。第一版允许把
重命名降级为删除加创建，但不能漏掉删除或提交宿主控制文件。

### 6.3 小文件性能

代码项目包含大量 `lookup/stat/open`。PVLogFS 必须在内存中持有 EntryIndex，并共享验证过的
对象缓存，不能让每次系统调用经过 HTTP 或 SQLite。

### 6.4 Runtime 权限

Runtime Daemon 是新增高权限组件。必须使用窄 API、固定路径、固定镜像和严格参数校验，不得
退化成远程 Docker 控制器。

### 6.5 控制状态恢复

SQLite、容器、mount 和临时 Upper 跨越多个系统。所有操作必须有状态机和幂等清理，不允许
启动时看到异常便删除 Upper。

## 7. 仍需由技术探针回答的问题

1. 目标部署内核是否支持 OverlayFS 使用 PVLogFS/FUSE Lower；
2. `fuse-overlayfs` 的性能和 whiteout 表示是否满足提交器；
3. Docker bind mount 对挂载传播需要哪些最小宿主配置；
4. 容器异常和 Runtime 重启后挂载如何可靠识别与卸载；
5. 大量小文件下 EntryIndex、inode 和目录缓存的内存成本；
6. 大文件随机读取时 Chunk 缓存与请求粒度；
7. Upper 容量限制如何在超限时向容器返回稳定错误。

这些问题不改变产品模型，但会决定 Runtime 的具体实现。

## 8. 评审结论

设计逻辑自洽：

- 不可变存储、可变发布点、固定输入和临时写层边界一致；
- Workspace、Run、Ref 和执行器职责明确；
- 最小披露、失败隔离、结果审阅和 GC 生命周期闭环；
- 与现有 File Service、文件管理器和 Docker 部署方向兼容。

冗余已经压缩：

- 不增加独立 Universe 服务；
- 不增加第二套 Workspace 数据库；
- 不复制文件浏览器；
- 不把 WebDAV 当作另一套本地挂载主线；
- 不提前冻结 Workspace App 协议；
- 不做完整来源映射和自动合并。

结论：可以进入“挂载技术探针”阶段。完整施工应在探针验证 Overlay、挂载传播、whiteout 和
异常卸载后再批准。
