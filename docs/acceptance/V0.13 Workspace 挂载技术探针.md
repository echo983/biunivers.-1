# V0.13 Workspace 挂载技术探针

状态：通用挂载、Docker 隔离与真实固定 PVLog HEAD 探针通过

日期：2026-07-30

## 1. 目的

在修改正式 File Service、RefStore 和数据库 Schema 之前，验证 Workspace Runtime 的关键挂载假设：

- 固定文件树可以通过用户态 FUSE 只读暴露；
- COW 层可以使用该 FUSE mount 作为 Lower；
- Lower 保持不变，新增、修改、重命名和删除只落入 Upper；
- Upper 中的删除标记可以被提交器解释；
- merged 可以只作为 `/workspace` bind mount 进入受限容器；
- 正常结束和中断后不遗留 mount、进程或临时目录。

本探针不读取正式 PVLog/S3 数据，也不承担生产实现。

## 2. 实现

```text
crates/workspace-mount-probe/
  Cargo.toml
  src/main.rs

scripts/run-workspace-mount-probe.sh
```

只读夹具包含：

- `/hello.txt`；
- `/docs/readme.md`；
- `/boundary.bin`：按位置确定性生成的 `1 MiB + 1 byte` 文件，用于验证随机读取边界。

COW 路线固定使用 `fuse-overlayfs`。内核 OverlayFS 需要额外权限，不作为无特权探针的前置条件。

Docker daemon 需要穿过用户创建的 FUSE mount，因此目标宿主必须在 `/etc/fuse.conf` 中启用：

```text
user_allow_other
```

探针仅在 `--docker` 模式为 Lower 和 merged 添加 `allow_other`；普通模式不扩大 mount
可见范围。

## 3. 执行

不含 Docker：

```bash
bash scripts/run-workspace-mount-probe.sh
```

包含受限 Docker bind mount：

```bash
sg docker -c 'bash scripts/run-workspace-mount-probe.sh --docker'
```

脚本使用独立临时目录，并在退出信号和失败路径中按 merged、Lower、进程、目录的顺序清理。

- [x] 覆盖 Lower 文件不改变 Lower；
- [x] 新建、重命名和嵌套目录写入落入 Upper；
- [x] 删除 Lower 文件后 merged 不再可见；
- [x] Upper 中存在可解释的删除标记；
- [x] 删除并重建 Lower 目录产生可解释的 opaque 标记；
- [x] 受限容器可读写 `/workspace`；
- [x] 容器中无 `/data`、Docker socket 和网络；
- [x] 容器写入落入 Upper；

## 5. 2026-07-30 实测结果

环境：

```text
Linux 6.12.96+deb13-amd64
FUSE kernel ABI 7.40
libfuse/fusermount3 3.17.2
fuse-overlayfs 1.13-dev
Rust 1.97.1
```

结果：

- 普通探针连续执行通过；
- 受限 Docker 探针连续执行通过；
- TERM 中断后无 mount、探针进程和临时目录残留；
- Lower 文件删除表示为 Upper 中同名字符设备，例如 `readme.md:c`；
- Lower 目录删除并重建表示为 `user.fuseoverlayfs.opaque=79`，其中 `79` 是 ASCII
  `y`；
- Docker 只获得 merged 的 `/workspace` bind mount，不获得 `/dev/fuse`、`/data`、
  Docker socket、network 或 capabilities；
- 容器 root filesystem 为只读，进程使用宿主测试用户 UID/GID。

结论：阶段 1 和阶段 2 的核心挂载假设成立，可以进入真实固定 PVLog HEAD 探针。

## 6. 真实固定 PVLog HEAD

实现：

```text
server/workspace/pvlogMountBridge.ts
server/workspace/pvlogMountProbeCli.ts
crates/workspace-mount-probe/src/pvlog_head.rs
scripts/run-pvlog-head-mount-probe.sh
```

边界：

- Node 桥复用正式 `loadCurrentEntryIndex`、`FileContentStore.readRange` 和对象 FID
  校验；
- 启动时读取两次 `main` Ref，只有 Head 与 revision 未变化才发布只读快照；
- FUSE 只获得固定 EntryIndex 元数据，通过本机 Unix socket 按请求读取字节区间；
- 探针不接受任意 Ref、不写 PVLog、不修改 Schema；
- Unix socket 是探针边界，不在本阶段承诺为最终 Runtime API。

执行：

```bash
sg docker -c 'PATH=/home/edwin/.cargo/bin:$PATH bash scripts/run-pvlog-head-mount-probe.sh'
```

2026-07-30 使用真实 RefStore 和 S3 桶实测：

```text
fixed HEAD: 7661e170ee81fff78da7cf056506359a
revision: 88
entries: 27
EntryIndex load: 174.83 ms（第二轮）
snapshot metadata: 4,534 bytes
largest file: 1,477,115,279 bytes
bridge read requests: 4
bytes read: 32,143
```

验证通过：

- 固定 HEAD 的目录树完整枚举；
- 空文件和普通文件访问；
- 1.47 GB Manifest 文件尾部随机读取；
- `64 MiB` 边界前后各 `4 KiB` 的跨分片 Range 读取；
- 未全量下载最大文件，约 32 KiB 的实际桥读取即可完成所有读取用例；
- S3 Range 响应区间和长度、Manifest 结构继续由现有 File Service 校验；
- 挂载结束后桥容器、Unix socket、FUSE mount 和临时目录全部清理。

首次实测发现并修复了 Unix socket 半关闭时序：桥必须使用 `allowHalfOpen`，等待异步
S3 Range 完成后再关闭响应端。

结论：固定 PVLog HEAD 可以在不物化完整 Workspace 的情况下挂载，目录元数据与文件内容
能够分离加载，阶段 3 的核心 Go 条件成立。

限制：局部 Range 无法独立重算整个 Chunk 的 XXH3 FID，因此该用例没有证明局部字节的完整
Chunk 哈希。正式 PVLogFS 采用“首次访问时完整下载并验证单个 Chunk，再从 cache
`pread`”的策略；参见 PVLogFS 与 Compute Runtime 局部设计。

## 7. Go/No-Go

以下条件全部满足后才进入真实固定 PVLog HEAD：

1. 无特权 FUSE + COW 在目标 Linux 环境稳定工作；
2. 容器不需要 `/dev/fuse`、mount capability 或 Docker socket；
3. Upper 能确定性表达本阶段覆盖的文件系统变化；
4. 脚本可重复运行且异常路径能够恢复；
5. 已记录 whiteout/opaque directory 的实际表示，并据此冻结提交器输入规范。
