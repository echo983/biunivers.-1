# 浏览器云端个人桌面 V0.2 需求方案

状态：草案

版本主题：第三方静态应用生态

前置版本：V0.1

## 1. 目标

V0.2 把已经定义的第三方静态应用规范落成可用产品：

> 管理员可以从公开 GitHub 仓库检查并安装一个符合 Biunivers Static App Protocol v1 的应用，Biunivers 固定版本、提供静态文件、注册桌面入口，并支持配置、更新、停用和卸载。

首版重点是建立一条可靠、容易理解的完整链路，不建设通用应用商店或插件运行时。

## 2. 目标用户

### 桌面管理员

部署并管理自己的 Biunivers，能够：

- 安装公开 GitHub 仓库中的静态应用；
- 在安装前看到应用身份、版本、来源和公开配置；
- 管理已经安装的应用；
- 在安装或更新失败时继续使用当前桌面。

### 第三方开发者

依据 V1 开发包交付：

- 根目录 `index.html`；
- `biunivers.app.json`；
- `BIUNIVERS_APP_PROTOCOL_V1.md` 原文；
- `LICENSE`；
- 可以直接运行的静态资源。

开发者不需要理解 Biunivers 内部 React store、窗口库或服务端实现。

## 3. 核心用户流程

### 3.1 检查应用

1. 管理员打开内建“设置”；
2. 进入“应用管理”；
3. 输入公开 GitHub 仓库地址和 branch、tag 或 commit；
4. Biunivers 获取并检查仓库；
5. 页面展示：
   - 应用名称和 ID；
   - 版本；
   - 描述和许可证；
   - GitHub 来源；
   - 解析后的 commit SHA；
   - 需要填写的公开配置；
   - 明确的校验错误或警告。

检查成功不等于已经安装。

### 3.2 安装应用

1. 管理员填写 manifest 声明的配置；
2. 确认这些值会发送到浏览器，不得包含 secret；
3. 发起安装；
4. Biunivers 验证配置并完成文件落盘；
5. 最后注册 APP；
6. 应用出现在桌面或应用菜单；
7. 用户打开应用，Biunivers 在窗口中加载其 `index.html`。

首次安装失败时，桌面不得出现损坏的应用入口。

### 3.3 更新应用

1. 管理员为已安装应用输入新的 ref；
2. Biunivers 按首次安装标准重新检查；
3. 确认 `appId` 不变；
4. 管理员确认新配置；
5. 新版本安装成功后切换 APP；
6. 已经打开的旧窗口不被强制替换；
7. 关闭后重新打开使用新版本。

更新失败时继续使用旧版本。

### 3.4 停用和启用

- 停用后应用从桌面注册表移除，但保留文件、配置和安装记录；
- 启用不重新访问 GitHub，直接恢复当前已安装版本；
- 停用时关闭或提示关闭正在运行的应用窗口。

### 3.5 卸载

1. 管理员看到要删除的应用、版本和服务器端数据；
2. 明确确认；
3. Biunivers 阻止继续启动；
4. 关闭对应窗口；
5. 移除 APP 注册、安装记录、配置和应用文件；
6. 界面说明浏览器端存储不一定能由服务器完全清除。

## 4. 功能范围

### 4.1 必须实现

- 公开 `github.com` 仓库；
- 仓库根目录应用；
- branch、tag 或 commit 输入；
- ref 解析并固定完整 commit SHA；
- Manifest Schema 校验；
- 协议版本和协议原文校验；
- `LICENSE`、`index.html` 和 icon 校验；
- 拒绝符号链接和异常路径；
- 安装大小限制；
- 安装过程中不执行仓库代码；
- 根据 manifest 生成公开配置表单；
- 本地持久化应用文件、配置和安装记录；
- 动态 APP 表；
- iframe 运行已安装应用；
- 更新、停用、启用和卸载；
- 管理操作认证；
- 桌面 origin 与第三方应用 origin 分离；
- 基本错误、加载和空状态；
- 失败时保留既有可用状态。

### 4.2 保留现有能力

- 编译期内建设置与关于；
- 管理员提供的传统 iframe 和 external 配置；
- 桌面图标、应用菜单和任务栏；
- 窗口拖动、缩放、最小化、最大化、还原和关闭；
- 本地桌面状态恢复；
- iframe “在新标签页打开”。

### 4.3 明确不做

- GitHub 私有仓库；
- GitHub 以外的安装源；
- monorepo 子目录；
- 安装期间执行构建；
- 应用专属后端和数据库；
- secret 配置；
- 自动更新；
- 应用商店、评分或审核；
- 发布者签名；
- 应用依赖解析；
- 多实例安装；
- Host API；
- 应用间调用、文件关联和资源交换；
- 完整 capability 权限系统；
- 多用户和角色系统。

## 5. 业务规则

### 5.1 应用身份

- 一个 `appId` 在一个 Biunivers 实例中只能安装一次；
- `appId` 必须与 GitHub owner 匹配；
- 更新不能改变 `appId`；
- 第三方应用不能使用任何内建应用 ID；
- 第三方应用始终注册为 `iframe`，不能成为 `internal`。

### 5.2 版本

- 用户输入的 ref 只用于定位；
- 安装记录必须保存解析后的完整 commit SHA；
- 运行时不继续跟随 branch 或 tag；
- 用户必须显式发起更新；
- SemVer 用于展示，不替代 commit 身份。

### 5.3 配置

- 只接受 manifest 声明的 key；
- 缺失值先使用默认值；
- 必填项没有值时不能安装；
- 修改配置后重新打开应用生效；
- 所有配置都是浏览器可见数据；
- 管理界面必须明确提示不能填写 secret。

### 5.4 协议版本

- 宿主维护显式支持的应用协议和 manifest 版本列表；
- V0.2 只支持 `biunivers.static-app/1` 和 manifest `1`；
- 是否长期向后兼容留待未来决定；
- 不支持的版本必须明确拒绝，不能猜测兼容。

### 5.5 应用来源

- V0.2 只接受规范的 `https://github.com/<owner>/<repo>`；
- 仓库必须公开；
- 安装服务不能被用作任意 URL 或局域网代理；
- 已安装文件本地可用时，GitHub 故障不影响应用运行。

## 6. 安全和信任底线

V0.2 不建设完整沙箱或供应链系统，但必须做到：

- 管理 API 不能匿名修改；
- 管理凭据不能传入第三方 iframe；
- 第三方 iframe 与桌面使用不同 origin；
- 安装器不执行仓库内容；
- 下载和解包有文件数、单文件、总大小和超时限制；
- 防止路径穿越和符号链接逃逸；
- 静态服务不暴露 `.git`、dotfile、manifest 和协议文档；
- 第三方 manifest 不能影响 `internal` 映射；
- 安装、更新和卸载记录基本审计信息。

V0.2 仍以管理员主动安装公开开源应用为信任前提，不承诺应用经过官方安全审核。

## 7. 体验要求

### 安装界面

- 一次只展示当前需要用户处理的信息；
- 检查阶段和安装阶段明确分开；
- 表单标签来自 manifest，并显示类型、默认值和说明；
- 错误必须指出具体文件或字段；
- 长操作显示当前阶段，不能只显示无限转圈；
- 重复点击不能产生两个相同安装。

### 应用管理列表

每项至少显示：

- icon 和名称；
- app ID；
- 版本；
- 来源仓库；
- 当前 commit 短 SHA；
- active 或 disabled；
- 配置、更新、停用/启用和卸载操作。

### 降级行为

- 管理服务或动态 APP 表不可用时，桌面仍能打开内建设置和关于；
- 传统配置中其他有效 iframe/external 继续可用；
- 单个已安装应用损坏不能阻止整个桌面启动。

## 8. 验收场景

### A. 安装最小示例

给定开发者包中的最小应用发布到公开 GitHub 仓库：

1. 输入仓库和 tag；
2. 检查成功；
3. 填写问候语；
4. 安装成功；
5. 应用出现在桌面；
6. 打开后显示配置值；
7. 调整尺寸、最小化、还原和关闭均正常。

### B. 拒绝不兼容仓库

以下任一情况必须在注册 APP 前失败：

- 缺少根目录 `index.html`；
- 缺少或修改协议原文；
- Manifest 不合法；
- 缺少 LICENSE 或 icon；
- owner 与 app ID 不匹配；
- 协议版本不支持；
- 包含危险路径或符号链接；
- 超过部署大小限制。

### C. 更新失败回退

1. 已安装 V1 可正常打开；
2. 选择一个不合法的新 ref 更新；
3. 更新失败并显示原因；
4. APP 仍指向原 commit；
5. 原版本仍可打开。

### D. 生命周期

- 停用后桌面不再显示应用；
- 启用后无需 GitHub 即可恢复；
- 配置修改后重新打开读取新值；
- 卸载后 APP 消失且服务器端文件进入清理流程。

### E. 特权边界

- 运行时配置不能创建新的 internal 应用；
- 安装 manifest 不能覆盖设置或关于；
- 第三方应用 origin 无法访问桌面 DOM；
- 第三方应用无法调用管理 API 的授权操作。

## 9. 成功标准

V0.2 完成需要同时满足：

- 核心用户流程全部通过；
- 最小示例完成真实 Docker 端到端安装；
- 单元、集成和桌面 E2E 测试通过；
- 现有 V0.1 窗口体验无回归；
- Docker 数据卷重启后安装记录和应用仍存在；
- 安装和更新失败不会破坏当前 APP 表；
- 文档、实现和开发者包字段一致；
- 经过参考实现验证后，决定是否把 V1 协议从草案提升为正式。
