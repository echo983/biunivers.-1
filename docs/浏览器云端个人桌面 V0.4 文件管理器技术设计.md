# 浏览器云端个人桌面 V0.4 文件管理器技术设计

状态：设计基线

对应需求：internal 文件管理器

## 1. 总体结构

```text
system.files React internal 应用
  │
  ├─ 窗口实例 bootstrap
  │    └─ FileCapabilityRegistry(appId = system.files)
  │
  ├─ 现有 Host File API
  │    ├─ 目录列表
  │    ├─ 文件/待保存句柄
  │    └─ 一次性 GET/PUT transfer
  │
  └─ 新增 Internal File Manager API
       ├─ 新建目录
       ├─ 重命名/移动 Entry
       └─ 移除 Entry
            │
            └─ FileSystemTransactions
                 └─ PVLog objects → RefStore CAS
```

前端不直接导入服务端存储模块。服务端内部管理接口不接受管理员 token，也不向 iframe 暴露；
权限来自可信 Desktop Origin 与绑定 `system.files` 的短期窗口实例 token。

## 2. internal 注册

新增默认应用：

```text
id: system.files
kind: internal
desktop: true
pinned: true
```

`AppRenderer` 只对这个固定 ID 渲染 `FileManagerApp`。服务端 reserved app IDs、客户端 registry
冲突处理和测试同步加入 `system.files`。

## 3. 窗口实例

现有 `POST /api/v1/host/instances` 扩展为接受编译期 internal 文件应用 allowlist。第三方应用
仍必须来自已安装且 active 的 APP 表。

`FileManagerApp` 挂载时用随机 `windowInstanceId` 创建实例，卸载时关闭实例。File Service
disabled/offline 返回现有 `HOST_API_UNSUPPORTED`，前端显示不可用状态。

internal 管理服务对每次请求调用：

```text
requireDesktopOrigin
→ 读取 Biunivers-Instance token
→ FileCapabilityRegistry.authorizeInstance
→ appId === system.files
```

## 4. API

复用：

- `GET /api/v1/host/files`
- `POST /api/v1/host/handles`
- `POST /api/v1/host/save-handles`
- `POST /api/v1/host/transfers`
- `DELETE /api/v1/host/handles/:handleId`
- `/api/v1/files/transfers/:transferId`

新增：

```text
POST   /api/v1/internal/files/directories
PATCH  /api/v1/internal/files/entries/:entryId
DELETE /api/v1/internal/files/entries/:entryId
```

创建目录请求：

```json
{
  "parentEntryId": "32 lowercase hex",
  "name": "Documents",
  "expectedRevision": 3
}
```

移动或重命名请求：

```json
{
  "newParentEntryId": "32 lowercase hex",
  "newName": "notes",
  "expectedRevision": 4
}
```

移除请求：

```json
{
  "recursive": true,
  "expectedRevision": 5
}
```

成功响应包含新的 `revision` 和受影响的稳定 `entryId`。根 Entry 不允许移动、重命名或移除。
名称、父目录、循环移动、重名和非空目录规则由服务端验证。

`expectedRevision` 与当前 Ref 不一致时返回 `FILE_VERSION_CONFLICT`（HTTP 409），即使目标 Entry
仍存在也不自动重试。

## 5. 内部事务服务

新增 `InternalFileManagerService`，依赖：

- `ImmutableObjectRepository`
- `SqliteRefStore`
- `FileSystemTransactions`
- `FileCapabilityRegistry`

服务在调用事务前重新构建当前 EntryIndex，并验证：

- instance 属于 `system.files`；
- revision 精确匹配；
- parent 为存在的目录；
- Entry 存在且不是根；
- 新名称符合统一名称规则；
- 目标目录内没有同名 Entry；
- 目录不能移动到自身或后代；
- 非递归移除不能作用于非空目录。

校验与 Ref CAS 之间仍可能竞争；底层 `REF_CONFLICT` 统一映射为
`FILE_VERSION_CONFLICT`。

## 6. 上传与下载

上传复用待保存句柄：

```text
选择本机 File
→ issueSaveHandle(parent, name)
→ issue PUT transfer
→ fetch PUT File.stream/body
→ 成功后刷新目录
```

内容上传完成并发布 Ref 前不显示新 Entry。V0.4 第一版同名文件不自动覆盖，提示用户先重命名
或移除目标。

下载复用只读句柄和 GET transfer。浏览器通过认证 fetch 读取响应并触发本地下载。第一版允许
浏览器生成 Blob；超大文件的纯流式本地落盘属于后续体验优化。

File transfer CORS/Origin 校验增加一个窄例外：当 transfer identity 的 `appId` 为
`system.files` 时只接受精确 Desktop Origin；其他应用仍只接受各自独立 App Origin。

## 7. 前端状态

`FileManagerApp` 保持窗口本地状态：

- instance bootstrap 状态；
- 当前目录和面包屑栈；
- 当前 listing 与 revision；
- 单个选中 Entry；
- 当前对话框；
- 上传/下载操作状态；
- 可恢复错误。

不把 Entry 列表或 instance token 写入 localStorage。任何成功 mutation 后重新读取目录；
发生冲突时清除选择、刷新并显示提示。

## 8. 历史兼容

V0.4 不新增“永久删除”。PVLog `RemoveEntry` 只使 Entry 在新 checkpoint 中不可见，父 Head
历史仍保留旧 checkpoint 和内容引用。

文件管理器不得把 revision 当作可编辑版本号，也不得提供 Ref 倒退。后续版本历史服务可以：

1. 按 Head/revision 重建只读 EntryIndex；
2. 从旧内容另存副本；
3. 把旧状态作为新 revision 发布；
4. 创建命名快照并纳入 GC 根。

## 9. 安全与失败

- internal 路由不启用 CORS；
- Origin/Fetch Metadata 检查在解析业务参数前完成；
- Entry ID 不授予权限，必须同时持有 internal instance token；
- 错误不返回 FID、S3 Key、Ref 或服务器路径；
- 文件内容不经过 JSON；
- 失败上传、失败事务和 CAS 冲突不改变旧 Ref；
- File Service offline 时不构造部分可用的管理服务。

## 10. 测试

- internal 默认注册与冲突保护；
- internal instance bootstrap 和第三方拒绝；
- 服务端目录操作的正常、重名、循环、根保护、非空目录和 stale revision；
- internal 路由 Origin、token、appId 与错误映射；
- 上传、下载和 disabled/offline 前端状态；
- React 基础交互：导航、新建、重命名、移动、移除确认和刷新；
- Docker + R2 人工验收及重启恢复。
