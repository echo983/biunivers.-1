# 浏览器云端个人桌面 V0.14 Runtime Proxy、网络与 iframe 局部设计

日期：2026-07-31  
状态：施工候选  
基线：V0.14-B Lifecycle 阶段验收通过

## 1. 目标与非目标

V0.14-C 要把已经可运行的 BWA 变成浏览器桌面内可打开、可管理的产品能力：

```text
Desktop Window
→ Manager internal 启动/故障页
→ 稳定 Instance Origin
→ Runtime Proxy
→ 当前 Run 的 Container :8080
```

第一版必须闭环：

- 容器不直接发布宿主或局域网端口；
- 每个 Instance 具有稳定且隔离的浏览器 origin；
- 普通 HTTP、Range、流式响应和 WebSocket 可代理；
- 未授权浏览器不能仅凭 Instance ID 访问；
- 停止、崩溃、更新和重建不会改变 iframe URL；
- 容器不可用时显示宿主故障页；
- Manager internal 页面可完成必要控制。

第一版不实现多用户 RBAC、外部身份提供者、任意 ingress、TLS 自动签发、Service Mesh、
逐域名出站 ACL 或通用容器编排。

## 2. 组件边界

```text
Desktop Server :8080
├── Manager internal UI
├── BWA 控制 API
└── 生成一次性 bootstrap ticket

App/Proxy Server :8081
├── 现有静态 App Host
└── BWA Runtime Proxy

Compute Runtime daemon
├── Docker bridge 管理
├── Container lifecycle
└── 当前 Run endpoint 查询

BWA Container
└── 0.0.0.0:8080
```

Docker socket、任意 Docker 参数、容器 IP、Run capability 和 secret 不进入浏览器。

## 3. 稳定 Instance Origin

沿用 `appSpecificOrigin()` 的哈希子域思想，为 BWA 增加独立标签：

```text
bwaOriginLabel(instanceId) = bwa-<sha256(instanceId) 前 40 hex>
```

示例：

```text
Desktop        http://localhost:8080
App base       http://localhost:8081
BWA Instance   http://bwa-<hash>.localhost:8081/
```

路由只由请求 Host 映射 Instance，不接受 URL 中的 repository、Run ID、Container ID 或 IP。
每个 Instance 获得不同 origin，因此 Cookie、LocalStorage、IndexedDB、Service Worker 和
浏览器缓存不会在不同 Instance 间共享。

Instance 的 Workspace Fork 后会产生新 Instance ID 和新 origin。镜像更新、保存重启和新
Run 不改变 origin。

## 4. 浏览器访问授权

稳定 URL 不是 bearer capability。首次打开采用单次 bootstrap：

```text
Desktop 同源控制请求
→ Manager 校验当前用户可打开 Instance
→ 生成 256-bit 随机 ticket，TTL 30 秒，单次使用，只存内存
→ iframe 导航到 BWA Origin /__biunivers/bootstrap?t=<ticket>
→ Proxy 原子消费 ticket
→ Set-Cookie: __Host-biunivers-bwa=<随机会话>; HttpOnly; Path=/; SameSite=None; Secure; Partitioned
→ 303 到 /
```

生产 HTTPS 增加 `Secure`；localhost HTTP 开发环境不设置 `Secure`。bootstrap 响应使用
`Cache-Control: no-store`、`Referrer-Policy: no-referrer`，票据和值不得进入普通访问日志。

会话：

- 绑定一个 Instance；
- 随机 256-bit，只存 Manager 内存；
- 空闲 12 小时失效；
- Application 停用、Instance 删除或用户显式撤销时立即失效；
- Instance 暂停/重启时保留，使同一 iframe 可在恢复后刷新；
- 不注入 BWA 上游请求头，不向应用代码暴露值。

上游 `Set-Cookie` 允许用于应用自身状态，但 Proxy 拒绝或改名保留前缀
`__Host-biunivers-`，防止覆盖宿主会话 Cookie。

## 5. Docker 网络

Compute Runtime 管理固定 bridge：

```text
biunivers-bwa
├── BWA 容器可以访问网络路由可达目标
├── 宿主 Runtime Proxy 可访问容器 :8080
├── 容器不使用 host network
└── 不使用 docker publish/-p
```

BWA OCI plan 从 `network=none` 改为 `--network biunivers-bwa`。固定诊断 Executor 继续
`network=none`，不放宽。

Runtime 新增窄查询：

```text
resolveBwaEndpoint(runId)
→ { address, port: 8080, runtimeIdentity }
```

Runtime 必须同时校验：

- Run 为 BWA 且控制/本地状态均为 RUNNING；
- 容器身份等于 manifest 的 `runtimeIdentity`；
- endpoint 来自固定 `biunivers-bwa` 网络；
- 地址是 Docker inspect 返回的单个有效 IP；
- 端口永远为 8080。

该结果只经 `0600` Unix socket 返回 Manager，不持久化到 RefStore，不返回浏览器。

第一版明确以 Linux Docker bridge 为部署基线。未来若适配不能从宿主访问 bridge IP 的
Runtime，只替换 endpoint adapter，不改变浏览器协议和 Instance URL。

## 6. Proxy 目标解析

每次新请求按以下顺序解析，不能只相信旧缓存：

```text
Host → Instance
→ Application enabled
→ 浏览器会话授权
→ 查找唯一 RUNNING BWA Run
→ Runtime resolveBwaEndpoint
→ 代理到 http://<address>:8080
```

endpoint 可按 `runId + runtimeIdentity` 短期缓存；Instance 当前 Run 改变、Runtime 查询失败
或连接失败时立即失效。缓存不能跨 Run 复用。

## 7. HTTP 代理

第一版透明转发所有标准 HTTP 方法和流式 body/response，保留：

- URL path 与 query；
- `Range`、`If-*`、`ETag`、`Content-Range`；
- 准确状态码和响应流；
- SSE 和长响应。

必须移除 hop-by-hop headers，并重新生成上游 `Host`。不得转发浏览器 Cookie 中的
Biunivers 保留会话；应用自身 Cookie 可单独转发。增加固定：

```text
X-Forwarded-Proto
X-Forwarded-Host
X-Forwarded-Prefix=/
```

不注入用户身份、admin token、Instance token、Workspace ID、Run ID 或 secret。

第一版不重写 HTML、JavaScript、绝对 URL、CSP 或应用 Cookie Domain。BWA 必须以 `/` 为
根运行，不能依赖容器 IP。应用必须允许被 Biunivers Desktop Origin iframe 嵌入，不得返回
冲突的 `X-Frame-Options` 或 `frame-ancestors`。

## 8. WebSocket

App/Proxy Server 处理 `upgrade`：

1. 精确校验 BWA Host；
2. 校验会话 Cookie；
3. 解析当前 endpoint；
4. 转发握手和双向字节流；
5. Instance 停止或上游断开时关闭连接。

不实现消息级解析、重连、广播和 Socket.IO 语义适配。重连由应用负责。

## 9. 健康与故障页

`GET /health` 是 BWA 必需接口，返回任意 `2xx` 即就绪。Manager 启动页最多等待 30 秒，
采用固定短间隔探测，不无限等待。

Proxy 只为 HTML 顶层/iframe 导航返回宿主 HTML 故障页；API、媒体、Range 和 WebSocket 返回
结构化/协议原生错误，避免把 HTML 混入业务流：

| 状态 | HTTP | 表现 |
|---|---:|---|
| 未授权/会话失效 | 401 | 宿主“重新打开应用”页 |
| Application disabled / Instance 不存在 | 404 | 宿主不可用页 |
| STOPPED | 503 | 宿主启动入口或重新打开提示 |
| STARTING / health 未就绪 | 503 + `Retry-After` | 启动中页 |
| FAILED / CONFLICT Upper | 409 | 宿主恢复处置页 |
| 上游连接失败 | 502 | 运行故障页并触发一次 endpoint 失效 |

故障页不回显容器 IP、Docker 错误、secret、内部路径或原始异常栈。

## 10. BWA iframe Protocol v1

V1 是最小嵌入与运行约定，不复制 Static App Protocol：

- OCI label `io.biunivers.workspace-application.protocol=1`；
- HTTP 监听 `0.0.0.0:8080`；
- `GET /` 提供图形界面，`GET /health` 提供就绪检查；
- 页面适应 iframe 尺寸，不访问父 DOM，不导航 `top`；
- 需要 `postMessage` 时必须校验精确 origin、`event.source` 和消息 Schema；
- 关闭 iframe 不等于停止 Instance；
- Workspace 持久性只在宿主成功提交后成立；
- V1 不提供文件遍历、Docker、宿主 shell 或 admin API；
- 浏览器权限仍由 iframe `allow`、CSP 和用户策略决定。

V1 不强制 ready postMessage、菜单 API、主题 API、窗口控制 API或 Host API 新方法。健康检查和
iframe load 已足够支撑第一版启动体验。

## 11. Manager internal 控制面

第一版提供一个编译期 internal 系统应用，而非让 BWA 自己管理自身：

- Application：安装、启停、更新、回退、source 链接和 OCI 描述；
- Instance：创建、启动、停止、保存重启、打开、环境变量和 secret 名称；
- Workspace：绑定信息、Fork 入口和打开 Workspace 管理器；
- ERROR：异常 Upper 的提交或丢弃；
- 启动页：进度、health 超时和重试。

不在第一版提供 Docker 参数编辑器、Compose 表单、日志终端、容器 shell、资源监控大盘或
通用任务调度器。

- 浏览器只凭稳定 Instance Origin 无法访问，bootstrap 后可访问；
- 两个 Instance origin、Cookie 和浏览器存储隔离；
- 容器无 published port，代理可访问固定 8080；
- 保存重启前后 iframe URL 不变；
- HTTP POST、流式响应、Range、SSE 和 WebSocket 通过；
- 停止、崩溃、更新和异常 Upper 显示确定性宿主页；
- 管理界面可完成安装到卸载的用户闭环；
- Static App、Resource Session、Wormhole 和 V0.13 Runtime 不退化。
