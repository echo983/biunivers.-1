# 浏览器云端个人桌面 V0.4 文件管理器需求方案

状态：设计基线

版本主题：internal 文件管理器

前置版本：`v0.3.0`

## 1. 目标

V0.4 提供一个基础可用的 `system.files` internal 应用，让用户无需借助第三方记事本的文件
选择器即可管理 Biunivers File Service 中的当前文件树。

文件管理器是高权限系统界面，但不是存储实现。它只能调用 File Service 的内部语义接口，
不能访问 S3 凭据、对象 Key、FID、Head、Segment、Checkpoint、Manifest、SQLite 或
RefStore 文件。

## 2. 第一版闭环

用户可以：

1. 从桌面或任务栏打开“文件”；
2. 浏览根目录和子目录，并通过面包屑返回上级；
3. 查看名称、类型、大小和修改时间；
4. 新建目录；
5. 重命名文件或目录；
6. 把文件或目录移动到另一个目录；
7. 经明确确认后，从当前文件树移除文件或目录；
8. 从本机上传文件；
9. 把文件下载到本机；
10. 在并发状态变化时收到冲突提示并刷新，而不是静默覆盖。

File Service 未配置或离线时，文件管理器仍可打开，但只显示明确的不可用状态，不影响桌面和
应用管理。

## 3. internal 边界

`system.files` 必须加入编译期 internal 白名单，不能由运行时配置或第三方 manifest 创建、
覆盖或替换。

它拥有普通第三方应用没有的权限：

- 浏览完整当前文件树；
- 创建目录；
- 重命名、移动和移除任意非根 Entry；
- 为上传和下载签发文件 capability。

它仍然没有：

- 管理员 token；
- S3 或 RefStore 凭据；
- 任意 FID 读取接口；
- 修改或删除不可变协议对象的能力；
- 绕过 File Service 事务和校验的能力。

所有管理请求同时要求：

- 请求来自精确 Desktop Origin；
- Fetch Metadata 符合同源页面；
- 有效窗口实例 token；
- token 的 `appId` 必须为 `system.files`。

第三方 App Origin 即使知道路由和 Entry ID，也不能调用这些接口。

## 4. PVLog 语义

文件管理器只展示当前 revision，但所有修改继续通过 PVLog 产生新 revision：

- 新建目录产生新 revision；
- 重命名和移动保持 Entry ID 稳定；
- 移除只改变当前文件树，不物理删除历史对象；
- 上传新文件在内容完整写入后才发布 Entry；
- 操作失败时旧 revision 仍然有效。

每个破坏性或结构性操作必须携带界面读取时的 `expectedRevision`。如果 Ref 已前进，服务返回
冲突，客户端刷新目录并要求用户重新确认。

未来恢复旧版本时必须发布更高的新 revision，不能把 Ref 静默倒退。V0.4 第一版不提供版本
历史、回收站或快照 UI，但不得破坏这些后续能力。

## 5. 交互要求

- 基础可用优先，不追求高视觉设计；
- 默认列表视图，目录优先、名称稳定排序；
- 单击选择，双击目录进入；
- 文件双击暂不定义“打开方式”，避免私有文件关联；
- 重命名、新建目录和移动使用简单对话框；
- 移除目录时明确提示是否递归及其影响；
- 上传显示进行中、成功或失败状态；
- 下载失败显示可理解错误；
- 键盘焦点、按钮名称和选中状态可辨识；
- 窗口缩小到最小尺寸时仍可完成核心操作。

## 6. 不包含

- 用第三方应用打开文件；
- 文件类型关联或 Resource Exchange；
- 版本历史、时间线、快照管理和恢复；
- 回收站产品语义；
- 复制、分享、收藏、标签和全文搜索；
- 拖放移动；
- 多选批处理；
- GC 删除；
- 多用户权限与共享目录。

## 7. 验收条件

- `system.files` 不能由 managed APP 或传统配置覆盖；
- File Service 关闭时显示降级状态；
- 文件树浏览、新建目录、重命名、移动、移除、上传和下载闭环通过；
- 重命名和移动后 Entry ID 不变；
- 目录递归移除不物理删除不可变对象；
- stale revision 操作返回冲突且不改变当前树；
- 第三方 Origin 无法调用 internal 管理接口；
- 上传失败不创建可见空文件；
- 容器重启后最终文件树和文件内容保持一致；
- 文档、实现和自动化测试一致。
