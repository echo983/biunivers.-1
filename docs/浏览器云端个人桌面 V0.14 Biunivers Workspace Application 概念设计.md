# 浏览器云端个人桌面 V0.14 Biunivers Workspace Application 概念设计

状态：第三版，概念冻结候选

日期：2026-07-31

基线：`v0.13.0`

第三版继承第二版对 Task/Session/Service 类型、复杂自动重启、完整 OCI
Distribution 客户端和 Manager 多进程预设的删减；进一步冻结镜像操作权限边界、
长期运行状态保存、启动意图、全 Instance 一致更新和真实网络能力。

## 1. 目标

V0.13 已打通与具体应用无关的 Workspace Runtime：

```text
main 选择集
→ 派生 Workspace
→ 固定 PVLog Head
→ PVLogFS
→ COW overlay
→ OCI Run
→ 原子提交
→ Diff
→ 选择性导回 main
```

V0.14 的问题不再是技术可行性，而是如何把已有原语组合成可安装、可呈现、
可长期管理的容器应用系统。

## 2. 核心定义

**Biunivers Workspace Application**（简称 **BWA**）是：

> 以 OCI 镜像交付、自带 HTTP 图形界面、以 Workspace 承载主要持久状态，并由
> Biunivers Workspace Application Manager 统一安装、配置、运行和代理访问的容器应用。

BWA 不是 Docker Compose 包，也不是一份可由应用自由声明宿主权限的表单。
第一版一个 BWA 只对应一个 OCI 镜像。

## 3. 应用身份与安装来源

长期应用身份使用规范化 OCI repository：

```text
ghcr.io/<owner>/<image>
```

实际安装和运行的版本必须固定 digest：

```text
ghcr.io/<owner>/<image>@sha256:<digest>
```

身份分层：

```text
OCI repository   长期应用身份
OCI digest       不可变安装版本
OCI tag          只用于发现更新
Run ID           一次执行身份
Container ID     临时实现细节
```

第一版安装来源限定为公开 GHCR，但数据模型使用通用 OCI registry/repository
概念，不将长期协议永久绑定到 GitHub。

## 4. OCI 元信息

应用作者使用标准 OCI annotations 提供应用介绍和外部文档：

```text
org.opencontainers.image.title
org.opencontainers.image.description
org.opencontainers.image.source
org.opencontainers.image.version
org.opencontainers.image.revision
org.opencontainers.image.licenses
org.opencontainers.image.created
```

第一版强制提供：

```text
org.opencontainers.image.description
org.opencontainers.image.source
```

Manager 在安装和管理界面展示 description、source、repository、digest 及可用的
版本信息。

- description 只按纯文本呈现；
- source 第一版只接受 HTTPS；
- 外部链接使用 `noopener noreferrer`；
- 界面明示说明这些内容由应用作者提供；
- source 和开源不构成 Biunivers 的安全审核或背书；
- digest 才是实际已安装代码的不可变身份。

## 5. 最小协议声明

不使用 Compose 式 Manifest。镜像通过少量 OCI label 表示协议兼容，具体 label
名称在规范评审中冻结，概念形式为：

```text
io.biunivers.workspace-application.protocol=1
```

其余运行约定由协议固定：

```text
OCI 启动入口      镜像 Entrypoint/Cmd
HTTP 监听地址    0.0.0.0
HTTP 端口        8080
界面入口         GET /
健康检查         GET /health
Workspace          /workspace
临时目录          /tmp
```

固定 8080 以保持非 root、零 capabilities 和跨 OCI Runtime 兼容，不要求
`CAP_NET_BIND_SERVICE`。

## 6. 界面要求

每个可安装 BWA 必须在容器 8080 端口提供可用 HTTP 图形界面。宿主不关注
它使用什么语言、框架或进程结构。

界面通过 iframe 呈现，并遵守待定义的 **Biunivers Workspace Application
Protocol v1**。它可以沿用 Biunivers App Protocol v1 的消息安全原则，但两者
不是同一协议：

- iframe 与桌面宿主隔离 origin；
- 不能直接访问宿主 DOM；
- `postMessage` 校验 origin、source 和消息 Schema；
- 应用不能伪造宿主授权界面；
- 全屏、剪贴板等浏览器权限由宿主决定；
- iframe 关闭不自动等于停止后台 Run。

Biunivers 目前没有通用 CLI，因此无界面的纯执行器不能作为独立 BWA 直接
交付给普通用户。后台逻辑可以是 BWA 内部组成部分。

BWA 未运行时无法提供自身 HTTP 界面，因此 Manager 必须同时提供不依赖
BWA 容器的 internal 宿主控制界面。桌面打开流程为：

```text
桌面图标
→ Manager 宿主页
→ 检查 Application/Instance
→ 必要时创建并启动 Run
→ 显示启动进度
→ GET /health 就绪
→ 切换到 BWA iframe
```

配置、启动、停止、启动失败、异常 Upper 处置、更新和卸载始终由宿主
控制界面提供。BWA 业务页面不负责保证自身容器存在。

## 7. Workspace 状态模型

Workspace 是 BWA 的主要持久业务状态：

```text
程序与界面       OCI image@digest
已提交业务状态   Workspace Ref/Head
未提交变化       Run Upper
普通启动配置     Manager 数据库
Secret           Manager 敏感变量存储
执行记录          Workspace Run
执行载体          OCI Container
```

容器不是应用实例，容器 ID 也不得成为长期应用身份。容器可以销毁和重建，
而 Workspace、实例配置与运行记录保持稳定。

## 8. 平行状态与默认体验

同一 BWA 可以绑定多个 Workspace，形成互不影响的平行状态：

```text
BWA Application
├── Instance A → Workspace A
├── Instance B → Workspace B
└── Instance C → Workspace C
```

同一 Head 可以低成本 Fork 为多个单写世界线，用于并行尝试、长期服务状态和
锁冲突隔离。结果使用已有 Diff 与选择性导回回收。

但普通用户的默认心智模型仍应接近传统桌面：

```text
安装应用
→ 首次打开时创建或选择一份状态
→ 点击打开
→ 继续使用上次状态
```

Instance 可以保持为内部术语。只有用户显式选择“创建副本”或“从此分支”
时，界面才显示平行状态。

安装 Application 时不无条件创建 Workspace。首次打开时，Manager 提供三种来源：

1. 创建空白 Workspace（默认主操作）；
2. 从现有 Workspace Fork；
3. 从 main 选择集派生。

用户确认后才创建 Instance 并绑定 Workspace，避免安装即产生无用状态。

## 9. 持久实体

概念数据模型：

```text
BwaApplication
├── applicationId = OCI repository
├── installedDigest
├── previousDigest | null
├── protocolVersion
├── displayMetadata
└── enabled

BwaInstance
├── instanceId
├── applicationId
├── workspaceId
├── desiredState
├── startupPolicy = MANUAL | ON_OPEN | AUTOMATIC
├── ordinaryEnvironment
└── sensitiveEnvironment

WorkspaceRun
├── runId
├── workspaceId
├── executorDigest
├── inputHead
├── state
└── outputHead
```

关系：

```text
Application 1 ── N Instance
Instance    1 ── 1 Workspace
Instance    1 ── N Run
Run         1 ── 0/1 当前 Container
```

Instance 不把 `currentRunId` 或另一份持久运行 `state` 作为第二份权威真相。活动
Run 以 Workspace Run 记录和已有写租约为事实来源；Manager 保存用户的
`desiredState`，并在启动和恢复时对账派生 `observedState`。

## 10. Workspace Application Manager

**Biunivers Workspace Application Manager** 是 BWA 的统一系统控制面：

```text
Workspace Application Manager
├── Registry
├── Lifecycle
├── Runtime Proxy
└── Internal UI
```

Manager 负责：

- OCI repository 注册、digest 固定、安装、更新、停用和卸载；
- OCI annotations 与 BWA 协议声明校验；
- 应用实例的创建和管理；
- Workspace 创建、关联和 Fork；
- 普通环境变量与敏感启动变量；
- 人工启动、打开时启动和自动后台运行；
- desired state 和宿主重启后的恢复；
- 稳定 iframe URL 和透明 HTTP/WebSocket 代理；
- 调用 Compute Runtime 创建、停止、提交和清理 Run。

Manager 是产品控制面；已实现的 Compute Runtime 仍是特权执行面。Manager
不得绕过 Runtime 状态机直接组装 Docker 命令。

第一版不预设 Manager 内部模块分布在多个进程。Registry、Lifecycle、Proxy 和
Internal UI 可以在同一宿主进程中保持清晰代码边界；Proxy 不直接执行 RefStore
写事务。

Manager 不得持有 Docker socket。镜像发现和本地准备也必须经过 Compute Runtime 的窄
Image API：

```text
resolveImage(repository, tag)
pullImage(reference)
inspectImage(digest)
```

Image API 只返回规范化 repository、RepoDigest、OCI labels、Entrypoint/Cmd、架构和本地
image ID，不接受任意 Docker 创建参数。第一版内部可复用 Docker Engine pull/inspect，
但 Docker 权限始终留在 Compute Runtime 执行面。

## 11. Runtime Proxy

容器 8080 端口不直接发布到局域网。浏览器只通过 Manager 代理访问：

```text
Browser iframe
→ Manager Runtime Proxy
→ BWA Instance 的当前 Run
→ Container :8080
```

代理路由绑定稳定 `instanceId`，不绑定临时 Run ID 或 Container ID。容器重建后
iframe URL、Instance 和 Workspace 均不变。

代理需要支持：

- 透明代理普通 HTTP 方法、请求/响应头和流式响应，不无故移除 Range 语义；
- WebSocket；
- 健康检查；
- 实例身份与用户访问校验；
- 应用停用或实例停止后立即撤销入口；
- 容器未就绪、崩溃与重连的宿主故障页。

## 12. 网络和信任定位

第一版 BWA 容器默认可以访问容器网络路由可达的网络，不设计逐应用出站授权、
域名/私网白名单或语义审查。真实能力可能包括互联网、局域网、宿主网关及其他
路由可达服务。安装界面必须清楚提示：

> 此应用可以访问互联网和宿主网络可达的其他服务，并能读取和修改其绑定的
> Workspace。

Biunivers 不承诺识别、审查或隔绝所有恶意代码。它负责准确呈现代码身份与
实际授予的能力，并实施结构边界，不对应用的行为目的作出安全背书。

默认出站网络访问不意味着宿主特权。BWA 仍不得因此获得：

- Docker socket；
- 宿主 `/data`、RefStore 或 secret 目录；
- 宿主设备和任意路径挂载；
- 宿主网络 namespace；
- 未经认证的 Biunivers 管理 API；
- Docker/OCI 管理能力。

V0.13 诊断执行器使用 `network=none`；BWA 需要新的私有代理网络模式：

```text
BWA 私有容器网络
├── 容器可出站访问路由可达网络
├── Manager Proxy 可入站访问 :8080
├── 不直接发布任何宿主/LAN 端口
└── 不使用 host network
```

容器可出站访问网络时，Biunivers 管理 API 仍必须独立认证，不得仅依赖网络不可达。

## 13. 权限原则

> 镜像描述自己是什么；用户和 Manager 决定它能做什么。

镜像不通过 label 或 Manifest 自动获得 Workspace、自动启动、宿主挂载、secret、
资源或其他权限。应用作者可以在 source 文档中提供使用建议，实际配置由
用户和 Manager 决定。

## 14. 环境变量与 Secret

环境变量和 secret 是 BWA Instance 的启动配置。Manager 在每次创建容器时动态
组装类似 `.env` 的运行环境，但第一版不要求将明文 `.env` 写入磁盘。

变量分为：

```text
镜像 OCI ENV
用户普通环境变量
Manager 保存的敏感变量
Manager 系统变量
```

组装优先级：

```text
OCI ENV
→ 用户普通变量覆盖
→ Secret 注入
→ BIUNIVERS_* 系统变量最终覆盖
```

系统变量候选：

```text
BIUNIVERS_WORKSPACE_PATH=/workspace
BIUNIVERS_HTTP_PORT=8080
BIUNIVERS_PROTOCOL_VERSION=1
```

用户变量不得使用 `BIUNIVERS_*` 保留前缀。容器启动后，当前 Run 的环境快照
不随实例配置的后续修改变化；修改在下次启动生效。

普通变量：

- 可查看、编辑和长期保存；
- 不进入 Workspace；
- Fork 实例时可由用户选择是否复制。

Secret/敏感变量：

- 不进入 Workspace；
- 不在界面回显原值；
- 不进入普通配置导出；
- Fork 实例时默认不复制；
- 第一版可作为特殊环境变量注入；
- 未来可扩展为 `/run/secrets/<name>`。

第一版的安全承诺限定为：敏感值与普通配置分开存储，存储载体权限限制为
`0600`，不回显、不普通导出、不进入 Workspace，并在容器启动时以内存组装的
环境变量注入。它不承诺抵抗已获得宿主数据目录读取权的攻击者，也不在第一版
引入外部 Vault、硬件密钥或自动轮换。

第一版不要求应用提供配置 Schema。Manager 提供通用键值编辑器，作者在 source
文档中说明需要的变量。

更新 digest 时，Manager 在一次更新确认页中列出将继续注入的敏感变量名称，不要求
用户逐项重新输入。只有换到不同 repository、新增敏感变量或用户主动撤销时，
才使用单独确认。

## 15. 生命周期与状态持久化

第一版不定义 Task、Session 和 Service 三种持久类型。一个通用 Instance 即可通过
启动方式、程序是否自行退出和用户何时停止来覆盖当前需求。

启动方式由用户和 Manager 决定：

```text
MANUAL      只由用户显式启动
ON_OPEN     打开应用时启动
AUTOMATIC   Biunivers 启动时自动运行
```

镜像可以在文档中建议使用方式，但不能强制自动启动。`AUTOMATIC` 第一版只表示
宿主正常启动时将 desired state 恢复为运行，不表示异常崩溃后无限重启。

`desiredState` 表示当前用户意图，`startupPolicy` 表示哪些宿主事件可以将该意图切换到
`RUNNING`：

```text
用户点击启动       desiredState = RUNNING
用户点击停止       desiredState = STOPPED
ON_OPEN 打开窗口       desiredState = RUNNING
AUTOMATIC 宿主启动    desiredState = RUNNING
关闭 iframe 窗口       不改变 desiredState
容器自行 exit 0       desiredState = STOPPED
容器异常退出         desiredState = STOPPED，observedState = ERROR
```

宿主受控关机时，Manager 正常停止并提交当前 Run，但不把这次基础设施停止解释为
用户主动停止。`AUTOMATIC` 实例在下次宿主启动时再进入 `RUNNING`。

最小 Instance 状态机：

```text
STOPPED
→ STARTING
→ RUNNING
→ STOPPING
→ COMMITTING
→ STOPPED

任一阶段无法安全完成
→ ERROR
```

Workspace 作为应用持久状态的关键规则：

```text
用户正常停止
→ 停止容器
→ 扫描 Upper
→ 提交 Workspace
→ Run = COMMITTED
→ Instance = STOPPED
```

```text
容器自行 exit 0
→ 视为正常完成
→ 同样提交 Upper
→ Instance = STOPPED
```

```text
非零退出 / OOM / SIGKILL / Runtime 异常
→ 不自动提交
→ 保留 Upper
→ Instance = ERROR
→ 用户选择恢复现场、审查并提交，或丢弃
```

关闭 iframe 窗口不触发停止和提交。只有 Manager 的“停止应用”、程序正常退出或
宿主受控关机流程才进入正常提交。提交失败时 Instance 不得显示为正常停止，
Upper 必须保留。无变化时复用 V0.13 no-op 语义，不制造虚假 revision。

第一版不做在线 checkpoint：运行中 Upper 尚未进入 Workspace Head，只有正常停止/完成后
成为稳定已提交状态。

为避免长期运行应用的状态长期只停留在本机 Upper，Manager 第一版提供显式
“保存状态并重启”：

```text
用户点击保存状态并重启
→ graceful stop
→ 扫描并提交 Upper
→ 以新 Workspace Head 创建新 Run
→ 等待 health
→ 恢复原稳定 iframe URL
```

这是受控停机/重启，不是在线 checkpoint。第一版不自动周期执行，界面需明确提示
长期未保存状态仍属于未提交 Upper。

## 16. 安装与更新

第一版由 Compute Runtime Image API 在内部通过现有 Docker Engine 执行 pull/inspect，获得
RepoDigest、OCI Config 和 labels。Manager 只信任 Image API 返回的规范 digest，不在
第一版实现完整 OCI Distribution 客户端、registry 认证和分层缓存。

安装流程：

```text
用户输入 ghcr.io/owner/image
→ Manager 读取 OCI metadata
→ 校验 BWA protocol label
→ 解析并固定 digest
→ 展示 description、source、repository 和 digest
→ 告知路由可达网络与 Workspace 能力
→ 用户确认
→ 注册 Application
```

首次打开流程：

```text
打开已安装 Application
→ Manager Internal UI
→ 创建空白 Workspace / Fork 现有 Workspace / 从 main 派生
→ 创建 Instance 并原子绑定 Workspace
→ 填写环境变量与敏感变量
→ 启动 Run
→ 显示宿主启动页
→ 等待 GET /health
→ 通过 Manager Proxy 打开 iframe
```

更新流程：

```text
发现新 tag/digest
→ 展示新旧 digest 和 OCI metadata
→ 用户确认
→ 正常停止并提交该 Application 的全部运行 Instance
→ 任一 Instance 有未处理异常 Upper 则拒绝更新
→ previousDigest = installedDigest
→ 更新 installedDigest
→ 列出将继续注入的敏感变量名称并一次确认
→ 各 Instance 下次启动统一使用新 digest
→ Workspace 状态保持不变
```

更新前必须先完成旧 Run 的正常停止与提交。旧 digest 在用户确认新版本可用前保留，
只支持回退到一个 `previousDigest`。Application 下的所有 Instance 始终使用同一
`installedDigest`，不支持实例级版本分叉。Workspace 回滚或数据迁移不在第一版
自动承诺中。

停用与卸载：

- 停用 Application 先阻止新 Run 和代理访问，正在运行的 Instance 必须通过正常
  停止流程处理；
- 卸载删除 Application 注册、Instance 启动配置和敏感变量，不默认删除已提交
  Workspace；
- 用户可以另行选择删除不再需要的 Workspace；
- 未处理的异常 Upper 存在时拒绝直接卸载，必须先恢复、提交或丢弃；
- 未被任何 Application 使用的本地镜像清理是后续存储维护，不与注册删除绑定。

## 17. 第一版明确不做

- Docker Compose 和多容器编排；
- 任意宿主目录、设备或 Docker socket 挂载；
- 任意宿主端口发布；
- 应用自行申领 capabilities 和宿主权限；
- 逐域名出站网络权限；
- 自动恶意代码识别和审查承诺；
- 应用配置 Schema；
- 应用自行决定权限或自动启动；
- Task/Session/Service 三套持久类型和状态机；
- 异常退出后无人确认的自动提交或无限崩溃重启；
- 运行中 Workspace checkpoint；
- 完整 OCI Distribution 客户端和私有 registry 凭据；
- 外部 Vault、硬件密钥和自动 secret 轮换；
- Manager 多进程拆分；
- 多个可写 Workspace 同时挂载；
- 跨 Workspace 原子事务；
- 自动三方合并；
- 将 Container ID 作为长期应用或实例身份。

## 18. 总体架构

```text
OCI Repository
长期应用身份
        │
        ▼
Workspace Application Manager
注册、安装、配置、Workspace 关联、生命周期、代理
        │
        ├── BWA Instance ─── Workspace
        │        ├── ENV
        │        ├── 敏感变量
        │        └── desired state
        │
        ▼
Compute Runtime
Image API、固定 Head、PVLogFS、COW、Run、提交、恢复
        │
        ▼
OCI Container :8080
HTTP UI + Backend + Worker
        │
        ▼

        │

```

## 19. 施工前的三份局部设计

总概念在第三版后不再继续扩张。施工前只需要三份有界局部设计：

### 19.1 Registry、Image 与持久 Schema

- Application/Instance SQLite Schema、版本迁移和原子事务；
- 空白 Workspace 创建与 Instance/Workspace 原子绑定；
- Compute Runtime Image API、公开 GHCR、digest 固定和单次回退；
- 普通/敏感变量的存储、`0600` 载体、日志脱敏和注入上限。

### 19.2 Lifecycle、提交与异常恢复

- `desiredState/startupPolicy/observedState` 与现有 Workspace Run 的映射；
- 正常停止、`exit 0`、异常退出与宿主受控关机；
- “保存状态并重启”的 stop→commit→new Run 协调；
- 异常 Upper 的恢复现场、审查提交和丢弃；
- Application 级更新、全 Instance 停止门和单次版本回退。

### 19.3 Runtime Proxy、网络与 iframe

- BWA 私有网络和 Manager Proxy 到容器 `:8080` 的入站路径；
- 稳定 Instance 路由身份、origin、Cookie/令牌和 WebSocket 认证；
- BWA iframe 协议与 Static App Protocol v1 可复用的安全原则；
- Manager Internal UI 的启动、进度、错误恢复和代理切换；
- `GET /health` 超时、代理中断和容器异常时的确定性故障页。

## 20. 结论

V0.14 概念基线为：

> 一个 BWA 以 OCI repository 为长期身份，以 digest 固定版本，必须在容器
> 8080 端口提供 HTTP 界面，以 Workspace 承载可分叉的主要持久状态，并由
> Workspace Application Manager 统一决定安装、配置、权限、启停、自动运行、
> Workspace 关联与代理访问。

这一产品层不改变 V0.13 已验证的固定 Head、单写租约、COW、CAS 提交、恢复与
选择性导回基底。
