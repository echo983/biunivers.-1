# 浏览器云端个人桌面 V0.14 Biunivers Workspace Application 概念设计

状态：设计共识已落盘，待规范评审

日期：2026-07-31

基线：`v0.13.0`

## 1. 目标

V0.13 已打通与具体应用无关的 Workspace Runtime：

```text
main 选择集
→ 派生 Workspace
→ 固定 PVLog Head
→ PVLogFS
→ COW overlay
→ OCI Run
→ 原子提交
→ Diff
→ 选择性导回 main
```

V0.14 的问题不再是技术可行性，而是如何把已有原语组合成可安装、可呈现、
可长期管理的容器应用系统。

## 2. 核心定义

**Biunivers Workspace Application**（简称 **BWA**）是：

> 以 OCI 镜像交付、自带 HTTP 图形界面、以 Workspace 承载主要持久状态，并由
> Biunivers Workspace Application Manager 统一安装、配置、运行和代理访问的容器应用。

BWA 不是 Docker Compose 包，也不是一份可由应用自由声明宿主权限的表单。
第一版一个 BWA 只对应一个 OCI 镜像。

## 3. 应用身份与安装来源

长期应用身份使用规范化 OCI repository：

```text
ghcr.io/<owner>/<image>
```

实际安装和运行的版本必须固定 digest：

```text
ghcr.io/<owner>/<image>@sha256:<digest>
```

身份分层：

```text
OCI repository   长期应用身份
OCI digest       不可变安装版本
OCI tag          只用于发现更新
Run ID           一次执行身份
Container ID     临时实现细节
```

第一版安装来源限定为公开 GHCR，但数据模型使用通用 OCI registry/repository
概念，不将长期协议永久绑定到 GitHub。

## 4. OCI 元信息

应用作者使用标准 OCI annotations 提供应用介绍和外部文档：

```text
org.opencontainers.image.title
org.opencontainers.image.description
org.opencontainers.image.source
org.opencontainers.image.version
org.opencontainers.image.revision
org.opencontainers.image.licenses
org.opencontainers.image.created
```

第一版强制提供：

```text
org.opencontainers.image.description
org.opencontainers.image.source
```

Manager 在安装和管理界面展示 description、source、repository、digest 及可用的
版本信息。

- description 只按纯文本呈现；
- source 第一版只接受 HTTPS；
- 外部链接使用 `noopener noreferrer`；
- 界面明示说明这些内容由应用作者提供；
- source 和开源不构成 Biunivers 的安全审核或背书；
- digest 才是实际已安装代码的不可变身份。

## 5. 最小协议声明

不使用 Compose 式 Manifest。镜像通过少量 OCI label 表示协议兼容，具体 label
名称在规范评审中冻结，概念形式为：

```text
io.biunivers.workspace-application.protocol=1
```

其余运行约定由协议固定：

```text
OCI 启动入口      镜像 Entrypoint/Cmd
HTTP 监听地址    0.0.0.0
HTTP 端口        8080
界面入口         GET /
健康检查         GET /health
Workspace          /workspace
临时目录          /tmp
```

固定 8080 以保持非 root、零 capabilities 和跨 OCI Runtime 兼容，不要求
`CAP_NET_BIND_SERVICE`。

## 6. 界面要求

每个可安装 BWA 必须在容器 8080 端口提供可用 HTTP 图形界面。宿主不关注
它使用什么语言、框架或进程结构。

界面通过 iframe 呈现，并遵守待定义的 **Biunivers Workspace Application
Protocol v1**。它可以沿用 Biunivers App Protocol v1 的消息安全原则，但两者
不是同一协议：

- iframe 与桌面宿主隔离 origin；
- 不能直接访问宿主 DOM；
- `postMessage` 校验 origin、source 和消息 Schema；
- 应用不能伪造宿主授权界面；
- 全屏、剪贴板等浏览器权限由宿主决定；
- iframe 关闭不自动等于停止后台 Run。

Biunivers 目前没有通用 CLI，因此无界面的纯执行器不能作为独立 BWA 直接
交付给普通用户。后台逻辑可以是 BWA 内部组成部分。

## 7. Workspace 状态模型

Workspace 是 BWA 的主要持久业务状态：

```text
程序与界面       OCI image@digest
已提交业务状态   Workspace Ref/Head
未提交变化       Run Upper
普通启动配置     Manager 数据库
Secret           Manager Secret Store
执行记录          Workspace Run
执行载体          OCI Container
```

容器不是应用实例，容器 ID 也不得成为长期应用身份。容器可以销毁和重建，
而 Workspace、实例配置与运行记录保持稳定。

## 8. 平行状态与默认体验

同一 BWA 可以绑定多个 Workspace，形成互不影响的平行状态：

```text
BWA Application
├── Instance A → Workspace A
├── Instance B → Workspace B
└── Instance C → Workspace C
```

同一 Head 可以低成本 Fork 为多个单写世界线，用于并行尝试、长期服务状态和
锁冲突隔离。结果使用已有 Diff 与选择性导回回收。

但普通用户的默认心智模型仍应接近传统桌面：

```text
安装应用
→ 创建一个默认状态/Workspace
→ 点击打开
→ 继续使用上次状态
```

Instance 可以保持为内部术语。只有用户显式选择“创建副本”或“从此分支”
时，界面才显示平行状态。

## 9. 持久实体

概念数据模型：

```text
BwaApplication
├── applicationId = OCI repository
├── installedDigest
├── protocolVersion
├── displayMetadata
└── enabled

BwaInstance
├── instanceId
├── applicationId
├── workspaceId
├── desiredState
├── startupPolicy
├── ordinaryEnvironment
├── secretReferences
├── configurationRevision
└── currentRunId

WorkspaceRun
├── runId
├── workspaceId
├── executorDigest
├── inputHead
├── state
└── outputHead
```

关系：

```text
Application 1 ── N Instance
Instance    1 ── 1 Workspace
Instance    1 ── N Run
Run         1 ── 0/1 当前 Container
```

## 10. Workspace Application Manager

**Biunivers Workspace Application Manager** 是 BWA 的统一系统控制面：

```text
Workspace Application Manager
├── Application Registry
├── Installation Manager
├── Instance Manager
├── Workspace Binding Manager
├── Configuration Manager
├── Lifecycle Controller
├── Runtime Proxy
└── Recovery/Reconciliation
```

Manager 负责：

- OCI repository 注册、digest 固定、安装、更新、停用和卸载；
- OCI annotations 与 BWA 协议声明校验；
- 应用实例和默认实例的创建；
- Workspace 创建、关联和 Fork；
- 普通环境变量与 secret 引用；
- 人工启动、打开时启动和自动后台运行；
- desired state、崩溃退避和宿主重启后的恢复；
- 稳定 iframe URL 和 HTTP/WebSocket/Range 代理；
- 调用 Compute Runtime 创建、停止、提交和清理 Run。

Manager 是产品控制面；已实现的 Compute Runtime 仍是特权执行面。Manager
不得绕过 Runtime 状态机直接组装 Docker 命令。

## 11. Runtime Proxy

容器 8080 端口不直接发布到局域网。浏览器只通过 Manager 代理访问：

```text
Browser iframe
→ Manager Runtime Proxy
→ BWA Instance 的当前 Run
→ Container :8080
```

代理路由绑定稳定 `instanceId`，不绑定临时 Run ID 或 Container ID。容器重建后
iframe URL、Instance 和 Workspace 均不变。

代理需要支持：

- HTTP 与流式响应；
- WebSocket；
- Range；
- 健康检查；
- 实例身份与用户访问校验；
- 应用停用或实例停止后立即撤销入口；
- 容器未就绪、崩溃与重连的宿主故障页。

## 12. 网络和信任定位

第一版 BWA 容器默认可以访问互联网，不设计逐应用出站授权、域名白名单或
语义审查。安装界面必须清楚提示：

> 此应用可以访问互联网，并能读取和修改其绑定的 Workspace。

Biunivers 不承诺识别、审查或隔绝所有恶意代码。它负责准确呈现代码身份与
实际授予的能力，并实施结构边界，不对应用的行为目的作出安全背书。

默认互联网访问不意味着宿主特权。BWA 仍不得因此获得：

- Docker socket；
- 宿主 `/data`、RefStore 或 secret 目录；
- 宿主设备和任意路径挂载；
- 宿主网络 namespace；
- 未经认证的 Biunivers 管理 API；
- Docker/OCI 管理能力。

## 13. 权限原则

> 镜像描述自己是什么；用户和 Manager 决定它能做什么。

镜像不通过 label 或 Manifest 自动获得 Workspace、自动启动、宿主挂载、secret、
资源或其他权限。应用作者可以在 source 文档中提供使用建议，实际配置由
用户和 Manager 决定。

## 14. 环境变量与 Secret

环境变量和 secret 是 BWA Instance 的启动配置。Manager 在每次创建容器时动态
组装类似 `.env` 的运行环境，但第一版不要求将明文 `.env` 写入磁盘。

变量分为：

```text
镜像 OCI ENV
用户普通环境变量
Manager 保存的 Secret
Manager 系统变量
```

组装优先级：

```text
OCI ENV
→ 用户普通变量覆盖
→ Secret 注入
→ BIUNIVERS_* 系统变量最终覆盖
```

系统变量候选：

```text
BIUNIVERS_INSTANCE_ID
BIUNIVERS_RUN_ID
BIUNIVERS_WORKSPACE_ID
BIUNIVERS_WORKSPACE_PATH=/workspace
BIUNIVERS_HTTP_PORT=8080
BIUNIVERS_PROTOCOL_VERSION=1
```

用户变量不得使用 `BIUNIVERS_*` 保留前缀。容器启动后，当前 Run 的环境快照
不随实例配置的后续修改变化；修改在下次启动生效。

普通变量：

- 可查看、编辑和长期保存；
- 不进入 Workspace；
- Fork 实例时可由用户选择是否复制。

Secret：

- 不进入 Workspace；
- 不在界面回显原值；
- 不进入普通配置导出；
- Fork 实例时默认不复制；
- 升级到新 digest 时应重新确认授予；
- 第一版可作为特殊环境变量注入；
- 未来可扩展为 `/run/secrets/<name>`。

第一版不要求应用提供配置 Schema。Manager 提供通用键值编辑器，作者在 source
文档中说明需要的变量。

## 15. 生命周期

底层能力可支持：

```text
TASK       一次性执行
SESSION    有限时长交互
SERVICE    长期后台运行
```

三者共用 Instance、Workspace、Run 和 Container 基底。区别主要是何时创建容器、
何时停止、如何提交和是否自动恢复。详细策略留给后续局部设计。

启动方式由用户和 Manager 决定：

```text
手动启动
打开应用时启动
Biunivers 启动时自动运行
```

镜像可以在文档中建议使用方式，但不能强制自动启动。自动运行使用 Manager
保存的 desired state、健康检查和有界崩溃退避。

## 16. 安装与更新

安装流程：

```text
用户输入 ghcr.io/owner/image
→ Manager 读取 OCI metadata
→ 校验 BWA protocol label
→ 解析并固定 digest
→ 展示 description、source、repository 和 digest
→ 告知互联网与 Workspace 能力
→ 用户确认
→ 注册 Application
→ 创建默认 Instance
→ 创建或绑定 Workspace
→ 填写环境变量与 Secret
→ 按用户策略启动
→ 等待 GET /health
→ 通过 Manager Proxy 打开 iframe
```

更新流程：

```text
发现新 tag/digest
→ 展示新旧 digest 和 OCI metadata
→ 用户确认
→ 停止旧 Run
→ 更新 installedDigest
→ 重新确认 Secret 授予
→ 创建新 Run
→ Workspace 状态保持不变
```

## 17. 第一版明确不做

- Docker Compose 和多容器编排；
- 任意宿主目录、设备或 Docker socket 挂载；
- 任意宿主端口发布；
- 应用自行申领 capabilities 和宿主权限；
- 逐域名出站网络权限；
- 自动恶意代码识别和审查承诺；
- 应用配置 Schema；
- 应用自行决定权限或自动启动；
- 多个可写 Workspace 同时挂载；
- 跨 Workspace 原子事务；
- 自动三方合并；
- 将 Container ID 作为长期应用或实例身份。

## 18. 总体架构

```text
OCI Repository
长期应用身份
        │
        ▼
Workspace Application Manager
注册、安装、配置、Workspace 关联、生命周期、代理
        │
        ├── BWA Instance ─── Workspace
        │        ├── ENV
        │        ├── Secret refs
        │        └── desired state
        │
        ▼
Compute Runtime
固定 Head、PVLogFS、COW、Run、提交、恢复
        │
        ▼
OCI Container :8080
HTTP UI + Backend + Worker
        │
        ▼
Manager Runtime Proxy
        │
        ▼
Biunivers iframe
```

## 19. 后续评审项

下列问题不影响概念成立，但需在施工前通过局部设计冻结：

1. OCI Distribution API 的拉取、digest 解析和缓存边界；
2. Application/Instance 的 SQLite Schema 和原子事务；
3. 默认 Workspace 是空白创建、由 main 派生还是由用户选择；
4. 一次性 Task、交互 Session 和长期 Service 的最小状态机；
5. 正常停止、崩溃、提交、丢弃和自动重启的关系；
6. Runtime Proxy 的路由身份、origin、Cookie/令牌与 WebSocket 认证；
7. 普通环境变量的保存方式与 Secret Store 第一版的加密边界；
8. 更新时 Workspace 兼容性、回退和 secret 重新确认；
9. 无界面、健康检查失败或容器持续崩溃时的用户体验；
10. Manager 内部 Registry、Lifecycle 和 Proxy 的进程/模块隔离。

## 20. 结论

V0.14 概念基线为：

> 一个 BWA 以 OCI repository 为长期身份，以 digest 固定版本，必须在容器
> 8080 端口提供 HTTP 界面，以 Workspace 承载可分叉的主要持久状态，并由
> Workspace Application Manager 统一决定安装、配置、权限、启停、自动运行、
> Workspace 关联与代理访问。

这一产品层不改变 V0.13 已验证的固定 Head、单写租约、COW、CAS 提交、恢复与
选择性导回基底。
