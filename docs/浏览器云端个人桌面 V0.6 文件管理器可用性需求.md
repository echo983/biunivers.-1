# 浏览器云端个人桌面 V0.6 文件管理器可用性需求

状态：设计基线

前置版本：`v0.5.0`

## 1. 目标

V0.6 补齐文件管理器日常使用中最明显的三个缺口：直接新建普通文件、低成本复制现有文件，
以及在目录请求期间提供不会误导用户的加载状态。

本版本不扩大第三方协议，也不改变 PVLog、RefStore 或不可变对象格式。

## 2. 用户闭环

用户可以：

1. 在当前目录点击“新建文件”，填写名称并创建零字节文件；
2. 默认名称为 `未命名.txt`，创建后可以通过既有 Handler 双击打开；
3. 选中普通文件后点击“复制”，修改副本名称并在当前目录创建副本；
4. 副本获得新 Entry ID，但复用原文件不可变内容 FID，不重新上传字节；
5. 需要复制到其他目录时，先复制再使用已有“移动”；
6. 目录或移动目标正在加载时看到明确状态，陈旧列表和提交按钮不可操作；
7. revision 冲突时刷新当前目录，不产生半完成的可见结果。

## 3. 必要约束

- 新建和复制仅限编译期 internal 应用 `system.files`；
- 请求仍要求 Desktop Origin、Fetch Metadata 和窗口实例 token；
- 文件名使用既有统一校验，目标目录内不允许重名；
- 新建文件的空内容先作为不可变 Chunk 写入，再以单次 PVLog 事务发布 Entry；
- 复制文件只创建新 Entry，内容引用保持不变；
- 所有结构变更携带 `expectedRevision` 并经过 Ref CAS；
- 失败不修改当前 Ref；已经写入但未引用的不可变对象允许由未来 GC 处理。

## 4. 不包含

- 递归复制文件夹；
- 跨目录复制对话框；
- 覆盖同名文件；
- 剪切板、拖放、多选和批处理；
- 新建时直接编辑内容；
- 文件模板、媒体类型嗅探或扩展名强制；
- 新的第三方 Host API。

文件夹递归复制需要多 Entry 原子事务或可恢复批处理。现有事务模型一次发布一个结构变更，
本版本不以可能留下半棵目录的循环请求模拟原子复制。

## 5. 验收条件

- 新建空文件产生新 revision，大小为 0，并可由 Notepad 打开和保存；
- 复制文件产生不同 Entry ID、相同内容 FID 和新 revision；
- 大文件复制不读取或重新上传 Chunk/Manifest；
- 目录重名、复制目录、无权实例和 stale revision 均被拒绝；
- 快速重复提交不会创建多个副本；
- 加载期间不显示可操作的陈旧目标；
- lint、测试、构建和真实 Docker/R2 验收通过。
