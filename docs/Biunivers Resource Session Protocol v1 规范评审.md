# Biunivers Resource Session Protocol v1 规范评审

状态：评审通过

日期：2026-07-29

评审对象：[Resource Session Protocol v1 设计](<Biunivers Resource Session Protocol v1 设计.md>)

## 1. 结论

Resource Session 有真实、近期且无法由 Host API v1 良好解决的需求：大型文件不能先完整下载，
视频拖动需要重复随机读取，文档应用也不应为每次读取重新申请一次性 transfer。

采用资源租约是必要且足够小的扩展。第一版只冻结：

- 合法启用应用与 Handler 资格；
- 宿主交付具体对象后创建会话；
- 60 秒建议续租与 300 秒硬过期；
- 批量续租、合法访问隐式续租和主动释放；
- 完整 GET、单区间 Range GET、完整 PUT；
- 不可变读取快照和写入 CAS；
- 应用状态撤销；
- Host API v1 兼容。

不需要窗口状态协议、请求级一次性授权、媒体专用 API 或完整文件系统权限模型。

## 2. 必要性逐项审查

| 能力 | 第一版 | 理由 |
|---|---|---|
| 应用启用状态校验 | 必须 | 用户对应用的总授权开关 |
| Handler 类型与 access 校验 | 必须 | 防止应用通过会话扩大接收范围 |
| 具体对象交付 | 必须 | Handler 不是文件枚举权限 |
| 资源会话 | 必须 | 支持持续读取、暂停和编辑 |
| 60/300 秒租约 | 必须 | 崩溃后自动回收且实现简单 |
| 批量续租 | 必须 | 避免每资源独立心跳 |
| 访问隐式续租 | 必须 | 避免活跃播放因心跳偶发失败中断 |
| 单区间 Range | 必须 | 视频 Seek 和通用随机读取的最小能力 |
| 多区间 Range | 删除 | 浏览器和 WASM 首版不依赖 multipart 响应 |
| 完整 PUT | 必须 | 记事本和编辑器闭环 |
| 区间写入 | 删除 | 与不可变内容模型冲突，近期无需求 |
| 内容快照 | 必须 | 多次 Range 必须读取同一组字节 |
| 原生 `<video src>` URL | 删除 | 自定义认证头另案处理，WASM/MSE 已可验收 |
| 目录会话 | 删除 | 会引入枚举和批量授权，超出近期需求 |
| 多文件会话 | 删除 | 没有首个验证应用，避免提前设计事务 |
| 持久授权 | 删除 | 会引入重启、恢复和用户撤销 UI |
| 跨应用转让 | 删除 | 属于未来 Resource Exchange |
| 会话持久化 | 删除 | 300 秒租约本就适合内存状态 |
| 窗口生命周期绑定 | 删除 | 关闭后自然停止续租即可 |

## 3. 应用启用与对象边界

采用以下规则：

```text
安装并启用
  + Handler 匹配类型和 action
  + 宿主路由或用户选择具体对象
  = 可以创建该对象的资源会话
```

“启用”表示用户允许应用处理它注册的对象类型，不要求每次 Range 请求重新确认。它不表示应用
能够枚举所有同类型文件。否则应用声明 `*/*` 就会变成文件系统全局授权。

第一版不新增权限清单或安装时权限弹窗。现有 Manifest、Handler、启用状态和对象打开动作
已经足以表达近期需求。

## 4. 租约参数评审

固定语义为：

- 客户端建议每 60 秒续租；
- 服务端以最后一次成功续租或合法资源活动为起点，300 秒后过期；
- 过期以服务端时钟判断；
- 续租批次部分成功；
- 过期不能复活；
- 主动释放幂等；
- 停用、卸载、更新和宿主重启撤销会话。

60/300 提供五倍宽限，足以覆盖普通定时器抖动。浏览器冻结、设备休眠或断网超过五分钟后
重新打开资源是明确且可接受的代价。第一版不增加后台 Service Worker、持久租约或复杂恢复。

合法数据请求在开始时检查租约。已经接受的流式请求允许完成，避免大文件传输在五分钟边界
被截断；停滞连接仍由 HTTP 超时处理。

## 5. Range 语义评审

采用标准 HTTP 单区间语义，不设计媒体时间 API：

- 播放器负责从容器索引把时间换算为字节位置；
- 宿主负责把字节区间映射到不可变 Chunk；
- 合法 Range 返回 `206`；
- 越界返回 `416`；
- 不带 Range 返回完整 `200`；
- 多区间请求第一版明确拒绝。

这个抽象同时适合视频、PDF、压缩包、音频、数据库查看器和 WASM 工具，必要性高于媒体专用
接口。

## 6. 快照与文件生命周期

资源会话固定创建时的内容描述：

- 移动和重命名不改变 Entry 身份；
- 外部保存不改变会话正在读取的字节；
- 删除后已经打开的只读会话可以读到租约结束；
- 新会话不能领取已删除对象；
- 编辑保存必须对预期版本执行 CAS；
- 外部修改或删除后保存返回冲突。

这与不可变 S3 对象天然一致，不需要复制临时文件或锁住当前 Entry。

## 7. 兼容策略评审

Host API v1 已被真实 Notepad 使用，不能原地改变一次性语义。V0.8 采用并行实现：

- 保留现有 `FileCapabilityRegistry` 和 `FileTransferService`；
- 新增 Resource Session Registry 和数据服务；
- 两者共同调用现有 `FileContentStore`、`FileSystemTransactions`、RefStore 和 Repository；
- Open Resource 的待领取对象由客户端选择 V1 handle 或 Resource Session；
- 新开发者文档推荐 Resource Session，旧应用无需迁移。

第一版不强行把 V1 重写成 Resource Session 适配器。并行复用核心比立即统一注册表风险更低，
以后有足够测试再考虑内部合并。

## 8. 安全评审

每次控制面和数据面请求必须同时验证：

- app runtime 凭据；
- 当前 app ID；
- 应用仍启用；
- 精确 App Origin；
- session ID 属于该 app；
- 会话未过期；
- access 允许本次操作。

session ID 使用专用请求头，不进入 URL、日志和应用持久化。错误不区分其他应用会话、随机 ID
或未授权资源。

应用被停用、卸载或更新时，宿主主动撤销该 app ID 的会话；每次访问再次检查当前应用状态，
覆盖生命周期通知与请求竞争。

## 9. 可施工性

现有实现已经提供所需基础：

- 应用级独立 Origin；
- app runtime instance token；
- Handler 和 Open Resource Launch；
- 稳定 Entry ID；
- FileContentStore 的 Chunk/Manifest 读取；
- FileSystemTransactions 的内容 CAS；
- 应用生命周期管理；
- 精确 CORS；
- SQLite RefStore 和不可变 Repository。

新增工作集中在内存会话表、Range 映射、少量消息/API 路由和兼容测试，不要求修改持久格式、
S3 权限、Manifest v1 或 Static App Protocol v1。

## 10. 评审出口

评审通过。施工必须继续遵守：

1. 不修改既有冻结协议原文；
2. 不增加目录或同类型文件枚举；
3. 不把 session ID 放入 URL；
4. 不为原生 video URL 扩大第一版范围；
5. 不暴露 FID、Entry ID、S3 Key 或 Ref；
6. 不削弱现有写入 CAS；
7. 先验证 Host API v1 回归，再验证 Range 播放场景。
