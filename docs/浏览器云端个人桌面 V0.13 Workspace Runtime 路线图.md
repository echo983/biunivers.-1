## 1. 路线原则

V0.13 按“先证明挂载，再建设控制面，最后形成产品闭环”的顺序推进：

```text
挂载技术可行性
→ Ref 与 Workspace 控制面
→ 最小子宇宙派生
→ Compute Runtime
→ COW 提交
→ Diff 与导回
→ 安全恢复与里程碑
```

阶段之间使用明确出口，不同时铺开 Workspace UI、PVLogFS、容器运行时和第三方协议。

## 2. 阶段 0：环境与实验规格

状态：已完成（2026-07-30）

工作分支：

```text
probe/workspace-mount-v0.13
```

准备：

- Linux 6.12 或当前部署目标内核；
- FUSE 3；
- `fusermount3`；
- `fuse-overlayfs`；
- Rust 工具链；
- Docker；
- 当前用户具有受控的 Docker 测试权限。

产出：

- 独立探针目录；
- 一键运行与清理脚本；
- 测试夹具；
- 结果报告格式；
- 不修改正式 File Service 和数据库 Schema。

出口：探针可重复运行，并能在失败后清理自身创建的容器、进程、mount 和临时目录。

## 3. 阶段 1：通用只读 FUSE + COW

状态：已完成（2026-07-30）

实现固定测试树的最小只读 FUSE：

- `lookup`；
- `getattr`；
- `readdir`；
- `open`；
- `read/pread`；
- 所有写操作返回只读错误。

验证：

- FUSE 作为 Lower；
- 优先测试内核 OverlayFS；
- 不兼容时测试 `fuse-overlayfs`；
- merged 中读取 Lower；
- 新建、覆盖、截断、重命名和删除；
- whiteout 与 opaque directory；
- Upper 内容可以被确定性解释；
- 正常和强制卸载；
- 探针中断后可重新运行。

Go/No-Go：

- 至少一条 COW 路线稳定支持目标行为；
- 容器不需要 `/dev/fuse`、mount capability 或 Docker socket；
- Upper 能完整表达新增、修改和删除；
- 无法可靠解释的文件系统变化不得进入正式提交器。

两条 Overlay 路线均失败时，停止完整施工并重新评审 COW 实现；不静默把全量物化改成正式
架构。

## 4. 阶段 2：Docker 挂载与隔离

状态：已完成（2026-07-30）

将 merged bind mount 到固定诊断容器的 `/workspace`：

- 容器非 root；
- root filesystem 只读；
- `/workspace` 可写；
- 默认断网；
- 删除 capabilities；
- `no-new-privileges`；
- CPU、内存、PID 和运行时间限制；
- 无宿主 `/data`、secret、Docker socket 和设备。

验证容器内：

- `find`、`stat`、随机读取；
- 新建和修改；
- 重命名与删除；
- 编译或批量小文件访问；
- 容器退出后 Upper 保留；
- 容器崩溃不破坏 Lower；
- 清理顺序可重复。

出口：容器只看到 merged 工作区，所有写入停留在 Upper。

## 5. 阶段 3：真实固定 PVLog HEAD

状态：核心 Go 条件已通过（2026-07-30）

把测试树替换为真实 File Service 数据：

1. 读取目标 Ref；
2. 固定 `inputHead`；
3. 验证 Head；
4. 加载 Checkpoint 与必要 Segment；
5. 构造 EntryIndex；
6. 通过 FUSE 暴露普通文件与目录；
7. 按需读取 Manifest/Chunk；
8. 校验全部读取内容 FID。

测量：

- 首次挂载时间；
- EntryIndex 内存；
- 千级小文件 `stat/open`；
- 目录枚举；
- 首次和缓存后读取；
- 跨 64 MiB 分片随机读取；
- 未访问内容是否没有提前下载；
- Cache 命中、损坏与回收。

出口：大 Workspace 无需全量下载即可启动，真实工具能在固定 HEAD 上稳定读取。

## 6. 阶段 4：冻结局部设计

状态：下一步

根据探针结果更新总设计，并冻结三份局部设计：

1. Workspace 控制面；
2. PVLogFS + Compute Runtime；
3. COW 提交、Diff 与导回。

重点冻结：

- 选择的 Overlay 实现；
- mount 传播和清理协议；
- inode/Entry 映射；
- Cache；
- Runtime 窄 API；
- Upper/whiteout 规范；
- Workspace/Run 状态机；
- 崩溃恢复。

出口：实现选择不再依赖未验证假设，完整施工计划通过评审。

## 7. 阶段 5：Ref-aware 控制面

升级 SQLite 控制库：

- Workspace records；
- Run records；
- Workspace + Ref 原子创建删除；
- Workspace 写租约；
- 状态机；
- 备份恢复；
- 所有 Ref 的 GC 可达性。

将内部服务从硬编码 `main` 调整为显式 Ref：

```ts
loadEntryIndex(repository, refStore, refId)
FileSystemTransactions({ refId, ... })
```

外部和第三方 API 不增加任意 `refId` 参数。

出口：

- `main` 全量回归通过；
- 测试 Workspace Ref 可安全创建、推进和删除；
- GC 保护所有活动 Ref。

## 8. 阶段 6：最小 Workspace 产品

文件管理器增加“创建工作空间”：

- 同目录选择；
- 文件和目录；
- 目录递归；
- 新虚拟根；
- 新 Entry ID；
- 新 lineage；
- 内容 FID 共享；
- revision 0 Genesis HEAD。

新增 internal “工作空间”应用：

- Workspace 列表；
- 概览；
- Ref-aware 文件浏览；
- 删除；
- 临时/保留策略。

出口：不依赖计算运行时，用户也能创建、浏览和删除最小子宇宙。

## 9. 阶段 7：Compute Runtime 与 Run

实现独立 Runtime Daemon：

- 受认证的窄 API；
- PVLogFS Supervisor；
- COW Mount Manager；
- OCI Runtime Adapter；
- 固定诊断执行器；
- 资源限制；
- 异常清理。

规则：

- Run 固定 `inputHead`；
- 一个 Workspace 最多一个写 Run；
- Run 持有 Workspace 写租约；
- 关闭 UI 不停止 Run；
- 停止 Run 不删除 Workspace。

出口：诊断容器可以修改工作区，但 Workspace Ref 尚未被自动推进。

## 10. 阶段 8：提交、Diff 与导回

实现：

- 暂停写入；
- Upper/whiteout 解释；
- 目标状态构造；
- 新内容分片、FID 与去重；
- PVLog operations；
- Segment、Checkpoint、Head；
- CAS 发布；
- 冲突保留 Upper；
- 丢弃不推进 Ref。

Workspace 应用增加：

- Baseline/current Diff；
- 文本 Diff；
- 二进制元数据变化；
- 选择结果；
- 复制到 `main` 指定目录；
- 同名冲突确认。

不自动删除或覆盖 `main`，不做三方合并。

出口：

```text
派生
→ 挂载
→ 运行
→ 提交
→ 审阅
→ 导回或丢弃
```

形成完整产品闭环。

## 11. 阶段 9：安全、恢复与里程碑

真实验证：

- 主服务重启；
- Runtime 重启；
- 容器崩溃；
- 遗留 mount；

- Upper/磁盘超限；
- Workspace 删除；
- GC；
- 大文件和大量小文件；
- `main`、Wormhole、Resource Session 与文件管理器回归。

完成：

- 运维说明；
- 清理脚本；
- 备份恢复；
- 关于界面；
- 验收记录；
- 文档归档。

出口：合并并标记 `v0.13.0`。

## 12. V0.13 之后

V0.13 不冻结 Workspace App 第三方协议。底座稳定后再设计：

```text
biunivers.workspace-app/1
├── 固定 OCI image digest
├── iframe Runtime UI
├── 网络策略
├── secret 注入
└── 第三方安装与更新
```

Agent、FFmpeg、编译器和 OCR 都作为 Workspace App/Executor 使用相同底座。Agent 专用的模型、
审批、聊天和计划界面不进入 V0.13。

## 13. 用户参与节点

需要人工参与：

1. 安装 FUSE/Overlay 依赖；
2. 运行需要宿主 mount 和 Docker 权限的探针；
3. 验收 Workspace 创建与浏览；
4. 验收容器修改、提交和丢弃；
5. 验收 Diff 与导回；
6. 最终里程碑验收。

其他阶段优先使用自动测试、固定夹具和可重复脚本推进。
