# 浏览器云端个人桌面 V0.5 资源打开技术设计

状态：设计完成，待施工

依赖：

- [V0.5 资源打开设计](<浏览器云端个人桌面 V0.5 资源打开设计.md>)
- [V0.5 资源打开规范评审](<浏览器云端个人桌面 V0.5 资源打开规范评审.md>)
- [Open Resource Protocol v1](developer-kit/v1/BIUNIVERS_OPEN_RESOURCE_PROTOCOL_V1.md)

## 1. 当前结构约束

现有桌面有四个直接影响方案的事实：

1. `AppDefinition` 和窗口状态以 appId 为键，每个应用只有一个窗口；
2. 第三方 iframe 挂载后才创建 Host API instance token；
3. 文件 handle 必须由服务端绑定到该 instance token；
4. 默认桌面状态保存在浏览器 `localStorage`，安装记录保存在服务端。

因此不能在文件管理器双击时直接签发目标句柄，也不能把 handle 或 launch ticket 放入 iframe
URL。V0.5 使用“服务端待领取 Launch + 客户端单实例投递”。

## 2. 模块边界

```text
文件管理器
  │ 用户双击 Entry
  ▼
Open Resource 服务（服务端）
  ├─ 读取已验证 Handler
  ├─ 解析候选
  └─ 创建待领取 Launch
          │ launchId 仅在宿主控制面
          ▼
桌面 Launch Broker（父页面）
  ├─ 打开/聚焦目标 appId
  └─ 通知 IframeApp 有待领取上下文
          ▼
第三方应用
  └─ launch.getContext
          ▼
IframeApp / 服务端 claim
  ├─ 验证 app + window instance
  ├─ 原子消费 Launch
  └─ 签发该实例专属 file handle
          ▼
既有 Host API v1
```

## 3. 安装时 Handler 验证

新增服务端类型：

```ts
interface OpenResourceDeclaration {
  protocol: "biunivers.open-resource/1";
  handlers: ResourceHandler[];
}

interface ResourceHandler {
  id: string;
  actions: Array<"open" | "edit">;
  extensions: string[];
  mediaTypes?: string[];
  access: "read" | "read-write";
}
```

检查流程在普通 Manifest 和仓库文件检查之后执行：

1. 两个扩展文件都不存在：返回无扩展；
2. 只存在一个：检查失败；
3. 协议 Markdown 与内置冻结原文逐字比较；
4. JSON 使用严格 schema 和语义校验；
5. 检查 Handler ID 唯一；
6. 把规范化声明放入 inspection result；
7. 安装确认时与应用记录原子保存。

`InstalledAppRecord` 增加可选 `openResource`。旧 schemaVersion 1 记录缺少该字段仍有效，不需要
批量迁移；写回时保留明确的可选字段。应用更新以新 commit 检查结果整体替换，不能沿用旧
声明。

管理检查 UI 应显示应用请求登记的扩展名、动作和最大访问级别，使管理员在安装前可见。

## 4. Handler 投影

活动 managed app 的公开桌面投影增加只读 Handler 信息：

```ts
interface AppDefinition {
  // existing fields
  resourceHandlers?: ResourceHandler[];
}
```

它只用于桌面展示和初步候选计算，不作为权限权威来源。服务端创建和领取 Launch 时必须再次
读取当前安装记录，验证应用启用、Handler 仍存在且支持动作。

传统 `public/config/apps.json`、external app 和 internal app 不能用运行时字段伪造第三方
Handler。V0.5 只接受经过 managed 安装流程验证的第三方声明。

## 5. 候选解析

服务端 `OpenResourceService.resolve` 输入：

```ts
{
  sourceInstanceToken,
  entryId,
  expectedRevision,
  requestedAction: "edit"
}
```

V0.5 来源只允许 `system.files` internal instance。服务读取当前 Entry 并检查：

- Entry 存在且是文件；
- expected revision 没有过期；
- 文件名最后扩展名规范化为小写；
- 候选应用当前 active；
- Handler 声明对应扩展名。

`edit` 解析优先支持 edit 的 Handler；没有 edit 候选时可以返回 open 候选，但 UI 必须把
实际动作和可能只读状态展示清楚。

返回只包含：

- 文件公开名称；
- 规范化扩展名；
- 候选 appId、应用名称、图标；
- handlerId、支持动作和最大访问级别。

不返回 Entry ID 之外的存储身份、FID、路径、Ref 或 S3 信息。

## 6. 默认关联

默认关联 key：

```text
extension:.txt:edit
extension:.txt:open
```

值为：

```ts
{ appId: string; handlerId: string }
```

`PersistedDesktopState` 升级到 schemaVersion 2，增加：

```ts
defaultResourceHandlers: Record<string, {
  appId: string;
  handlerId: string;
}>;
```

读取器兼容 schemaVersion 1，并迁移为空关联；写入只写 v2。恢复桌面时不删除暂时失效的关联，
但解析时只有候选集合中仍有效的关联才能执行。

首版设置 UI至少提供查看和清除默认关联。设置默认项只发生在用户勾选“始终使用”并确认打开
方式后。

## 7. 待领取 Launch

服务端新增内存 `OpenResourceLaunchRegistry`，记录：

```ts
interface PendingLaunch {
  launchId: string;
  targetAppId: string;
  handlerId: string;
  entryId: string;
  action: "open" | "edit";
  writable: boolean;
  createdAtMs: number;
  expiresAtMs: number;
}
```

Launch 不是持久状态：

- 使用 CSPRNG 生成不透明 launchId；
- 最长 5 分钟；
- 不进入 URL、应用状态、日志或 localStorage；
- 每个 appId 同时最多一个 pending Launch；
- 宿主进程重启后自然失效；
- 原子 claim 后从 registry 删除；
- 创建失败不签发 handle；
- 过期或取消时不改变文件系统。

文件管理器选定 Handler 后，通过 internal API 创建 Launch。服务端再次验证 Entry、revision、
目标应用、Handler 和动作，然后返回 launchId 给可信桌面父页面。

## 8. 客户端 Launch Broker

新增只在父页面内存存在的 broker：

```ts
deliverLaunch(appId, launchId)
subscribeLaunch(appId, listener)
consumeLaunchId(appId)
```

它不持久化 launchId。

文件管理器创建 Launch 后：

1. 调用 `openApp(appId)`；
2. 把 launchId 交给 broker；
3. 如果 iframe 首次挂载，`IframeApp` 在 Host instance ready 后消费 broker 通知；
4. 如果 iframe 已运行，窗口被置前并收到新的通知；
5. `IframeApp` 只向正确 App Origin 发送
   `{"protocol":"biunivers.open-resource/1","event":"launch.contextAvailable"}`。

通知没有 launchId、文件名或 handle。

## 9. `launch.getContext`

`IframeApp` 与 Host API 类似地校验：

- `event.source` 是当前 iframe；
- `event.origin` 等于该应用 App Origin；
- protocol、requestId、method 和 params 严格有效。

收到 `launch.getContext` 后：

1. 等待 Host instance token ready；
2. 从 broker 取得该 appId 的 launchId；
3. 调用服务端 claim API，提交 instance token 和 launchId；
4. 服务端验证 instance 的 appId 等于 Launch target；
5. 再次验证 Handler 和 Entry 当前有效；
6. 按权限交集调用既有 `FileCapabilityRegistry.issueHandle`；
7. 原子消费 Launch；
8. 返回协议响应。

普通桌面启动没有 pending launch 时返回 `NO_LAUNCH_CONTEXT`。过期返回
`LAUNCH_CONTEXT_EXPIRED`。应用已领取后再次请求时也返回 `NO_LAUNCH_CONTEXT`，不通过错误
差异暴露旧上下文。

若 claim 期间 Entry revision 变化，返回 `FILE_VERSION_CONFLICT`，不签发基于过期选择的
handle。

## 10. 权限计算

V0.5 的 `system.files` 来源允许用户请求读写当前文件，但最终 writable 必须同时满足：

- requested action 是 edit；
- Handler access 是 read-write；
- 当前文件可写；
- 用户没有选择只读回退。

否则签发只读 handle。应用只读取 Launch Context 中的实际 permissions。

handle、transfer、读写和冲突全部复用既有 `FileCapabilityRegistry`、
`FileHostService` 和 `FileTransferService`，不新增第二套文件访问实现。

## 11. 文件管理器 UI

双击行为：

- 目录：保持进入目录；
- 文件：发起 resolve；
- 唯一 edit 候选：直接创建 Launch；
- 多候选：打开方式对话框；
- 只有 open 候选：以只读语义打开；
- 无候选：显示明确提示；
- pending Launch 忙碌：提示目标应用仍有未处理的打开请求。

打开方式对话框显示候选应用、动作和访问语义。勾选“始终使用”后，只有 Launch 成功创建才
写入默认关联。

## 12. 第三方记事本改造

`biunivers-notepad` 仓库需要：

- 携带冻结协议原文和 Handler 声明；
- 实现 Open Resource 消息客户端；
- 普通启动处理 `NO_LAUNCH_CONTEXT`；
- 启动资源后复用当前 Host API 读取与保存；
- 收到后续 `launch.contextAvailable` 时处理未保存内容；
- 读取实际 permissions 并支持只读状态；
- 保持 `FILE_VERSION_CONFLICT` 保护；
- 切换或关闭文档时释放旧 handle。

主仓库不直接修改第三方仓库；两边分别提交、测试和打版本。

## 13. 错误模型

至少包含：

- `OPEN_RESOURCE_UNSUPPORTED`；
- `NO_LAUNCH_CONTEXT`；
- `LAUNCH_CONTEXT_EXPIRED`；
- `RESOURCE_OPEN_BUSY`；
- `NO_RESOURCE_HANDLER`；
- `HANDLER_NOT_AVAILABLE`；
- `REQUEST_INVALID`；
- `FILE_NOT_FOUND`；
- `FILE_VERSION_CONFLICT`；
- 既有 handle 和 transfer 错误。

错误信息不得用于探测其他应用的私有状态或未授权 Entry。

## 14. 测试策略

单元测试：

- schema 与语义校验；
- Handler 安装、更新、停用和卸载投影；
- 扩展名和动作匹配；
- v1 → v2 桌面状态迁移；
- Launch 创建、忙碌、过期、claim 和跨 app 拒绝；
- 权限交集；
- broker 与单实例后续通知；
- 普通启动和错误响应。

集成测试：

- internal 来源限制；
- App Origin 和 window instance 隔离；
- claim 后得到可用 Host API handle；
- stale revision 不签发 handle；
- 应用停用后 pending Launch 不能 claim；
- URL、投影和公开配置不含 capability。

人工端到端：

- `.txt` 双击到记事本；
- 多候选打开方式与默认关联；
- 打开第二个 TXT 时处理未保存内容；
- 重命名和移动后的 Entry；
- 并发保存冲突；
- 应用停用、更新、卸载；
- 容器重启后的安全失效和文件内容完整性。

## 15. 不变性与故障语义

Open Resource 只选择现有 Entry 并签发 capability，不写 PVLog。只有目标应用完成既有
`file.writeTransfer` 才产生文件系统 revision。

任意中间失败最多留下过期的内存 Launch 或窗口，不会创建空文件、修改 Ref 或上传不可达
内容。它不改变 File Service 的不可变对象保证和一次刻录存储适配性。
