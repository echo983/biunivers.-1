# 浏览器云端个人桌面 V0.14 Lifecycle、提交与异常恢复局部设计

状态：实现基线

日期：2026-07-31

基线：V0.14-A Registry、Image 与持久 Schema 已验收

## 1. 范围

本设计冻结 V0.14-B：

```text
BWA Instance
→ 创建并启动动态 OCI Run
→ 正常停止或正常自行退出
→ 提交 Upper
→ 更新 Workspace Head
→ 再次启动恢复状态
```

同时冻结非零退出、OOM、强制终止、Runtime/宿主中断和提交失败时的 Upper 保留与人工处置。

本阶段不实现 iframe、HTTP/WebSocket 代理、健康页和最终应用管理 UI；它们属于 V0.14-C。
生命周期先使用系统测试入口和诊断镜像验收。

## 2. 不改变的 V0.13 基底

- Workspace Ref/Head 是已提交状态的唯一权威；
- 一个 Workspace 同时只有一个写 Run；
- Run 固定 input Head 和 revision；
- PVLogFS Lower 只读，Overlay Upper 单写；
- 正常提交通过 Ref CAS 发布；
- Runtime Unix socket 是 Manager 到特权执行面的唯一入口；
- Docker socket、宿主路径和任意创建参数不暴露给 Manager 或应用。

V0.14-B 在这些原语之上协调，不另造第二套提交器、写租约或恢复记录。

## 3. 权威状态与派生状态

### 3.1 权威状态

```text
BwaInstance.desiredState   用户当前意图
BwaInstance.startupPolicy  宿主事件能否启动
WorkspaceRun.state         控制面 Run 事实
RuntimeManifest.state      本机执行面事实
Workspace.activeWriteRun   写租约事实
Workspace Ref              已提交状态事实
```

Instance 不新增持久 `observedState` 和 `currentRunId`。Manager 在一次 SQLite 读事务中按
Instance 对应的非终态 BWA Run 和本地 Runtime inspection 派生 observed state。

### 3.2 派生 observed state

```text
无活动 Run + desired STOPPED                  STOPPED
控制 PREPARING                                STARTING
控制 RUNNING + 本地运行                       RUNNING
控制 STOPPED/COMMITTING                       SAVING
正常提交完成 + desired STOPPED                STOPPED
正常提交完成 + desired RUNNING                STARTING（准备下一 Run）
控制 FAILED/CONFLICT 或本地缺失/异常           ERROR
```

同一 Instance 同时最多一个非终态 Run。该约束由事务检查和 Workspace 单写租约共同实施。

## 4. BWA Run 身份

RefStore 新增 `bwa_run_bindings`：

```sql
CREATE TABLE bwa_run_bindings (
  run_id BLOB PRIMARY KEY
    REFERENCES workspace_runs(run_id) ON DELETE CASCADE,
  instance_id BLOB NOT NULL
    REFERENCES bwa_instances(instance_id) ON DELETE RESTRICT,
  executor_digest TEXT NOT NULL,
  stop_reason TEXT CHECK(stop_reason IN (
    'USER_STOP', 'SAVE_RESTART', 'HOST_SHUTDOWN', 'EXITED'
  )),
  created_at_ms INTEGER NOT NULL CHECK(created_at_ms >= 0)
) STRICT;
```

`executorId` 继续满足 V0.13 通用 Run 记录，BWA 固定写 `bwa.workspace-application.v1`；实际
不可变代码身份由 binding 的 `executor_digest` 保存。Application repository 可经 Instance
关联取得，不在每个 Run 重复保存。

创建 BWA Run 使用单一事务：

```text
校验 Application enabled
→ 校验 Instance/Workspace 独占关系
→ 校验无未处置异常 BWA Run
→ 创建 WorkspaceRun 并取得写租约
→ 创建 bwa_run_bindings
→ 按调用原因更新 desiredState
```

## 5. 动态 BWA Launch Spec

V0.13 `ExecutorRegistry` 继续只服务宿主固定执行器。BWA 使用新的窄操作：

```text
prepareBwa({
  run identity,
  repository@digest,
  ordinary environment,
  sensitive environment,
  fixed host limits,
  capability
})
```

Runtime 只接受：

- 已规范化的 `ghcr.io/...@sha256:...`；
- 符合变量规则且不覆盖 `BIUNIVERS_*` 的环境；
- Manager 不能修改的 host limits；
- 已存在且身份一致的 WorkspaceRun/binding。

Runtime 以 `runId` 在内存登记 launch spec，调用现有 Snapshot/PVLogFS/COW prepare。非敏感的
执行身份进入 Runtime manifest v2；环境变量和 secret 不写入 manifest。

prepare 后 daemon 若在 start 前崩溃，该 Run 按中断恢复标为 FAILED，不尝试从磁盘恢复
secret。用户可以重试为新的 Run。

## 6. BWA OCI 计划

BWA 使用独立的 `buildBwaDockerOciPlan`，不放宽固定 Executor 计划：

```text
docker create
--name biunivers-run-<runId>
--read-only
--cap-drop ALL
--security-opt no-new-privileges
--pids-limit <host fixed>
--memory <host fixed>
--cpus <host fixed>
--user 65532:65532
--volume <validated merged>:/workspace:rw
--workdir /workspace
--tmpfs /tmp:rw,nosuid,nodev,noexec,size=<host fixed>
--env <validated values>
--env BIUNIVERS_WORKSPACE_PATH=/workspace
--env BIUNIVERS_HTTP_PORT=8080
--env BIUNIVERS_PROTOCOL_VERSION=1
repository@digest
```

不传 `--entrypoint`，使用镜像自己的 Entrypoint/Cmd。第一阶段 Runtime 测试可使用
`network=none`；V0.14-C 用私有 BWA 网络替换该固定网络模式，不开放任意网络参数。

镜像 Config.User 不授予权限；第一版由宿主固定 UID/GID。应用镜像必须保证程序和静态资源
可由该用户读取执行，并只向 `/workspace` 和 `/tmp` 写入。

环境通过 Docker create 参数注入，值可能被拥有 Docker/宿主权限的人检查；这与 V0.14
第一版 secret 威胁模型一致。值不得出现在 Runtime manifest、普通日志或错误消息。

## 7. 启动事务与补偿

```text
Instance START 请求
→ Instance 互斥锁
→ 解析 Application digest 和环境
→ RefStore 原子创建 BWA Run + binding + 写租约
→ Runtime prepareBwa
→ Runtime start
→ WorkspaceRun RUNNING
→ 返回 RUNNING
```

失败补偿：

- 创建控制 Run 前失败：不产生状态；
- prepare/start 失败：Runtime 尽力清理容器和挂载，保留可能存在的 Upper；
- 控制 Run 转 FAILED 并释放写租约；
- desiredState 设为 STOPPED，除非失败发生在“保存并重启”的重启半段；
- 不在同一请求内无限重试。

`AUTOMATIC` 和 `ON_OPEN` 只改变何时提出 START 请求，不产生不同 Run 类型。

## 8. 容器结束分类

Runtime 必须在删除容器前取得最终 `OciContainerState`。

### 8.1 正常结束

以下属于正常结束：

- 容器自行退出且 `exitCode = 0`、未 OOM；
- Manager 发出 graceful stop，容器在时限内退出，未 OOM、未被 SIGKILL；
- 宿主受控关机中的同一 graceful stop。

预期 SIGTERM 的平台退出码可作为用户发起 stop 的正常结果，但自行退出时只有 0 是正常。

### 8.2 异常结束

- 非零自行退出；
- OOMKilled；
- graceful stop 超时后强制终止；
- Docker inspect/remove/挂载释放不能确定完成；
- Runtime daemon 或宿主非受控中断。

异常结束绝不自动提交。

## 9. 正常停止与提交

用户停止：

```text
desiredState = STOPPED
→ binding.stopReason = USER_STOP
→ Runtime graceful stop
→ 捕获最终容器状态
→ 释放容器、挂载和 Snapshot
→ 控制 Run STOPPED
→ 现有 WorkspaceCommitCoordinator.commit
→ Run COMMITTED / CONFLICT
→ 销毁无须恢复的本地 Run 资源
```

程序自行 `exit 0`：Manager/Supervisor 检测后使用相同 finalize/commit 流程，并将
`desiredState = STOPPED`、`stopReason = EXITED`。

提交无变化时复用 no-op 语义，output Head 等于 input Head，不增加 revision。

提交失败或 CAS 冲突进入 ERROR，Upper 保留；不能显示正常停止。

## 10. 保存状态并重启

```text
Instance 互斥锁
→ desiredState 保持 RUNNING
→ stopReason = SAVE_RESTART
→ graceful stop
→ 正常提交
→ 使用新 Workspace Head 创建全新 Run
→ start
```

旧 Run 与新 Run 不复用 Container ID、Run ID、capability 或 Runtime manifest。若停止或提交
失败，不启动新 Run；若新 Run 启动失败，已提交 Head 仍有效、desiredState 保持 RUNNING，
observed state 为 ERROR，等待用户重试。

## 11. 宿主受控关机

Desktop Server 在关闭 Compute Runtime 前调用 Lifecycle `shutdown()`：

1. 阻止新 start/save/update；
2. 对全部正常 RUNNING BWA Instance 并发数受限地 graceful stop；
3. 正常停止者提交；
4. 失败者保留 Upper 并标 FAILED；
5. `AUTOMATIC` 或原 desired RUNNING 的意图保持 RUNNING；
6. 最后关闭 Runtime daemon。

下次启动仅对 `startupPolicy = AUTOMATIC` 且没有未处置异常 Upper 的 Instance 自动启动。
`ON_OPEN` 等待用户再次打开；MANUAL 不因旧 desired RUNNING 自动启动。

无法完成受控关机时不谎称已提交；非受控中断走现有 daemon recovery。

## 12. 异常 Upper

一个 Instance 存在未处置 FAILED/CONFLICT BWA Run 时，禁止创建新 Run、更新 digest、解绑
或卸载 Application。第一版提供三个明确动作：

### 12.1 提交保留内容

`publishFailedUpper(runId)`：

- 确认 Workspace Ref 仍等于 Run input Head/revision；
- 原子重新取得该 Workspace 写租约；
- 将 FAILED Run 转入 COMMITTING；
- 直接扫描保留 Upper 并调用同一提交器；
- 成功后 COMMITTED，失败继续保留 Upper。

不允许在 Ref 已前进时自动合并；此时返回 CONFLICT。

### 12.2 丢弃

`discardFailedUpper(runId)` 删除本地 Upper，将 Run 转为 DISCARDED。只有该动作完成后 Instance
才能再次启动。

### 12.3 恢复现场

第一版不实现“复用同一 Upper 继续运行”。它需要重新建立 overlay、恢复进程级语义并处理
应用迁移，必要性低于提交或丢弃。界面中的“恢复”第一版表示保留现场供查看和决定，不表示
容器续跑。

这项删减不会丢失数据，也避免为一个低频动作扩展 Runtime 状态机。

## 13. Supervisor

Manager 维护进程内轻量 Supervisor：

- 只跟踪数据库中的活动 BWA Run；
- 固定低频轮询 Runtime inspect，不依赖 iframe 窗口；
- 发现容器退出后只执行一次 finalize；
- 每个 Instance 使用互斥队列串行 start/stop/save/finalize；
- Manager 重启时从 RefStore 与 Runtime 对账，不以旧内存为真相。

第一版不做复杂指数退避、无限自动重启和通用作业调度器。

## 14. Application 更新门

V0.14-B 只冻结生命周期门，不扩展 Image A 的身份模型：

```text
锁定 Application
→ 阻止新 Run
→ 正常停止并提交全部 RUNNING Instance
→ 任一异常 Upper/提交失败则整体拒绝更新
→ 原子 previousDigest = installedDigest
→ installedDigest = newDigest
→ 解锁
```

已提交 Workspace 不随镜像更新。回退执行同一全 Instance 停止门，只交换当前和 previous
digest，不回滚数据 Head。

## 15. Runtime API 增量

Unix socket 增加有界操作：

```text
prepareBwa(input)
finalizeBwaStop(runId, reason)
finalizeExitedBwa(runId)
```

现有 `prepare/start/inspect/commit/destroy` 保持兼容。Manager 的生命周期服务组合这些窄操作，
Runtime 不自行改 Application/Instance desired state。

所有请求继续使用精确 key Schema、token、帧大小和字段上限。环境相关错误不回显值。

## 16. 第一施工顺序

1. RefStore BWA Run binding、desired/startup 更新和异常 Upper 门；
2. 动态 launch spec 与 BWA OCI plan 单元测试；
3. `prepareBwa`、正常 stop/finalize 和现有 commit 接合；
4. Manager Lifecycle start/stop/save-restart；
5. Supervisor 自行退出分类；
6. daemon/Manager/宿主恢复；
7. failed Upper 提交与丢弃；
8. 真实诊断镜像端到端验收。

## 17. V0.14-B 阶段出口

- 诊断 BWA 从固定 digest 启动，且不经过静态 ExecutorRegistry；
- 容器为非 root、零 capabilities、只读 rootfs，只写 Workspace/tmp；
- 普通与敏感环境正确注入且不进入 manifest/log；
- 正常 stop 和 exit 0 原子提交 Workspace；
- 保存并重启后状态继续且 Run ID 改变；
- 非零退出、OOM、强制停止和 daemon 中断均不自动提交；
- 异常 Upper 可以提交或丢弃，并在处置前阻止新 Run；
- 受控关机提交，非受控恢复保持 Ref 不变；
- Application 更新门不会留下混合 digest 的运行 Instance；
- V0.13 固定 Executor、提交和恢复测试全部不退化。

达到出口后进入 Runtime Proxy、网络与 iframe 局部设计。
