# 浏览器云端个人桌面 V0.7 桌面表面技术设计

状态：评审通过，待施工

对应需求：[V0.7 桌面表面需求方案](<浏览器云端个人桌面 V0.7 桌面表面需求方案.md>)

## 1. 总体结构

```text
DesktopSurface React
  ├─ Target Resolver
  │    ├─ app → App 表
  │    ├─ file → File Service EntryIndex
  │    └─ directory → File Service EntryIndex
  ├─ Selection / Marquee / Group Drag 状态机
  ├─ Desktop Context Menu
  ├─ Pixel Layout、碰撞求解与 Auto Align
  └─ Desktop Surface API
         └─ SQLite revision/CAS
```

Desktop Surface 不进入第三方 iframe，也不作为新的第三方协议。

## 2. 持久化模型

```ts
interface DesktopSurfaceRecord {
  schemaVersion: 1;
  revision: number;
  initialized: boolean;
  items: DesktopItem[];
}

interface DesktopItem {
  id: string; // 128-bit random lowercase hex
  target:
    | { type: "app"; handle: string }
    | { type: "file"; handle: string }
    | { type: "directory"; handle: string };
  position: { x: number; y: number };
  createdAtMs: number;
  lastKnownName?: string;
}
```

约束：

- `id`、目标和位置唯一；
- x/y 为非负安全整数，单位为逻辑 CSS 像素，并设置合理上限；
- app handle 按 app ID 语法校验；
- file/directory handle 为 32 位小写十六进制 Entry ID；
- 目标类型和 handle 发布后不原地改变；改变目标应删除旧项目并创建新项目；
- 任何批量变更只增加一次 revision。

SQLite 位于 `/data/desktop-surface.sqlite`。它保存可变 UI 引用，不复制文件元数据。selection、
marquee、pointer 坐标和拖动预览不持久化。

`lastKnownName` 是非权威展示缓存。Resolver 成功时更新它，目标失效时用它代替裸 handle。
缓存更新不增加 surface revision，不参与定位、权限、文件事实或 CAS；目标恢复后仍以 Resolver
当前名称覆盖。

## 3. 服务 API

第一版采用明确批量操作：

```text
GET    /api/v1/desktop-surface
POST   /api/v1/desktop-surface/items
PATCH  /api/v1/desktop-surface/layout
DELETE /api/v1/desktop-surface/items
POST   /api/v1/desktop-surface/resolve
```

添加请求包含 target、期望位置和 expectedRevision。服务验证目标当前存在且类型相符；重复目标
返回冲突。

布局请求：

```json
{
  "expectedRevision": 12,
  "moves": [
    { "itemId": "32 hex", "position": { "x": 328, "y": 222 } },
    { "itemId": "32 hex", "position": { "x": 434, "y": 222 } }
  ]
}
```

服务在同一 SQLite 事务中验证项目存在、位置无重复、未移动项目不冲突以及 revision CAS，
然后一次提交。

批量移除只删除引用。解析接口返回展示投影，不返回文件 content ref、FID 或 capability。

桌面图标右键菜单直接调用同一批量移除 mutation（单项数组），不引入另一套删除语义。
任务栏右键菜单复用现有 pin/unpin 状态；取消固定与关闭运行窗口保持为两个独立命令。

现有产品尚无用户会话，路由至少要求精确 Desktop Origin 和 same-origin Fetch Metadata。
从文件管理器添加 Entry 时额外接受并验证 `system.files` 窗口实例。未来引入用户账户时，
surface 自然绑定 user ID，不改变项目模型。

## 4. Resolver

宿主维护封闭注册表：

```ts
interface DesktopTargetResolver {
  type: string;
  validateHandle(handle: string): boolean;
  resolve(handles: string[]): Promise<ResolvedDesktopTarget[]>;
}
```

Resolver 只解析状态和允许的宿主动作：

- App Resolver：名称、图标、active/disabled/missing；
- File Resolver：当前名称、文件类型、存在状态；
- Directory Resolver：当前名称、存在状态。

第三方 manifest 不能注册 Resolver。未来增加 `view` 时通过新版本 schema 和宿主实现扩展，
不接受未知类型“透传执行”。

## 5. 激活动作

应用复用 `openApp(appId)`。

App 菜单的应用项目保持单一主按钮。`click` 调用 `openApp`；`contextmenu`、菜单键和
`Shift+F10` 打开宿主管理浮层。浮层从 Desktop Surface 和 `pinnedAppIds` 派生两组互斥文案，
不保存重复状态。桌面 mutation 等待服务端成功后关闭，失败时保留错误；任务栏切换复用现有
pin/unpin store，不能调用窗口关闭逻辑。

文件复用 V0.5 的 resolve → Handler/default → Pending Launch → capability 流程。桌面只提供
Entry ID，不接触目标应用 handle。

目录使用 internal `Directory Launch Broker`：

```ts
openApp("system.files", { directoryEntryId });
```

Broker 只在宿主内存保存待导航 Entry ID。文件管理器验证 Entry 当前仍为目录后导航；已打开时
聚焦并切换目录。它不是第三方协议，也不签发文件内容权限。

## 6. 初始化与迁移

当前 localStorage `PersistedDesktopState v2` 继续保存窗口、壁纸、任务栏和默认关联，不再负责
桌面项目。

Desktop Surface 第一次初始化时：

1. 读取当前 App 表；
2. 把当时 `desktop: true` 的有效应用各创建一个项目；
3. 按当前列优先顺序分配默认网格，并保存换算后的像素坐标；
4. 原子设置 `initialized = true`；
5. 后续应用安装不能仅凭 manifest 强制添加图标，由用户选择“添加到桌面”。

初始化具备幂等保护，两个标签页不能重复生成项目。

## 7. 客户端状态

持久状态与交互状态分开：

```ts
interface DesktopInteractionState {
  selectedItemIds: Set<string>;
  focusedItemId: string | null;
  marquee: null | {
    pointerId: number;
    origin: Point;
    current: Point;
    baseline: Set<string>;
    mode: "replace" | "toggle" | "add";
  };
  drag: null | {
    pointerId: number;
    origin: Point;
    itemIds: string[];
    originalPositions: Map<string, DesktopPosition>;
    previewDelta: Point;
  };
  contextMenu: null | {
    anchor: Point;
  };
}
```

高频 pointermove 留在组件局部状态或 reducer，不写全局持久 store。只有 selection 结果需要供
上下文菜单读取；只有 drop 结果调用服务 API。

## 8. 指针状态机

统一使用 Pointer Events：

```text
idle
  ├─ blank pointerdown → pending-marquee
  │    ├─ movement < 4px + up → clear/保留选择
  │    └─ movement ≥ 4px → marquee → up/cancel → idle
  └─ item pointerdown → pending-drag
       ├─ movement < 4px + up → click selection
       ├─ movement ≥ 4px → group-drag → valid drop → commit
       └─ cancel/invalid/conflict → restore → idle
```

组件必须调用 `setPointerCapture`，并处理 `lostpointercapture`。双击只有在两次完整 click 都未
进入 drag 时触发。拖动开始后阻止 click/double-click activation。

框选命中使用一次读取的图标 DOMRect 集合，并在滚动/resize 后重新计算。选择框坐标转换到
desktop-icon-layer 本地坐标，不能混用 viewport 和持久坐标。窗口、任务栏和菜单的层级及
pointer target 保持高于图标层；不能用覆盖全屏的交互层截获这些区域。

## 9. 桌面右键菜单

`contextmenu` 处理器挂在 desktop-icon-layer 上，通过事件冒泡覆盖空白和图标。只有当事件的
传播路径仍属于桌面表面时才调用 `preventDefault()`；窗口、iframe、任务栏、开始菜单和浮层
不在该层内。

菜单使用宿主 React 浮层渲染，按桌面可见边界修正坐标，并具备 `menu` / `menuitem` 语义。
打开菜单不改变当前选择。“刷新”处理器只关闭浮层，不调用 `location.reload()`、数据重新
获取或任何 mutation。该 no-op 必须有组件测试，防止后续维护误接真实刷新。

“自动对齐”读取当前 surface 和可见网格，计算全部项目的新像素位置，并通过同一个 layout
mutation 原子提交。计算期间不修改 selection；CAS 冲突后重新读取，不自动重放。

## 10. 像素布局、成组移动与自动对齐

Pixel Layout 负责：

- desktop-icon-layer 本地像素坐标与 DOMRect；
- 视口可用边界；
- 首个空格自动放置；
- 成组像素 delta；
- 与未选项目的碰撞检查；
- 从期望 delta 向外做有界搜索，寻找最近合法整组位置；
- 小视口临时投影。

候选位置只能为所有项目应用同一个 delta，不得重排组内位置。碰撞求解是纯函数并用黄金用例
测试。拖动期间只渲染 preview transform；成功响应后替换规范 positions，失败恢复原位置。

默认网格只用于初始化、自动放置和“自动对齐”，不能介入普通 pointerup。自动对齐算法：

1. 以当前 `y`、`x`、`createdAtMs`、`id` 排序项目；
2. 为每个项目生成按平方欧氏距离排序的可见网格候选；
3. 距离相同时按固定方向和网格坐标打破平局；
4. 依次领取未占用的最近候选；
5. 生成全部 moves 后一次提交。

这是一种确定性的贪心就近分配，不使用全局匹配算法。图标数量和桌面规模不需要承担更复杂
算法的实现与测试成本。

## 11. 并发与失败

- 所有 mutation 携带 expectedRevision；
- 冲突后重新读取 surface，不自动重放拖动；
- 请求期间锁定新的持久 mutation，但仍允许取消本地选择；
- 网络失败保留服务端已知布局并恢复 preview；
- Resolver 失败只把项目标记为暂时不可用，不删除引用；
- 批量移动和批量移除必须全成或全败。

## 12. 测试分层

- 纯函数：框选矩形、修饰键集合运算、像素碰撞、边界和自动对齐；
- reducer：pointer 状态转换、阈值、cancel 和 lost capture；
- 组件：单选、框选、多选拖动、键盘、双击、右键菜单边界和“刷新”无副作用；
- 服务：schema、Resolver、CAS、批量原子性和初始化幂等；
- 集成：App、文件、目录添加与激活；
- 真实浏览器：重叠窗口、不同缩放、两个标签页、容器重启。
