# 浏览器云端个人桌面 V0.1 施工计划

## 1. 开工结论

技术设计具备实施可行性，核心业务链路已经闭环，可以进入开发。

闭环检查结果：

- 应用来源：内建应用兜底，运行时配置提供业务应用；
- 启动入口：桌面图标、App 菜单和任务栏最终进入同一个 `openApp` 命令；
- 运行控制：创建、聚焦、隐藏、显示、最大化、恢复和关闭均有唯一控制路径；
- 单实例：runtime Map、创建中集合和恢复门闩共同防止重复窗口；
- 状态保存：产品状态可序列化，机械对象只保留在内存；
- 会话恢复：先加载配置、清理失效 ID，再恢复窗口，最后恢复活动窗口；
- 异常降级：配置失败仍能打开内建设置，单个应用错误不影响桌面；
- 部署：静态构建、Nginx、运行时挂载 `apps.json` 和健康检查形成完整交付链路。

开工前不需要 UI 稿、后端接口或额外产品决策。WinBox 的少量行为验证属于阶段二施工内容，不构成开工阻塞。

## 2. 施工规则

1. 严格按六个阶段推进，不跨阶段提前实现业务。
2. 每阶段只提交该阶段范围内的文件。
3. 每阶段结束必须满足：
   - TypeScript 类型检查通过；
   - `npm run build` 通过；
   - 当阶段已有单元测试全部通过；
   - 人工验收项通过；
   - 工作区不存在调试文件和无关改动。
4. 发现 WinBox 行为与设计不符时，先记录验证结果并做局部适配；不自行更换窗口库。
5. 不新增设计清单之外的运行依赖。确需新增时，先说明用途和不可替代性。
6. 每阶段保持 `npm run dev` 可启动，阶段六后保持 Docker 可部署。

## 3. 分支与提交策略

实施建议从设计 PR 合并后的 `main` 创建开发分支：

```text
agent/implement-v0-1
```

阶段提交建议：

```text
build desktop skeleton
add WinBox window lifecycle
add runtime app registry
add taskbar window controls
add desktop persistence
add settings and deployment
```

如果设计 PR 尚未合并，也可以在当前设计分支继续施工，但会让设计审查与代码审查混在一个 PR 中，因此默认等待设计 PR 合并后再开实施分支。

```text
阶段一 桌面骨架
   ↓
阶段二 窗口垂直切片
   ↓
阶段三 运行时应用注册表
   ↓

   ↓
阶段五 持久化与会话恢复
   ↓
阶段六 设置、部署与最终验收
```

不能并行施工的原因：

- 阶段二依赖阶段一的窗口层和基础 store；
- 阶段三依赖阶段二已验证的应用打开路径；
- 阶段四依赖稳定的窗口回调状态；
- 阶段五依赖前四阶段最终状态模型；
- 阶段六的设置和测试需要前面业务行为稳定。

## 6. 阶段二：窗口垂直切片

### 6.1 目标

用一个“关于”内建应用贯通 React → 控制器 → WinBox → store → React Root 卸载的完整生命周期。

### 6.2 施工顺序

1. 安装并锁定 WinBox 精确版本。
2. 验证 ESM 和 CSS 导入路径；按实际使用面补最小 TypeScript 声明。
3. 建立全屏 WindowLayer 引用注册。
4. 建立 runtime Map 和 `creatingAppIds`。
5. 实现窗口边界计算和初始居中。
6. 实现 `openApp`：
   - 校验应用；
   - 单实例判断；
   - 创建标记；
   - 建立容器和 React Root；
   - 创建 WinBox；
   - 登记 runtime；
   - 渲染内容；
   - 失败回滚。
7. 接入 WinBox focus、blur、move、resize、maximize、restore 和 close 回调。
8. 实现唯一 `finalizeClose`，加入只卸载一次保护。
9. 接入“关于”应用，从 App 菜单启动。
10. 验证 Strict Mode 下不会重复创建。
11. 验证任务栏底部边界和窗口 resize 后 clamp。

### 6.4 必做 WinBox 探针

建立一个临时开发验证页面或测试函数，验证后删除临时代码并将结论记录到代码注释或测试中：

- `root`、`mount`、`bottom` 和控制类；
- 回调顺序与参数；
- `hide/show` 是否触发 blur；
- `onclose` 返回值；
- iframe 点击与 focus；
- 最大化后 resize；
- 关闭时 WinBox unmount 与 React unmount 的次序。

如果 `hide()` 不触发 blur，采用设计中的显式 `blur()` 和 `activeAppId = null`。

### 6.5 测试与验收

单元测试：

- 边界 clamp；
- 重复 `openApp` 不创建第二个 runtime；
- 重复关闭只调用一次 Root unmount；
- 创建失败清理 runtime 和创建标记。

人工验收：

- 关于应用可从菜单启动；
- 可拖动、缩放、聚焦、最大化、恢复和关闭；
- 窗口不进入任务栏区域；
- 关闭后 DOM、runtime 和运行状态全部消失；
- Strict Mode 下无重复窗口和 React 未卸载警告。

## 8. 阶段四：任务栏完整控制

### 8.1 目标

让用户完全通过任务栏控制应用，并完成单实例业务闭环。

### 8.2 施工顺序

1. 实现固定 ID 与运行 ID 的稳定合并和去重。
2. 实现未运行、运行、活动、隐藏四种视觉状态。
3. 实现任务栏点击状态机。
4. 将隐藏定义为独立 boolean，保留最大化状态。
5. 隐藏活动窗口时显式 blur 并清空 active。
6. 再次显示时先 show 再 focus。
7. 实现右键菜单视口定位、点击外部和 Escape 关闭。
8. 实现固定、取消固定和关闭操作。
9. external 固定应用不显示运行状态。
10. 完善时钟整分钟对齐与 timer 清理。

### 8.3 文件

```text
src/desktop/TaskbarItem.tsx
src/components/ContextMenu.tsx
src/store/desktopStore.test.ts
```

同步修改 Taskbar、desktop.css、windowController 和 store。

### 8.4 状态机验收

| 当前状态 | 点击任务栏 | 结果 |
|---|---|---|
| 未运行 | 启动 | 创建并聚焦 |
| 已隐藏 | 显示 | 保留最大化状态并聚焦 |
| 可见但非活动 | 聚焦 | 置前并标记活动 |
| 可见且活动 | 隐藏 | blur，活动状态清空 |
| external | 打开 | 新标签，不产生运行态 |

测试必须覆盖固定/取消固定、单实例、隐藏后恢复、最大化后隐藏再恢复，以及关闭未固定运行应用后任务栏项目消失。

## 9. 阶段五：持久化与会话恢复

### 9.1 目标

确保刷新后恢复用户桌面，同时对损坏数据、旧版本和已删除应用安全降级。

### 9.2 施工顺序

1. 定义 schemaVersion 1 的完整持久化结构。
2. 加入 `preferencesInitialized`，明确首次固定逻辑。
3. 实现安全 parse 和字段级校验。
4. 实现 300ms 集中防抖与 `pagehide` flush。
5. 移动和缩放回调只更新内存状态，由防抖层写入。
6. 启动时先读本地状态，再加载最终应用注册表。
7. 清理不存在、无效和 external 的 ID。
8. 暂停持久化，串行恢复去重后的运行应用。
9. 恢复普通边界、hidden 和 maximized。
10. 最后恢复合法且可见的 active；否则为 null。
11. 恢复完成后一次性写入协调后的状态。
12. 浏览器尺寸变化时修正窗口边界。

### 9.3 文件

```text
src/store/persistedState.ts
src/store/persistedState.test.ts
src/windows/windowBounds.test.ts
```

同步修改 bootstrap、store、windowController、windowBounds、SettingsApp 和类型。

### 9.4 测试矩阵

- localStorage 不存在；
- 非法 JSON；
- 未知 schemaVersion；
- 字段类型损坏；
- 用户取消全部固定后刷新仍为空；
- 配置删除已固定或运行应用；
- runningAppIds 重复；
- hidden + maximized 组合；
- active 指向隐藏、external 或已删除应用；
- 保存坐标在当前视口之外；
- 恢复期间回调不会写入半成品快照；
- 用户明确关闭的窗口刷新后不恢复。

### 9.5 人工验收

分别验证壁纸、固定项、普通窗口边界、最大化窗口、隐藏窗口、多个窗口和活动窗口的刷新恢复。
