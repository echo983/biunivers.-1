# ADR-0001：应用接入与特权边界

状态：已接受

日期：2026-07-28

适用范围：V0.1 之后的应用接入设计

## 背景

Biunivers 需要同时满足两类需求：

- 少量系统功能需要直接访问桌面状态和宿主能力，例如设置、关于和未来的系统诊断；
- 大多数业务应用应当独立开发和部署，例如计算器、笔记、下载器及其他自托管 Web 服务。

如果所有应用都作为宿主内的 React 组件运行，第三方代码将天然拥有过大的能力，应用接入也会要求重新编译桌面。如果为第三方应用立即设计完整插件 SDK、权限系统和动态模块运行时，又会显著扩大项目范围。

因此需要明确一个长期稳定但足够小的应用信任边界。

## 决策

应用运行时分为三个层级：

| 类型 | 注册来源 | 宿主能力 | 主要用途 |
|---|---|---|---|
| `internal` | 编译期白名单 | 可直接使用明确开放的桌面 store 和宿主函数 | 设置、关于、系统诊断等少量系统应用 |
| `iframe` | 已安装静态应用或管理员运行时配置 | 默认不提供桌面 API | 计算器、笔记、小游戏及其他第三方应用 |
| `external` | 运行时 `apps.json` | 无 | 无法或不应嵌入的网站 |

总体原则：

> 宿主特权层保持极小；业务应用默认在宿主之外运行。

### internal

`internal` 是最小化的特权层，不作为普通第三方接入方式。

必须遵守：

1. internal 应用只能在源码中的编译期白名单注册；
2. 运行时 `apps.json` 不得新增 internal 应用；
3. internal ID 和组件映射必须静态、明确且可审查；
4. 不根据配置字符串动态导入任意模块；
5. internal 应用数量保持尽可能少；
6. 只有确实需要宿主状态或系统操作的功能才能进入该层。

建议映射形式：

```ts
const internalApps = {
  "system.settings": SettingsApp,
  "system.about": AboutApp,
} as const;
```

运行时配置如需调整内建应用，只能覆盖允许的展示字段，例如：

- 名称；
- 图标；
- 描述；
- 默认和最小窗口尺寸；
- 是否显示桌面图标；
- 默认固定状态。

运行时配置不得改变：

- internal ID；
- `kind`；
- `internalComponent`；
- 组件实现；
- 可访问的宿主能力。

实现收紧时可以采用以下任一策略：

- 最简单策略：`apps.json` 完全禁止 `kind: "internal"`；
- 兼容展示覆盖策略：只允许与编译期 internal ID 完全匹配的条目，并强制保留其 `kind` 和组件映射。

默认优先采用最简单策略，除非部署时覆盖内建应用展示信息已成为实际需求。

### iframe

`iframe` 是大多数第三方应用的标准接入方式。

iframe 有两种来源：

1. 通过 Biunivers 应用管理流程从公开 GitHub 仓库安装，并由 Biunivers 托管的静态应用；
2. 由管理员直接配置 URL 的兼容型远程 Web 应用。

两者使用相同的桌面窗口 runtime，但安装、版本和信任记录不同。已安装静态应用必须提供根目录 `index.html`，遵守显式版本的 Biunivers Static App Protocol，并由管理服务生成 APP 表投影。第三方 manifest 不能直接注册 `internal`。

第三方应用负责自身内容和业务状态；桌面负责：

- 窗口标题栏；
- 拖动和缩放；
- 最小化到任务栏；
- 最大化和还原；
- 聚焦；
- 关闭；
- 单实例；
- 窗口状态恢复。

第三方应用不应自行绘制第二套外层窗口控制，也不能直接读写桌面持久化 key。

当前不向 iframe 提供 Host API。第三方应用不能：

- 创建宿主窗口；
- 修改任务栏；
- 修改桌面设置；
- 动态修改宿主窗口标题；
- 请求宿主通知；
- 读取其他应用或桌面状态。

如果以后出现真实的跨边界需求，应先定义少量、版本化、可审查的消息接口，不直接暴露 Zustand store 或任意宿主函数。

文件类型关联、应用间打开和资源句柄属于未来独立的 Resource Exchange Protocol，不进入静态应用安装协议。

### 已安装静态应用

第一版第三方生态采用“GitHub 公开仓库 → 校验 → 本地托管 → APP 表 → iframe”的闭环：

1. 仓库根目录提供固定 `index.html`；
2. 仓库提供机器可读 manifest；
3. 仓库根目录保存所声明版本的 Biunivers 接入协议原文；
4. 安装固定到 Git commit SHA；
5. 安装器不执行仓库构建脚本；
6. 安装器只提供固定 commit 中经过路径检查的普通静态文件，不提供 Git 元数据、dotfile、manifest 和协议文档；
7. 用户在安装流程中填写公开客户端配置；
8. 管理服务原子注册、更新、停用和卸载应用。

应用内部使用 JavaScript、前端框架、WASM、WebGL、Canvas 或 Worker 不影响宿主模型。需要 Node、Python、数据库或其他服务端运行时的应用不属于该静态应用包。

静态应用不存在真正的进程环境变量。安装配置最终会交付给浏览器，不能包含密码、私钥或其他 secret。

### external

无法嵌入、无需桌面集成或不应获得 iframe 环境的应用使用 `external`，始终通过用户操作在新标签页打开。

external 不创建窗口 runtime，不进入运行应用和会话恢复状态。

## iframe 安全边界

当前的 `trusted: true` 表示管理员信任该 iframe 应用，不等于浏览器级权限隔离。

尤其需要注意：

- 同源且未设置 `sandbox` 的 iframe 可能访问父页面 DOM；
- 同源 iframe 可能访问桌面使用的 localStorage；
- 反向代理到同一域名能够简化 Cookie 和认证，但会扩大同源信任范围；
- `Content-Security-Policy: frame-ancestors` 和 `X-Frame-Options` 决定目标页面能否被嵌入；
- Cookie 的域、`SameSite` 和 `Secure` 会影响 iframe 登录状态。

在没有 sandbox 配置模型之前：

- 完全可信的自托管应用可以通过同源 iframe 接入；
- 不完全可信的应用优先使用独立 origin；
- 无法确认安全边界的应用使用 `external`；
- 不允许普通页面或最终用户输入任意 URL 创建 iframe。

## 未来的 sandbox 方向

如果实际使用证明有必要，可以增加少量宿主预定义的 sandbox profile，例如：

```json
{
  "kind": "iframe",
  "sandboxProfile": "restricted"
}
```

由宿主把 profile 映射为固定策略：

```ts
const sandboxProfiles = {
  restricted: "allow-forms allow-scripts",
  authenticated: "allow-forms allow-scripts allow-same-origin",
} as const;
```

第三方配置不能自由填写任意 sandbox 权限组合。增加 profile 前必须通过真实应用验证需求，避免提前演变为完整权限系统。

## 第三方窗口内容建议

第三方 iframe 应用应：

- 根元素填满 iframe 视口；
- 避免横向滚动条；
- 适应从声明的最小尺寸到最大化尺寸；
- 不依赖固定屏幕坐标；
- 不自行提供宿主窗口最小化、最大化或关闭按钮；
- 为键盘操作和 focus 状态提供基本可访问性；
- 使用自己的命名空间保存状态，例如 `calculator.history.v1`；
- 不读取或写入 `biunivers.desktop.v1`。

## 不在本决策中实现

本决策不授权或要求立即增加：

- 插件 SDK；
- 动态 JavaScript 模块安装；
- 权限申请界面；
- capability 系统；
- 应用签名；
- 跨应用事件总线；
- 任意 URL 安装；
- 细粒度 sandbox 权限编辑器；
- 应用间资源交换；
- 安装第三方服务端进程；
- 安装期间执行第三方构建代码。

这些能力只有在实际第三方应用证明现有三层模型不足时，才进入新的需求与设计流程。

## 影响

正面影响：

- 系统特权面保持可审查；
- 第三方应用可以独立开发和部署；
- 桌面不需要为普通应用重新编译；
- 不需要提前建设完整插件平台；
- 后续可以渐进增加隔离或 Host API。

代价：

- iframe 应用暂时无法调用宿主功能；
- 同源 iframe 仍需要管理员承担信任判断；
- internal 应用必须通过源码变更和桌面发布流程；
- 需要收紧现有配置校验，防止新 ID 复用 `settings` 或 `about` 组件成为 internal 别名。

## 后续实施约束

下一次修改应用注册表或配置协议时，应至少完成：

1. 运行时配置禁止创建新的 internal ID；
2. internal 映射收敛为编译期 ID → 组件映射；
3. 为上述限制增加配置校验单元测试；
4. 已安装静态应用只能投影为 iframe；
5. README 的第三方接入说明引用本决策；
6. 若引入 sandbox profile，单独编写新的 ADR 或版本设计；
7. 若引入跨应用资源能力，单独定义 Resource Exchange Protocol。
