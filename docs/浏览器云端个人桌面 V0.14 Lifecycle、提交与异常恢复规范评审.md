# 浏览器云端个人桌面 V0.14 Lifecycle、提交与异常恢复规范评审

状态：评审通过，可施工

日期：2026-07-31

评审对象：《浏览器云端个人桌面 V0.14 Lifecycle、提交与异常恢复局部设计》

## 1. 结论

设计在 V0.14-B 范围内闭环，可以施工。它没有复制 V0.13 Runtime 和提交器，而是在
Application/Instance 层补充动态镜像执行、用户意图、正常结束分类和异常 Upper 门禁。

## 2. 必要性审查

以下内容不可继续后移：

- BWA Run 与 Instance/digest 的持久绑定；
- 动态 launch spec 与固定 Executor 的隔离；
- 正常与异常结束的确定分类；
- stop→commit 和 save→restart 的串行协调；
- daemon/宿主中断不自动提交；
- 异常 Upper 在更新、卸载和新 Run 前的门禁；
- secret 不落 Runtime manifest；
- 受控关机先于 Runtime daemon shutdown。

缺少任一项都可能造成运行错误镜像、丢失写入、异常内容自动发布、平行写或用户看到虚假的
“已保存”。

## 3. 已删除的过度设计

- 不建立 Task/Session/Service 三套类型；
- 不引入通用调度队列；
- 不让应用声明 Docker 参数或资源权限；
- 不将动态 BWA 塞进可持久注册的 Executor 清单；
- 不从磁盘恢复 secret；
- 不做运行中 checkpoint；
- 不自动周期 stop/commit/restart；
- 不做异常退出无限重启；
- 不做自动三方合并；
- 不实现失败 Upper 的原地续跑；
- 不在 B 阶段实现代理、WebSocket 和最终 UI；
- 不持久化第二份 observed state/current Run 真相。

这些删减保留了数据安全闭环，同时避免把 Lifecycle 演化为 Kubernetes/Compose 式编排器。

## 4. 自洽性检查

### 4.1 动态执行身份

Application digest 已由 V0.14-A 固定；每个 Run binding 再记录实际 digest，因此更新后仍能
解释历史 Run。环境只用于创建容器，不参与长期执行身份。

### 4.2 写租约

启动先创建控制 Run并取得 Workspace 写租约，Runtime 才能 prepare。异常结束将控制 Run
标 FAILED 并释放租约，但 Instance 的异常 Upper 门继续阻止新 Run，避免“租约已释放”等同
“现场已处理”的错误推论。

### 4.3 正常提交

正常停止先终结容器和挂载，再扫描稳定 Upper，复用现有 CAS 提交。没有第二条写入路径。
no-op、冲突和提交失败语义与 V0.13 一致。

### 4.4 保存重启

保存不是在线 checkpoint。旧 Run 必须正常提交结束，新 Run 才能从新 Head 创建；任何一步
失败都不会同时保留两个写容器。

### 4.5 异常恢复

异常 Run 不自动提交。提交保留 Upper 时必须重新取得租约并验证 input Head；Ref 已前进则
冲突关闭。丢弃是唯一删除现场的动作，且必须由用户显式提出。

## 5. 需要在施工中验证的风险

### 5.1 Docker stop 分类

必须在 remove 前 inspect 最终状态，并以单元测试覆盖正常 SIGTERM、exit 0、137/OOM 和 stop
失败。若 Docker CLI 无法可靠区分超时强杀，Runtime 必须采用更明确的 stop/kill 序列，不能
猜测为正常。

### 5.2 固定 UID 对镜像兼容

真实诊断镜像必须以 `65532:65532` 成功读取程序并写 Workspace。失败时修订镜像交付规范，
不能退回运行 root。

### 5.3 Secret 生命周期

prepareBwa 后 start 前中断必须清空内存 launch spec；日志和异常快照需检查不包含测试 secret。
Docker inspect 对宿主管理员可见属于已声明威胁模型，不向普通界面返回。

### 5.4 Manager 与 Runtime 双重故障

每个状态转换必须可重入或在重启对账中得到唯一结论。特别检查“容器已停、控制 Run 仍
RUNNING”和“已提交、响应前 Manager 崩溃”。

## 6. 分段施工门

第一段只实现：

```text
绑定 BWA Run
→ 动态 prepare/start
→ 用户正常 stop
→ commit
```

该链通过真实诊断镜像后，再增加自行退出 Supervisor、保存重启和异常 Upper 人工处置。
这样每次扩展均建立在已验证状态机上。

## 7. 最终判断

V0.14-B 的复杂度主要来自必须诚实地区分“进程结束”“本地写入稳定”和“状态已经提交”。
当前设计为三者保留独立状态，没有用单一 running 布尔值掩盖失败窗口；同时删去了原地续跑
和通用调度等低必要能力，符合第一版边界。
