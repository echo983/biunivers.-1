# 浏览器云端个人桌面 V0.5 资源打开设计

状态：规范评审通过，协议冻结候选，待施工

版本主题：文件关联、打开方式与窗口级资源交付

## 1. 目标

V0.5 首先完成一个可验证的用户闭环：

> 用户在 internal 文件管理器中双击一个 `.txt` 文件，Biunivers 选择或询问一个兼容的第三方
> 记事本应用，为目标窗口重新签发文件 capability，并让记事本通过既有 Host API 读取、编辑
> 和保存该文件。

本设计同时为未来“NAS 文件管理应用把 MKV 交给视频播放器”等场景保留一致的扩展方向，
但不在第一版实现通用应用间调用、媒体流优化或复杂资源管道。

## 2. 核心决策

采用“应用自报能力 + 系统管理关联”的混合模型：

1. 应用包声明自己能够处理哪些资源；
2. 安装器验证声明并将其登记为候选处理器；
3. Biunivers 维护有效候选和用户默认关联；
4. 用户决定默认用哪个应用打开某类文件；
5. 每次打开时，宿主针对目标应用和窗口重新签发 capability。

一句话边界：

> 应用声明“我能处理什么”，Biunivers 决定“它是否可以参与”，用户决定“默认用谁”，宿主
> 决定“这一次能访问哪个资源”。

应用的能力声明不是文件访问权限，也不能自动把应用设为默认处理器。

## 3. 与现有协议的关系

以下已经发布或实现的边界保持不变：

- Static App Protocol v1 继续只定义静态应用包和 iframe 运行方式；
- App Manifest v1 不原地增加文件处理器字段；
- Host API v1 继续负责文件句柄、读取、写入、元数据和释放；
- PVLogS3Lite、FID、S3 Key、RefStore 和 Entry 结构不暴露给第三方应用；
- internal 文件管理器仍是受信任系统界面，不把自身特权转交给第三方。

V0.5 新增一个独立、可选、带版本的资源打开扩展。暂定名称：

```text
Biunivers Open Resource Protocol v1
```

规范评审后再冻结协议原文、固定文件名和 JSON Schema。预期第三方仓库根目录包含：

```text
BIUNIVERS_OPEN_RESOURCE_PROTOCOL_V1.md
biunivers.open-resource.json
```

没有该扩展的应用仍可按 Static App Protocol v1 正常安装和运行，只是不能成为文件处理器。

## 4. 概念模型

### 4.1 Handler 声明

应用作者在应用包中自报处理能力。例如：

```json
{
  "protocol": "biunivers.open-resource/1",
  "handlers": [
    {
      "id": "text-editor",
      "actions": ["open", "edit"],
      "extensions": [".txt", ".md"],
      "mediaTypes": ["text/plain", "text/markdown"],
      "access": "read-write"
    }
  ]
}
```

声明仅表示应用希望成为候选处理器，不表示：

- 声明内容一定可信；
- 应用已成为默认处理器；
- 应用可以枚举或读取所有匹配文件；
- 应用每次打开都能获得声明的最大权限。

### 4.2 已注册候选

安装器完成协议原文和 schema 校验后，把声明作为已安装应用记录的一部分保存。有效候选集合
必须从当前已安装且启用的应用派生，不能由 iframe 在运行时修改。

### 4.3 默认关联

默认关联是用户或桌面策略选择，不属于应用包。最小记录为：

```json
{
  "extension:.txt": {
    "appId": "io.github.echo983.biunivers-notepad",
    "handlerId": "text-editor"
  }
}
```

应用安装、更新不得未经用户确认抢占默认关联。应用停用或卸载后，指向它的默认关联视为
失效；恢复安装后是否恢复旧偏好属于后续产品策略。

V0.5 可先把默认关联保存在现有桌面持久化状态中。未来多用户、多设备同步可以迁移到服务端
用户设置，不改变对外协议。

### 4.4 一次资源授权

一次打开操作产生一个新的不透明文件句柄。句柄至少绑定：

- 目标 `appId`；
- 目标 `windowInstanceId`；
- 文件 Entry ID；
- 实际授予的读写权限；
- 过期时间；
- 用于冲突检测的版本状态。

句柄是宿主内部 capability。默认关联和 Handler 声明都不能代替句柄。

## 5. Handler V1 最小字段

V1 只保留完成闭环所需字段：

| 字段 | 含义 |
|---|---|
| `id` | 应用内部稳定的处理器 ID |
| `actions` | 支持 `open`、`edit` 中的一项或两项 |
| `extensions` | 小写、带前导点的扩展名列表 |
| `mediaTypes` | 标准媒体类型列表，可为空 |
| `access` | 最大能力：`read` 或 `read-write` |

校验要求：

- Handler ID 在同一应用内唯一；
- 每个 Handler 至少声明一个扩展名或媒体类型；
- 扩展名统一为小写并以 `.` 开头；
- 不接受路径、glob、正则表达式或任意 URL scheme；
- `access` 只是上限，实际句柄可以降级为只读；
- 未知字段是否拒绝由正式 JSON Schema 统一决定。

第一版不增加 Handler 图标、名称、优先级和入口 URL。名称与图标复用 App Manifest，应用仍
只有一个 `index.html` 入口。

## 6. 匹配与默认选择

当前 File Service 不把 `mediaType` 持久化为权威文件身份字段，因此 V0.5 以文件扩展名完成
首个闭环，不进行内容嗅探。

候选匹配：

1. 如果文件有宿主认可的媒体类型，收集匹配该媒体类型的 Handler；
2. 根据文件名最后一个扩展名收集 Handler；
3. 合并并去重当前已安装、已启用的候选；
4. 不读取文件内容猜测类型。

选择顺序：

1. 有效的用户扩展名默认关联；
2. 有效的用户媒体类型默认关联；
3. 只有一个候选时直接使用；
4. 多个候选时显示“打开方式”；
5. 没有候选时明确提示没有可用应用。

“打开方式”至少显示应用名称和图标，并可选择：

```text
始终使用此应用打开 .txt 文件
```

第一版不做“从应用商店查找”。

## 7. 双击打开流程

### 7.1 发起意图

文件管理器在明确的用户双击下向宿主请求：

```ts
openResource({
  entryId,
  expectedRevision,
  action: "open",
});
```

文件管理器不自行签发第三方句柄，也不把 S3 URL、FID、ContentRef 或路径交给应用。

### 7.2 解析处理器

宿主读取文件的当前元数据，解析候选和有效默认关联。若文件已在请求到处理期间删除或改变，
宿主返回结构化冲突或不存在错误，不使用过时路径继续打开。

### 7.3 创建或复用应用窗口

当前桌面窗口模型以 appId 为键，每个应用只有一个运行窗口。V0.5 不引入全桌面多窗口重构：

- 目标应用未运行时，创建窗口并附加首个待领取上下文；
- 目标应用已运行时，把窗口置前并附加一个新的待领取上下文；
- 宿主向已加载 iframe 发送不含资源信息的 `launch.contextAvailable` 通知；
- 应用收到通知后再次调用 `launch.getContext`；
- 应用负责在切换文件前处理未保存内容。

同一窗口最多保留一个未领取上下文。已有上下文尚未领取时，新打开请求返回忙碌错误，不能
覆盖或丢弃前一个资源。多窗口编辑属于后续独立桌面能力。

### 7.4 重新签发 capability

若需创建窗口，宿主先建立目标应用实例，再为该实例签发新的文件句柄。它不能：

- 转让文件管理器的 internal 句柄；
- 转让来源应用已有的句柄；
- 把目标应用未声明的最大权限直接授予目标窗口。

实际权限取以下条件的交集：

```text
来源操作允许的权限
∩ 目标 Handler 声明的最大权限
∩ 文件或快照当前允许的权限
∩ 用户本次确认的权限
```

### 7.5 交付启动上下文

capability 不放入 iframe URL、query、fragment 或公开配置。目标应用在完成宿主握手后主动
取得一次启动上下文。概念接口为：

```js
const context = await biunivers.launch.getContext();
```

返回示例：

```json
{
  "action": "open",
  "resources": [
    {
      "handleId": "opaque-value",
      "name": "note.txt",
      "mediaType": "text/plain",
      "permissions": ["read", "write"]
    }
  ]
}
```

启动上下文由宿主绑定到目标窗口实例；其他应用和窗口不能读取。应用使用主动拉取取得资源；
`launch.contextAvailable` 只表示有新上下文，不携带 handle，既避免初次加载丢消息，也支持
单实例应用窗口后续打开另一个文件。

V0.5 只允许一个资源。数组形态只为将来兼容保留，不表示 V1 支持批量打开。

### 7.6 应用读取与保存

应用取得句柄后，继续复用 Host API v1：

- `file.stat`；
- `file.readTransfer`；
- `file.writeTransfer`；
- `file.release`。

保存仍使用已有 expected content/revision 冲突保护。发生 `FILE_VERSION_CONFLICT` 时，记事本
必须保留编辑内容并提示重新打开或另存为，不得静默覆盖。

## 8. 安装、更新、停用与卸载

### 8.1 安装

1. 正常完成 Static App 和 Manifest 校验；
2. 若不存在资源打开声明，不增加处理器；
3. 若声明存在，协议原文必须存在且逐字匹配宿主白名单；
4. 校验声明 schema、扩展名、媒体类型和 handler 唯一性；
5. 将已验证声明原子写入正式安装记录；
6. 安装完成后候选处理器才可见。

声明存在但无效时，安装整体失败，避免应用成功安装却静默失去其声称的核心能力。

### 8.2 更新

更新后使用新 commit 的声明原子替换旧候选。新增能力不能自动修改用户默认关联；删除能力后，
不再有效的默认关联被忽略。

### 8.3 停用与卸载

- 停用应用后立即不再作为候选；
- 卸载应用后删除派生的 Handler 注册；
- 关闭或撤销其活动窗口和 capability；
- 不允许留下指向已卸载应用的有效默认关联。

## 9. 来源应用交给目标应用

未来应用 A 请求用应用 B 打开资源时，仍走宿主中介：

```text
A 持有资源 capability
→ A 在用户动作下请求 openResource
→ 宿主验证 A 的 capability 和意图
→ 宿主解析 B 或显示打开方式
→ 宿主为 B 的窗口签发一个全新 capability
```

A 不能把自己的 `handleId` 直接发给 B。宿主重新签发使权限可被降级、审计、过期和按窗口
撤销。

这条原则适用于未来 NAS → 播放器，但 V0.5 只实现 internal 文件管理器作为来源。

## 10. 安全边界

必须满足：

- 文件双击和“打开方式”属于明确用户动作；
- 自报扩展名不会带来目录遍历或文件枚举权限；
- 应用不能自行设置默认关联；
- capability 绑定 app、origin 和 window instance；
- 关闭窗口时撤销未释放句柄；
- 启动上下文不能被其他窗口重复领取；
- URL、日志和错误正文不包含 capability、FID、S3 Key 或 Ref；
- third-party iframe 仍使用独立 App Origin；
- internal 文件管理器权限不能因资源打开而传播；
- 文件关联失效时安全降级到选择器或无处理器提示。

## 11. V0.5 第一版范围

纳入：

- 一个可选的资源打开扩展协议；
- 应用包自报 Handler；
- 安装、更新、停用和卸载时维护候选；
- `.txt` 扩展名匹配；
- 默认关联和打开方式选择；
- 文件管理器双击文件；
- 宿主重新签发目标窗口句柄；
- 窗口启动上下文；
- 记事本读取、编辑、保存和冲突提示；
- 单实例应用窗口的后续资源通知与安全切换。

明确不纳入：

- 多文件批量打开；
- 文件拖放到应用；
- 应用后台或无用户动作调用；
- 应用直接转让句柄；
- 文件内容嗅探；
- Shell 命令、命令行参数和任意 scheme handler；
- 视频 Range/Seek 优化；
- stdin/stdout 式资源管道；
- 编辑锁和多人协作；
- 缩略图、预览器和完整右键菜单；
- 应用商店推荐。

## 12. TXT → 记事本验收闭环

1. 已安装记事本携带有效 Handler 声明；
2. 文件管理器双击 `note.txt`；
3. 唯一候选或用户选择记事本；
4. 记事本窗口收到只属于该实例的启动上下文；
5. 记事本通过 Host API 读取完整文本；
6. 保存产生新的 PVLog revision；
7. 文件移动或重命名后，基于 Entry ID 的已打开窗口仍对应同一文件；
8. 其他应用和窗口不能使用该句柄；
9. 并发修改返回版本冲突且不覆盖新内容；
10. 卸载或停用记事本后，不再被解析为可用处理器。

## 13. 已冻结的评审结论

规范评审已经冻结：

1. 协议标识为 `biunivers.open-resource/1`；
2. Handler 声明与运行时 Launch Context 归入同一个协议；
3. `open` 表示消费资源，`edit` 表示可修改原资源；
4. 唯一候选直接打开，多个候选显示打开方式；
5. 默认关联 V0.5 先保存在浏览器桌面状态；
6. 每个 Launch Context 绑定窗口且只领取一次；窗口可依次接收多个上下文，每个上下文
   5 分钟未领取过期；
7. 失效默认偏好可以保留，但在 Handler 恢复前不能执行。

详细理由和必要性审查见
[V0.5 资源打开规范评审](<浏览器云端个人桌面 V0.5 资源打开规范评审.md>)。
